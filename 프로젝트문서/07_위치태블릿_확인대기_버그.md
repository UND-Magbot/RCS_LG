# 위치 태블릿 — 경유지 확인대기 중 버튼 먹통 버그

- **발견일**: 2026-08-18 (현장 테스트 중)
- **상태**: 미해결 — 수정 방향 미결정
- **심각도**: 중 (로봇/데이터 손상 없음, 조작 경로가 막힘)
- **2026-08-18 재시작 복구 패치와 무관** — 패치 이전부터 있던 버그

---

## 1. 한 줄 정의

> 위치 태블릿의 **화면을 그리는 조건**과 **버튼이 실제로 동작하는 조건**이 서로 다르다.
> 그래서 누를 수 없는 버튼이 화면에 뜬다.

증상: 버튼을 누르면 `404 이 위치에 대기 중인 로봇이 없습니다`

---

## 2. 재현 절차

1. J3 벽 태블릿에서 로봇 호출 → 로봇이 랙을 들고 J3 도착
2. 경유지 경로 `[J4, J3]` 등록 → 로봇 출발
3. 로봇이 **J4 도착**
4. J4 벽 태블릿에 "다음 위치 선택" 그리드와 [작업 종료] 버튼이 뜸
5. 아무 버튼이나 누름 → **404**

---

## 3. 원인

### 3-1. 화면 쪽 — 3가지 상태를 "도착"으로 봄

`app/routers/dispatch.py` 의 `_poi_status()` (309~321행) 가 태블릿 화면 상태를 만든다.

```python
arrived = (
    db.query(DispatchSessionModel)
    .filter(
        DispatchSessionModel.current_poi_id == poi_id,
        or_(
            DispatchSessionModel.status == "awaiting_next",      # ①
            DispatchSessionModel.status == "awaiting_confirm",   # ②
            and_(                                                # ③
                DispatchSessionModel.status == "moving",
                DispatchSessionModel.target_poi_id.is_(None),
            ),
        ),
    )
)
...
if arrived:
    state = "arrived"
```

`state = "arrived"` 가 되면 태블릿은 `app/templates/dispatch_tablet.html` 의
`renderArrived()` (680~717행) 를 그린다 — **다음 위치 선택 그리드 + 작업 종료 버튼**.

### 3-2. 동작 쪽 — 1가지 상태만 인정

버튼이 호출하는 API 3개가 전부 같은 함수를 쓴다.

| 버튼 | API | 정의 위치 |
|---|---|---|
| 다음 위치 선택 | `POST /api/dispatch/poi/{id}/next` | `dispatch.py:795` |
| 작업 종료 | `POST /api/dispatch/poi/{id}/end` | `dispatch.py:814` |
| 경유지 경로 등록 | `POST /api/dispatch/poi/{id}/route` | `dispatch.py:665` |

세 엔드포인트 모두 첫 줄이 같다.

```python
session = dispatch_service.get_session_at_poi(poi_id)
if not session:
    raise HTTPException(status_code=404, detail="이 위치에 대기 중인 로봇이 없습니다")
```

`app/services/dispatch_service.py` 의 `get_session_at_poi()` (1217행):

```python
DispatchSession.current_poi_id == poi_id,
DispatchSession.status == "awaiting_next",     # ① 뿐
```

### 3-3. 불일치 표

| 상태 | 화면 | API | 결과 |
|---|---|---|---|
| ① `awaiting_next` | 도착 | 찾음 | 정상 |
| ② `awaiting_confirm` | 도착 | **못 찾음** | **404** |
| ③ `moving` + `target_poi_id IS NULL` | 도착 | **못 찾음** | **404** |

②와 ③은 화면엔 보이는데 API 는 못 찾는다. 이게 버그의 전부다.

## 4. 어느 타이밍에 터지나

경유지 순회 루프 `dispatch_service.py:550~582` 를 따라가면 정확히 보인다.

```python
_set_target_poi(session_id, next_id)      # 557  target=J4
_set_db_status(session_id, "moving")      # 560  이동 시작
ok = _move_to_poi(worker, poi)            # 561  실제 주행
_set_current_poi(session_id, next_id)     # 564  current=J4, target=NULL  ← ③ 진입
...
_set_db_status(session_id, "awaiting_confirm")   # 576                    ← ② 진입
worker.confirm_event.wait()               # 581  로봇 태블릿 [확인] 무한 대기
```

564행 `_set_current_poi()` 는 **`target_poi_id` 도 같이 비운다** (1076행 주석에 명시).
그래서 J4 에 닿는 순간부터 ③ → ② 로 이어지고, 이 구간 내내 J4 벽 태블릿은
버튼을 띄우지만 전부 404 다.

**이 구간은 사람이 로봇 태블릿에서 [확인] 을 누를 때까지 무한정 지속된다** (581행 `wait()`).
몇 초짜리 레이스 컨디션이 아니라, 사람이 올 때까지 계속 열려 있는 상태다.

`awaiting_next` 로 돌아오는 것은 경유지를 **전부** 돈 뒤 루프 맨 위 535행이다.
즉 **경유지 경로를 등록한 순간부터 마지막 경유지에 도착할 때까지,
모든 중간 지점의 벽 태블릿이 먹통**이다.

### 실제 발생 흐름 (2026-08-18)

```
J3 도착            status=awaiting_next          → J3 벽 태블릿 정상 동작 ✓
경유지 [J4, J3] 등록
J4 로 이동 중       status=moving, target=J4      → J4 는 "calling" 표시
J4 도착            status=moving, target=NULL    ← ③  버튼 뜸, 404
                   status=awaiting_confirm       ← ②  버튼 뜸, 404   ★ 여기서 종료 누름
```

당시 DB 세션:

```
id=102  robot=12  status='awaiting_confirm'  first=J2(998)  cur=J4(1000)  tgt=None
```

## 5. 영향 범위

- **종료 버튼만의 문제가 아니다.** 같은 화면의 다음 위치 선택 버튼도 전부 404.
- **중앙 관제 콘솔도 영향받는다.** 콘솔은 `poi/{id}/end` 와 `poi/{id}/route` 를 쓰므로
  같은 구간에서 콘솔의 종료·경로등록도 404. 다만 콘솔에는 `robot/{id}/confirm` 이
  따로 있어 확인은 눌러줄 수 있다.
- **로봇 부착 태블릿은 영향 없다.** `robot/{id}/end` → `send_end(robot_id)` 는
  POI 가 아니라 로봇 ID 로 워커를 직접 찾기 때문이다.

---

## 6. 위험도 평가 — 낮음

`send_end()` 는 `end_flag` 와 `confirm_event` 를 둘 다 세워서 어떤 대기 상태든 깨운다
(`dispatch_service.py:904~914`).

즉 **종료 경로 자체는 멀쩡하고, 위치 태블릿이 그 경로에 도달하지 못하는 것뿐**이다.
로봇이 이상하게 움직이거나 데이터가 깨지는 종류의 버그가 아니다.
404 로 깔끔하게 거부되고 아무 일도 일어나지 않는다.

## 7. 현재 우회 방법

로봇에 붙은 태블릿의 **[작업 종료]** 를 누른다.

```
http://192.168.30.17:8002/api/dispatch/robot-tablet/12
```

이건 위치 태블릿과 다른 경로(`/robot/{id}/end`)를 타서 `awaiting_confirm` 에서도
정상 동작한다. 랙 반납 후 충전소로 복귀한다.

### 원래 설계 의도대로의 정상 흐름

```
J3 벽 태블릿에서 호출  →  로봇이 랙 들고 J3 도착 (awaiting_next)
   ↓  J3 벽 태블릿 or 콘솔에서 경유지 [J4, J3] 등록
로봇이 J4 도착 (awaiting_confirm)
   ↓  ★ 로봇에 붙은 태블릿에서 [확인]   ← 벽 태블릿을 쓰는 구간이 아님
로봇이 J3 도착 (awaiting_confirm, 마지막)
   ↓  ★ 로봇 태블릿에서 [확인 — 작업 종료]
랙 반납 → 충전소 복귀 → completed
```

경유지 이동이 시작되면 **주도권이 벽 태블릿에서 로봇 태블릿으로 넘어간다.**

## 9. 수정안 3가지

### A. 종료만 살리기 — 추천

- `/poi/{id}/end` 가 `awaiting_confirm` · `moving`+target NULL 도 받게 하고
  `send_end(session.robot_id)` 호출
- 화면에서는 다음 위치 그리드를 감추고 "로봇 태블릿에서 [확인] 대기 중" 안내로 대체

→ "여기서 그만" 은 어디서든 가능해야 하고, 진행 중인 경로와 충돌하지 않는다.

```
[J4 위치 태블릿 — 확인 대기 중]

  로봇12 · J4 도착 · 렉 운반 중        99%

  ┌────────────────────────────────┐
  │  로봇 태블릿에서 [확인] 대기 중  │
  │  남은 경유지: J3                │
  └────────────────────────────────┘

  [ 작업 종료 (랙 반납 + 충전소 복귀) ]  ← 동작함
```

### B. 버튼 전부 숨기기

- `_poi_status()` 에서 ②③ 을 `arrived` 가 아닌 별도 상태로 내보내고 태블릿은 안내만 표시
- 백엔드 로직 변경 없이 화면만 손봄
- 단점: 벽 태블릿에서 종료가 영영 안 된다

### C. 이동까지 허용

- `get_session_at_poi()` 자체를 ②③ 도 받게 확장
- 유연하지만 진행 중인 경유지 경로를 벽 태블릿에서 덮어쓰게 되어
  남은 경유지와 꼬일 위험이 있다. 별도 검토 필요.
