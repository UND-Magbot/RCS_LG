## 1. 전체 구성 — 4개의 덩어리

일반 웹 시스템은 프론트/백엔드/DB 3개인데, RCS_LG는 **로봇**이 하나 더 붙어 4개다.

```
 ①               ②                    ③              ④
사람이         두뇌                 기억창고         손발
보는 화면  ←→  판단·명령      ←→    저장           ←→  실제 움직임
─────────      ─────────           ────────         ─────────
Next.js        FastAPI             MariaDB          longjack 로봇
:3002          :8002               :3306            :8090
(브라우저)     (파이썬 서버)        (DB 서버)        (AutoXing 펌웨어)
```

```
[사람이 만지는 것]                [서버]                        [로봇]
┌────────────────────┐
│ 배차 콘솔 (1대)     │──HTTP/3초폴링──┐
│ /api/dispatch/console│              │
└────────────────────┘              │
┌────────────────────┐              │      ┌──────────────────┐   HTTP :8090   ┌────────────┐
│ 로봇부착 태블릿     │──HTTP/3초폴링─┼─────▶│  RCS 백엔드       │───REST────────▶│  longjack  │
│ /robot-tablet/{id} │              │      │  FastAPI :8002    │◀──상태 폴링────│  (AutoXing)│
└────────────────────┘              │      │                  │                │            │
┌────────────────────┐              │      │  워커 스레드      │◀═ WebSocket ══▶│  py_axbot  │
│ 관제 Next.js :3002 │──HTTP/2~5초──┘      │  (로봇당 1개)     │  /ws/v2/topics └────────────┘
│ /monitoring        │◀══ WS 릴레이 ═══════│                  │
└────────────────────┘  (로봇 실시간 위치)  └────────┬─────────┘
                                                    │ SQLAlchemy
                                              ┌─────▼──────┐
                                              │  MariaDB   │
                                              │ rcs_lg_db  │
                                              └────────────┘
```

**핵심 원칙 3가지**

1. **UI는 로봇에 직접 명령하지 않는다.** 콘솔/태블릿은 오직 백엔드 REST만 호출한다.
   로봇 IP를 아는 건 백엔드뿐. (예외: 관제의 로봇 실시간 위치는 백엔드가 WebSocket을 *중계*)
2. **UI는 명령만 하고 결과는 폴링으로 본다.** 버튼을 누르면 백엔드는 "접수했다"만 즉시 응답하고,
   실제 로봇 움직임은 백그라운드 스레드가 처리한다.
3. **작업의 진짜 주인은 워커 스레드다.** DB는 "지금 어디까지 왔나"를 기록하는 장부일 뿐,
   실제 순서 제어는 메모리 위의 스레드가 한다.

## 2. 각 계층이 하는 일

### ① 프론트엔드 (Next.js, 포트 3002) — "보여주기와 입력받기"

**하는 일**

| 역할 | 구체적으로 |
|---|---|
| 화면 렌더링 | 3D 모니터링(Three.js), 맵 편집기, 로봇 목록, 로그 |
| 사용자 입력 수집 | 버튼 클릭, POI 편집, 원격 조종 방향키 |
| 백엔드에 요청 | `fetch()` 로 HTTP 요청 전송 |
| 받은 JSON을 화면에 그리기 | 배터리 %, 로봇 위치 점, 상태 뱃지 |
| 주기적 갱신(폴링) | `setInterval` 로 2~10초마다 재요청 |

**절대 안 하는 일**

- DB에 직접 접속 (브라우저는 MariaDB 프로토콜을 말할 수 없고, 해서도 안 됨 — DB 비번 노출)
- 로봇에 직접 명령 (로봇 IP는 사설망/LTE라 브라우저에서 닿지 않음)
- "이 로봇을 보낼까 말까" 판단 (전부 백엔드가 결정)

> **왜 프론트가 DB에 직접 못 붙나?**
> 프론트 코드는 사용자 브라우저에서 실행된다 = 누구나 열어볼 수 있다.
> 거기 DB 비밀번호를 넣으면 그 순간 DB가 공개된다. 그래서 접속 정보는 서버에만 두고
> 프론트는 백엔드에 "부탁"하는 구조가 된다. 이것이 3계층 구조의 존재 이유.

### ② 백엔드 (FastAPI, 포트 8002) — "모든 판단과 중계"

RCS_LG에서 제일 뚱뚱하다. 완전히 다른 4가지 역할을 겸한다.

**(a) API 서버** — 프론트 요청을 받아 JSON 응답

**(b) 비즈니스 로직(판단)** — 진짜 핵심
- 어느 로봇을 보낼지 결정 (배터리 순 + 온라인 + 같은 층)
- 그 POI가 점유 중인지 검증
- 잭을 올릴지, 충전소로 갈지

**(c) 로봇 컨트롤러** — 백그라운드 스레드로 로봇 조종
> 일반 웹서버는 "요청 받으면 응답하고 끝"인데, RCS는 요청이 끝난 뒤에도 계속 도는 스레드가 있다.
> 로봇 1대당 워커 스레드 1개가 붙어 몇 분~몇십 분씩 산다.

**(d) 웹서버 겸 프론트엔드** — 태블릿/콘솔 HTML을 직접 서빙
```python
return HTMLResponse(content=_CONSOLE_TEMPLATE.read_text(encoding="utf-8"))
```
콘솔과 로봇 태블릿은 Next.js가 아니라 **백엔드가 HTML 파일을 통째로 내려준다.**
(`BackEnd/app/routers/dispatch.py` console_page)

### ③ DB (MariaDB, 포트 3306) — "기억만 담당"

데이터를 표(테이블)로 저장하고, 조건에 맞는 행을 돌려주는 것. 그게 전부. 판단하지 않는다.

| 테이블 | 저장하는 것 | 성격 |
|---|---|---|
| `robots` | 로봇 IP, 이름, 충전소/대기장소 POI, 최대속도 | 설정 |
| `robot_status` | 배터리 %, 상태 | 현재값 |
| `map_pois` | POI 이름, world_x/y, 각도, 타입, rack_size | 설정 |
| `robot_maps` | 맵 메타정보, area 소속 | 설정 |
| **`dispatch_sessions`** | **작업 1건의 상태 머신** | 진행중 상태 ★ |
| **`dispatch_waypoints`** | **경유지 순서와 진행 여부** | 진행중 상태 ★ |
| **`dispatch_reservations`** | **호출 대기표(FIFO)** | 진행중 상태 ★ |
| `tablet_slots` | 태블릿 슬롯번호 → POI 매핑 | 설정 |
| `activity_logs`, `alarm_logs` | 이력 | 기록 |

> **DB가 왜 필요한가 — 메모리에 두면 안 되나?**
> 백엔드가 재시작되면(배포/크래시/재부팅) 메모리는 전부 날아간다. 그러면
> "3번 로봇이 랙 들고 B구역에 서 있다"를 아무도 모른다. DB에 써두면
> 재시작 후 `recover_on_startup()` 이 읽어서 복구할 수 있다.
> 반대로 **워커 스레드는 DB에 저장할 수 없다**(스레드는 메모리에만 존재).
> 그래서 재시작 시 상태를 `awaiting_next` 로 되돌리고 사람이 다시 지시하게 만든다.
> **"DB=장부, 스레드=일꾼"**

### ④ 로봇 (longjack, AutoXing 펌웨어, 포트 8090)

자기 안에 웹서버(`py_axbot`)를 돌린다. 한 번에 하나의 이동 명령만 이해하는 단순 실행기.
전체 계획은 모른다.

## 3. 통신 ① 프론트 ↔ 백엔드 — HTTP/REST

### 3-1. HTTP란

브라우저와 서버가 대화하는 표준 규약. **"요청 1번 → 응답 1번"** 하고 연결이 끊긴다.
서버는 그 다음에 뭘 먼저 말할 수 없다.

```
POST /api/dispatch/poi/12/call HTTP/1.1     ← 메서드 + 경로
Host: 192.168.0.44:8002                     ← 어느 서버
Content-Type: application/json              ← 헤더: 본문 형식
Authorization: Bearer eyJhbGci...           ← 헤더: 신분증

{"with_rack": true, "robot_type": "lifting"}  ← 본문(Body), JSON
```
```
HTTP/1.1 200 OK
Content-Type: application/json

{"ok": true, "robot_id": 3, "reserved": false}
```

### 3-2. HTTP 메서드

| 메서드 | 의미 | RCS 예시 |
|---|---|---|
| **GET** | 조회 (아무것도 안 바꿈) | `GET /api/dispatch/console/status` |
| **POST** | 생성·실행 (뭔가 일어남) | `POST /api/dispatch/poi/12/call` |
| **PATCH** | 일부 수정 | `PATCH /api/robots/5` |
| **DELETE** | 삭제 | `DELETE /api/dispatch/poi/12/reserve` |

### 3-3. HTTP 상태 코드

| 코드 | 뜻 | RCS에서 언제 |
|---|---|---|
| **200** | 성공 | 정상 |
| **400** | 요청이 잘못됨 | 경유지를 하나도 안 골랐을 때 |
| **401** | 인증 안 됨 | 토큰 만료 → 프론트가 자동 로그인 페이지로 |
| **404** | 없음 | "이 위치에 대기 중인 로봇이 없습니다" |
| **409** | **충돌** | **"다른 로봇이 점유 중인 위치입니다"** ← RCS에서 제일 자주 봄 |
| **500** | 서버 에러 | 백엔드 코드 예외 |

### 3-4. REST API란 — 정확한 정의

**API** = 프로그램이 다른 프로그램에 제공하는 **사용법 계약(메뉴판)**.
**REST** = HTTP로 API를 만들 때 쓰는 **설계 스타일(작명 규칙)**.

> 주소(URL)는 **명사(자원)** 로, 동작은 **메서드**로 표현한다.

```
❌ POST /callRobotToPoi?poi=12        (주소에 동작이 들어감)
✅ POST /api/dispatch/poi/12/call     (poi 12라는 자원에 call)
```

**중요 — 이 시스템에는 REST API가 2개 있다. 서로 완전히 별개다.**

| | API ①: RCS 백엔드 API | API ②: AutoXing 로봇 API |
|---|---|---|
| 제공자(서버) | 우리 백엔드 :8002 | 로봇 펌웨어 :8090 |
| 소비자(클라이언트) | 브라우저(프론트/콘솔/태블릿) | **우리 백엔드** |
| 누가 설계했나 | 우리 | AutoXing (우리가 못 고침) |
| 주소 예 | `/api/dispatch/poi/12/call` | `/chassis/moves` |

**브라우저는 로봇 API를 절대 호출하지 않는다.** 백엔드가 중간에서
"프론트에게는 서버, 로봇에게는 클라이언트" 두 역할을 동시에 한다.

```
브라우저 ──[API ①의 클라이언트]──▶ 백엔드 ──[API ②의 클라이언트]──▶ 로봇
             (백엔드가 서버)                    (로봇이 서버)
```

**"REST가 서버를 이해시켜주는 구조인가?"에 대한 정확한 답**

- 주소를 실제 함수에 연결해주는 것은 REST가 아니라 **라우팅(routing)** 이다.
  FastAPI의 `@router.post("/poi/{poi_id}/call")` 데코레이터가 그 일을 한다.
- REST가 없어도 서버는 주소를 이해할 수 있다(라우터에 등록만 하면 `/asdf1234` 도 동작).
- **REST는 "그 주소를 어떤 규칙으로 지을 것인가"에 대한 사람들 간의 약속**이다.
  규칙을 지키면 처음 보는 사람도 주소만 보고 뭘 하는지 짐작할 수 있다.

즉: **라우팅 = 기술적으로 이해시키는 것 / REST = 사람이 예측 가능하게 이름 짓는 것.**

### 3-5. JSON

프론트(TypeScript)와 백엔드(Python)는 다른 언어라 데이터를 그대로 못 주고받는다.
양쪽 다 읽을 수 있는 텍스트 형식으로 변환해서 보낸다.

```
Python dict ──직렬화──▶ '{"ok":true,"robot_id":3}' ──역직렬화──▶ JS object
```

### 3-6. CORS

브라우저는 보안상 "3002에서 받은 페이지가 8002에 요청하는 것"을 기본 차단한다
(Same-Origin Policy). 포트가 다르면 남의 서버 취급. 그래서 백엔드가 응답 헤더로
"얘는 허용"이라고 알려줘야 한다.

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], ...)   # main.py
```

### 3-7. JWT 인증

```
1. POST /api/auth/login {id, password}
2. 백엔드가 토큰 발급 → {"access_token":"eyJhbG...","token_type":"bearer"}
3. 프론트가 localStorage 에 저장
4. 이후 모든 요청 헤더에 첨부: Authorization: Bearer eyJhbG...
5. 401 이 오면 → 토큰 삭제 + 로그인 페이지로 이동
```
이 로직 전체가 `frontend/lib/api.ts` 의 `apiFetch` 한 함수에 모여 있다.

### 3-8. 폴링(Polling)

HTTP는 서버가 먼저 말을 못 건다. 그럼 "로봇이 도착했다"를 화면이 어떻게 아나?
→ **계속 물어본다.**

```
콘솔: "상태 어때?" → "아직 이동중"     (0초)
콘솔: "상태 어때?" → "아직 이동중"     (3초)
콘솔: "상태 어때?" → "도착! 확인대기"  (6초)  ← 여기서 화면이 바뀜
```
```javascript
pollTimer = setInterval(() => refresh(false), 3000);
```

> **폴링의 단점과 보완**: 3초 주기면 버튼을 눌러도 최대 3초간 화면이 안 바뀐다.
> 그래서 콘솔은 **낙관적 UI(optimistic UI)** 를 쓴다 — 버튼을 누르면 서버 응답을
> 기다리지 않고 화면을 먼저 바꾸고, 다음 폴링에서 진짜 값으로 교정한다.
> `send_route()` 가 상태를 동기적으로 먼저 DB에 쓰는 이유도 이것(안 그러면 화면이 되돌아감).

## 4. 통신 ② 백엔드 ↔ DB — SQL/ORM

### 4-1. 연결 문자열

```
mysql+pymysql://root:1234@192.168.0.21:3306/rcs_lg_db?charset=utf8mb4
   │       │      │   │        │          │      │
드라이버 라이브러리 계정 비번   DB서버IP   포트   DB이름
```
HTTP가 아니라 **MySQL 프로토콜**이라는 별도 TCP 통신이다.
(브라우저가 DB에 직접 못 붙는 또 다른 이유)

### 4-2. ORM이란

원래 DB와 대화하려면 SQL을 써야 한다:
```sql
SELECT * FROM map_pois WHERE id = 12 AND is_active = 1;
```
**ORM**(Object-Relational Mapping, 여기서는 SQLAlchemy)은 이걸 파이썬으로 쓰게 해준다:
```python
db.query(MapPOI).filter(MapPOI.id == 12, MapPOI.is_active == True).first()
```
SQLAlchemy가 위 SQL로 번역해 DB에 보내고, 결과를 `MapPOI` 객체로 만들어 돌려준다.

**모델(Model)** 이 번역표다 (`app/models/dispatch.py`):
```python
class DispatchSession(Base):
    __tablename__ = "dispatch_sessions"
    id = Column(Integer, primary_key=True)
    status = Column(String(20), nullable=False, default="starting")
```
= "파이썬 `DispatchSession` 클래스는 DB `dispatch_sessions` 테이블이고
   `status` 속성은 VARCHAR(20) 컬럼이다"

### 4-3. 세션과 커넥션 풀

**세션** = DB와의 대화 창구 하나. 열고 → 쓰고 → 반드시 닫아야 한다.
RCS에는 세션을 얻는 경로가 **두 가지**이고 이 구분이 중요하다.

**(1) API 요청 처리 — `Depends(get_db)`**
```python
def poi_call(poi_id: int, db: Session = Depends(get_db)):
```
FastAPI가 요청 시작 시 세션을 만들어 넣어주고, 응답 후 자동으로 닫는다. 에러 시 롤백도 해준다.

**(2) 백그라운드 워커 — `SessionLocal()` 직접**
```python
db = SessionLocal()
try:
    ...
finally:
    db.close()
```
워커 스레드는 FastAPI 요청 밖에서 도니까 자동 관리를 못 받는다.
직접 열고 `finally`에서 반드시 닫는다. 안 닫으면 커넥션 누수로 DB가 새 연결을 거부한다.

**커넥션 풀** (`database.py`)
```python
pool_size=10, max_overflow=20, pool_recycle=3600, pool_pre_ping=True
```
- `pool_size=10` 상시 10개 유지 / `max_overflow=20` 몰리면 최대 30개
- `pool_recycle=3600` 1시간 지난 연결은 폐기 (MySQL이 오래된 연결을 끊는 문제 방지)
- `pool_pre_ping=True` 쓰기 전에 살아있는지 확인

### 4-4. 트랜잭션과 commit

`commit()` 을 해야 실제로 저장된다. 안 하면 사라진다.
```python
s.status = "moving"
db.commit()        # ← 이게 있어야 진짜 저장
```
중간에 에러가 나면 `rollback()` 으로 되돌린다(절반만 저장되는 사태 방지).

## 5. 통신 ③ 백엔드 ↔ 로봇 — HTTP + WebSocket

### 5-1. 명령은 HTTP REST로 (백엔드 → 로봇)

```python
requests.post("http://192.168.0.101:8090/chassis/moves",
              json={"type":"standard","target_x":3.2,"target_y":1.5,"target_ori":0})
→ 응답: {"id": 4521}          ← 명령 접수번호(move_id)
```

**중요**: 로봇은 "갔다 왔어요"라고 알려주지 않는다. 접수번호만 주고 끝.
그래서 백엔드가 계속 물어봐야 한다 — 여기도 폴링이다.
```python
while 시간 남았으면:
    resp = GET /chassis/moves/4521
    if resp["state"] in ("succeeded","failed","cancelled"): 끝
    time.sleep(2)      # POLL_INTERVAL
```

### 5-2. 상태는 WebSocket으로 (로봇 → 백엔드)

**WebSocket** = 연결을 계속 열어두고 양방향으로 아무 때나 말할 수 있는 프로토콜.
주소가 `http://` 대신 `ws://` 로 시작한다.

```
[HTTP 폴링]  요청→응답 끊김, 요청→응답 끊김, ...   (3초마다 반복)
[WebSocket]  연결 ═══════════════════════════      (계속 열림)
                  ↑값↑   ↑값↑  ↑값↑              (서버가 알아서 밀어줌)
```

로봇은 `ws://{ip}:8090/ws/v2/topics` 에서 **토픽 구독** 방식으로 데이터를 흘려보낸다.
```python
ws.send('{"enable_topic": "/tracked_pose"}')   # "이 토픽 켜줘"
→ 이후 {"topic":"/tracked_pose","pos":[3.21,1.48],"ori":1.57} 가 계속 들어옴
```

| 토픽 | 내용 |
|---|---|
| `/tracked_pose` | 로봇 실시간 위치 (x, y, 방향) |
| `/planning_state` | 이동 상태 (moving/idle, 남은 거리) |
| `/battery_state`, `/detailed_battery_state` | 배터리 |
| `/jack_state` | 잭 상태 (jacking_up / hold / jacking_down) |
| `/detected_rack` | 랙 감지 여부 |
| `/global_positioning_state` | 위치 복구(SLAM 재측위) 결과 |

### 5-3. WebSocket 릴레이 — 프론트가 로봇 위치를 보는 법

브라우저는 로봇에 직접 못 붙는다(사설망/LTE). 그래서 백엔드가 중계한다.

```
[브라우저] ws://서버:8002/api/map/ws/{로봇IP}?topics=/tracked_pose
                │
                ▼
           [백엔드 릴레이]  (routers/map.py  ws_map_relay)
                │
                ▼
           ws://로봇IP:8090/ws/v2/topics
```

### 5-4. 통신 방식 비교표

| | HTTP/REST | WebSocket | SQL(ORM) |
|---|---|---|---|
| 누구↔누구 | 프론트↔백엔드, 백엔드↔로봇 | 브라우저↔백엔드↔로봇 | 백엔드↔DB |
| 포트 | 8002 / 8090 | 8002 / 8090 | 3306 |
| 연결 | 요청마다 끊김 | 계속 열림 | 풀에서 재사용 |
| 방향 | 클라이언트가 먼저만 | 양방향 | 백엔드가 먼저만 |
| 데이터 형식 | JSON | JSON 패킷 | 테이블 행 |
| 실시간성 | 폴링 주기만큼 지연 | 즉시 | — |

## 6. FastAPI와 Pydantic이 하는 일

### 6-1. FastAPI = 파이썬 웹 프레임워크

"파이썬 함수를 HTTP로 부를 수 있게 만들어주는 도구". 직접 하면 아주 번거로운 일들을 대신한다.

| FastAPI가 대신 해주는 일 | 없으면 직접 해야 하는 것 |
|---|---|
| **라우팅** — 주소를 함수에 연결 | URL 문자열 파싱, `if/elif` 분기 |
| **경로 변수 추출** — `/poi/{poi_id}` → `poi_id=12` | 문자열 자르기 + int 변환 |
| **본문 파싱** — JSON → 파이썬 객체 | `json.loads()` + 키 존재 확인 |
| **타입 검증** | 값마다 타입 체크 코드 |
| **응답 직렬화** — 객체 → JSON | `json.dumps()` + datetime 변환 |
| **에러 응답** — `HTTPException(409, ...)` | 상태코드/본문 수동 구성 |
| **의존성 주입** — `Depends(get_db)` | 함수마다 DB 세션 열고 닫기 |
| **문서 자동 생성** | API 명세서 수기 작성 |
| **lifespan** — 시작/종료 훅 | 별도 초기화 스크립트 |

한 줄 예:
```python
@router.post("/poi/{poi_id}/call", response_model=DispatchCallResult)
def poi_call(poi_id: int, body: DispatchCallRequest | None = None,
             db: Session = Depends(get_db)):
```
이 한 줄이 하는 일: POST 등록 + 주소에서 `poi_id` 추출 후 int 변환 +
본문 JSON을 `DispatchCallRequest` 로 변환·검증 + DB 세션 자동 주입 +
반환값을 `DispatchCallResult` 모양으로 JSON 직렬화 + 문서 등록.

**부가 기능 — 자동 API 문서**
서버가 떠 있으면 브라우저에서 바로 열린다:
```
http://서버:8002/docs      ← Swagger UI (여기서 직접 API 실행도 가능)
http://서버:8002/redoc
```
스키마 정의만으로 자동 생성되므로 문서를 따로 관리할 필요가 없다.

### 6-2. Pydantic 스키마 = 데이터 모양 정의서

`app/schemas/` 안의 클래스들. **"이 API에 들어오는/나가는 데이터는 이런 모양이다"** 를 선언한다.

```python
class DispatchCallRequest(BaseModel):
    with_rack: bool = True                    # 안 보내면 True
    robot_type: Optional[str] = None          # 없어도 됨
```

### 6-3. "자동 처리"가 뜻하는 것 — 5가지

**(1) 파싱**: JSON 문자열 → 파이썬 객체
```
'{"with_rack": false}'  →  DispatchCallRequest(with_rack=False, robot_type=None)
```
이후 `body.with_rack` 처럼 속성으로 접근. 딕셔너리 `body["with_rack"]` 가 아니라
**오타 나면 에디터가 잡아준다.**

**(2) 타입 검증 + 자동 변환**
```
{"with_rack": "true"}  → 문자열이지만 bool True 로 변환 (관대한 변환)
{"with_rack": "예"}    → 변환 불가 → 자동 422 에러 응답
```

**(3) 기본값 채우기**
```
{}  →  DispatchCallRequest(with_rack=True, robot_type=None)
```
"안 보냈을 때 뭘로 칠 것인가"를 API 함수 안에 쓸 필요가 없다.

**(4) 응답 직렬화** — `response_model` 이 붙으면
- 파이썬 객체 → JSON 자동 변환 (datetime → ISO 문자열 등)
- **스키마에 없는 필드는 응답에서 잘라낸다** → 실수로 비밀번호 같은 게 새는 걸 방지
- SQLAlchemy 모델을 바로 넘겨도 됨 (`from_attributes = True` 설정 시)

**(5) 검증 실패 시 자동 에러 응답**
```json
{"detail":[{"loc":["body","with_rack"],"msg":"value could not be parsed to a boolean"}]}
```
422 응답이 자동으로 나간다. 검증 코드를 한 줄도 안 써도 된다.

### 6-4. 세 종류의 "모델"을 헷갈리지 말 것

RCS에는 이름이 비슷한 클래스가 3종류 있고 역할이 다르다.

| 종류 | 위치 | 정체 | 예 |
|---|---|---|---|
| **SQLAlchemy 모델** | `app/models/` | **DB 테이블** 구조 | `DispatchSession` |
| **Pydantic 스키마** | `app/schemas/` | **API 입출력** 형식 | `DispatchSessionOut` |
| TypeScript 타입 | `frontend/lib/types/` | **프론트**가 받을 형태 | `interface DispatchSession` |

같은 데이터를 3번 정의하는 셈인데, 일부러 나눈 것이다:

- DB에는 있지만 API로는 안 내보내는 값이 있다 (내부 컬럼, 비밀번호 해시)
- API로는 내보내지만 DB에는 없는 값이 있다 — 예: `DispatchSessionOut.robot_name`,
  `current_poi_name` 은 테이블 컬럼이 아니라 **조인해서 만들어낸 값**
- DB 구조를 바꿔도 API 응답 형태는 유지할 수 있다 (프론트가 안 깨짐)

흐름으로 보면:
```
DB 행 ──(SQLAlchemy 모델)──▶ 파이썬 객체 ──(Pydantic 스키마)──▶ JSON ──▶ 프론트(TS 타입)
```

## 7. 백엔드 내부 3층 구조

`app/` 안이 역할별로 갈려 있다.

| 폴더 | 역할 | 규칙 |
|---|---|---|
| `routers/` | HTTP 접수·검증·응답 | 주소/상태코드만 다룸 |
| `services/` | **판단과 순서 제어** | 여기가 두뇌 (dispatch_service, jack_service…) |
| `crud/` | DB 읽기/쓰기 | SQL(ORM) 쿼리만 |
| `models/` | 테이블 정의 | |
| `schemas/` | API 입출력 정의 | |
| `constants/` | 고정값 (rack_specs, robot_types) | |
| `robot_api/`, `autoxing_api/` | 로봇 REST/WS 호출 래퍼 | |
| `templates/` | 콘솔·태블릿 HTML | |

호출 방향은 한 방향이다:
```
routers → services → crud → DB
              ↓
        robot_api → 로봇
```
`crud` 는 절대 `services` 를 부르지 않는다. 이렇게 해야 순환 참조가 안 생기고
"어디를 고쳐야 하나"가 명확해진다.

## 8. 용어 사전

### 8-1. 위치/맵

| 용어 | 뜻 |
|---|---|
| **POI** (Point Of Interest) | 맵 위의 이름 있는 지점. `map_pois` 테이블. `world_x/y`(미터), `angle`(라디안) |
| **poi_type** | `jack`(작업 위치=콘솔 타일), `standby`(랙 보관/대기), `charging`(충전소), `general` |
| **area / business** | 층(영역) / 사업장. 호출 시 같은 층 로봇 우선 배정 |
| **overlay** | 로봇 내부 맵에 얹는 도형 레이어(JSON). POI·충전소·가상벽이 전부 여기 |
| **Shelves Point** | overlay의 `type="34"`, `subtype="rack"` 지점. **없으면 `align_with_rack` 자체가 안 됨** |
| **grid_origin** | 맵 이미지(픽셀)↔실세계(미터) 원점. 틀어지면 POI 좌표가 전부 어긋남 |

### 8-2. 로봇 명령 (AutoXing)

이동은 전부 `POST /chassis/moves` 로 들어가고 **`type` 으로 성격이 갈린다.**

| move type | 뜻 | 언제 |
|---|---|---|
| **standard** | 일반 자율주행 | 경유지 이동, 대기장소 복귀 |
| **align_with_rack** | 랙 정렬 진입 (라이다로 다리 찾아 밑으로) | 픽업 1회 |
| **to_unload_point** | 랙 내려놓는 지점 진입 | 강제복귀 경로 |
| **charge** | 충전 도킹 | 종료 마지막 |

| 서비스 명령 | 뜻 |
|---|---|
| **jack_up** `/services/jack_up` | 잭 올려 랙을 들어올림. 이후 풋프린트가 랙 크기로 확장 |
| **jack_down** | 잭 내려 랙 내려놓음 |
| **relocalize** | "너 지금 여기 있어"라고 좌표 강제 주입 (`POST /chassis/pose`) |

> **잭(jack)이란**: longjack 상판의 승강 리프트. 랙 밑으로 들어가 **밑에서 들어올려**
> 통째로 운반. 지게차처럼 앞에서 찌르는 게 아니라 받쳐 드는 구조라
> 랙 다리 4개 사이에 정확히 들어가야 한다. 그래서 `align_with_rack` 이 필요.

### 8-3. rack.specs (LG에서 제일 말썽인 부분)

`app/constants/rack_specs.py`. 펌웨어는 `align_with_rack` 시
**라이다로 잰 다리 간격**과 등록된 spec을 비교해 매칭한다.

| 필드 | 뜻 | 함정 |
|---|---|---|
| `width`/`depth` | 랙 다리 **중심 간 거리**(m) | **도면 치수가 아님.** 라이다 측정값(detected)을 넣어야 함 |
| `leg_size`/`foot_radius` | 다리 굵기 기준 | 크게 잡으면 **옆 캐스터를 다리로 오인식** |
| `margin[4]` | 랙 풋프린트(장애물 제외 영역) | 캐스터가 튀어나오면 margin을 키워 랙 일부로 포함 |
| `alignment` | 정렬 기준 (center) | |

등록된 4종: `S300`, `S600`, `LG`(0.70×0.50), `LG2`(0.64×0.545).

> spec을 여러 개 등록하면 펌웨어가 엉뚱한 spec과 매칭을 시도해 실패한다.
> 그래서 `build_rack_specs_for_map()` 이 **그 맵의 POI들이 실제 쓰는 rack_size만큼만**
> 골라 로봇에 보낸다.

### 8-4. 배차(dispatch)

| 용어 | 뜻 |
|---|---|
| **dispatch_session** | 로봇 1대의 작업 1건. 시작~종료 생명주기를 DB에 기록 |
| **워커(worker)** | 세션을 실제로 굴리는 **파이썬 스레드**. 로봇당 1개. 메모리에만 존재 |
| **waypoint(경유지)** | 콘솔이 등록한 방문 순서. `seq` + `status`(pending/current/done) |
| **occupied(점유)** | 다른 로봇이 가 있거나·가는 중이거나·경유지로 찜한 POI. 호출 불가 |
| **reservation(예약)** | 가용 로봇 0대일 때 만들어지는 대기표. FIFO. 로봇이 놀면 자동 호출 |
| **with_rack** | true=랙 픽업해서 작업 / false=랙 없이 이동 |
| **use_jack** | 로봇 타입이 `serving`이면 false → 잭 동작 전부 생략 |
| **force_clear** | 로봇을 **움직이지 않고** 세션만 삭제. 잭·위치 그대로 |

### 8-5. 인프라/네트워크 (LG 현장 특성)

| 용어 | 뜻 | LG에서 왜 중요한가 |
|---|---|---|
| **LTE (M2M)** | LG U+ 전용 APN 사물인터넷 회선 | 로봇이 WiFi가 아닌 LTE → 왕복 지연 수백ms~1초+ |
| **CGNAT** | 통신사가 사설IP를 여러 가입자에 배분 | 로봇 직접 접속 불가 → 포트포워딩(8090) 필요 |
| **유동 IP** | 라우터 재부팅마다 WAN IP 변경 | 미해결 리스크. 고정IP/DDNS 필요 |
| **TTL 캐시** | 조회 결과를 N초 재사용 | 온라인 체크가 로봇당 수 초 → 15초 캐시로 방어 |

## 9. 운영 루틴

### 루틴 ① 호출 (Call)

```
[콘솔] POI 타일 클릭
   │  POST /api/dispatch/poi/{poi_id}/call   body {robot_type, with_rack}
   ▼
[백엔드] call_to_poi()
   │ 0. _try_claim_poi() → 같은 POI를 처리 중인 다른 요청이 있으면 거부  ★2026-08-11 추가
   │ 1. occupied_poi_ids() → 이미 점유된 자리면 409 거부
   │ 2. find_available_robot()
   │      조건: is_active + IP있음 + 같은 area + 활성워커 없음 + 배터리 ≥ min_battery
   │      정렬: 배터리 내림차순 → robot_id 오름차순
   │      마지막 관문: online_ips_cached() 실제 온라인 확인 (15초 TTL)
   │ 3-a. 로봇 있음 → start_session() → 워커 스레드 기동, 세션 생성(starting)
   │ 3-b. 로봇 없음 → dispatch_reservations 에 예약 생성 → "reserved"
   ▼
[콘솔] 3초 뒤 폴링에서 타일이 calling / reserved 로 변경
```

**설계 포인트 3개**

- **원자적 슬롯 예약**: "가용 확인"과 "배정" 사이에 다른 요청이 끼어들면 로봇 1대에 작업 2개가
  붙는다(TOCTOU). 그래서 락 안에서 `thread=None` 워커를 먼저 등록해 자리를 찜하고
  그 다음 DB 세션을 만든다.
- **POI 선점** (`_claimed_pois`, 2026-08-11 추가): 위는 **로봇** 쪽 방어일 뿐이라, 같은 POI를 동시에
  호출하면 서로 다른 로봇이 같은 자리로 배정됐다(모의 테스트에서 3~4대 재현). 그래서 POI 도 같은 방식으로
  선점한다. **잠금 안에서는 메모리 집합만 만지고 DB·네트워크는 부르지 않는다** — 온라인 체크(아래)가
  잠금 안에 들어가면 콘솔 전체가 수 초씩 멈추기 때문.
- **온라인 체크 캐시**: 로봇 하나 확인에 REST 3초 + WS 최대 12초. 콘솔이 3초마다 폴링하는데
  매번 하면 UI가 멈춘다 → IP별 15초 TTL 캐시.

### 루틴 ② 픽업 (Pickup)

```
status=picking_up
   ├─ standby POI 조회 (로봇 standby_id 우선, 없으면 그 층 standby 타입 POI)
   ├─ safe_move(type="align_with_rack", 랙 위치)
   │     → 라이다로 랙 다리 찾아 밑으로 진입 / 실패 시 세션 failed
   ├─ jack_up()
   └─ sleep(8초)   ← JACK_SETTLE_SEC
```

> **핵심 단순화**: `align_with_rack` 1회, `jack_up` 1회, `jack_down` 1회.
> 경유지를 아무리 많이 돌아도 **잭은 계속 든 채로** 다닌다. 잭 모터 부하 최소화가 목적.

### 루틴 ③ 경유지 등록 + 출발 (Route)

```
[콘솔] 경유지 A→B→C 지정 후 [출발]
   │  POST /api/dispatch/poi/{poi_id}/route  body {waypoints:[A,B,C]}
   ▼
[라우터] 출발지 자신 제외 + 중복 제거 + 점유 경유지 섞였으면 409
   ▼
[서비스] send_route()
   │ - POI 유효성 추림 (중복 제거) ← 잠금 밖
   │ ┌─ _route_lock(robot_id) ─────────────────────────┐  ★2026-08-11 추가
   │ │ - 상태가 awaiting_next 인지 확인 (아니면 거부)   │
   │ │ - dispatch_waypoints 에 seq 0,1,2 저장           │
   │ │ - ★ status를 "moving"으로 **동기적으로 먼저** 변경│
   │ │ - worker.pending_route = [A,B,C]                 │
   │ │ - worker.next_event.set()   ← 자고 있던 워커를 깨움│
   │ └──────────────────────────────────────────────────┘
   ▼
[워커] wait() 에서 깨어나 경유지 루프 진입
```

> **왜 잠금으로 묶었나** (2026-08-11): 경로는 **DB(태블릿이 읽음)** 와 **`pending_route`(워커가 읽음)**
> 두 곳에 쓰인다. 이 구간이 갈라져 있으면 [출발]이 겹칠 때 여러 건이 모두 수락되어
> **한쪽이 DB를 덮어쓴 뒤 워커는 다른 경로를 집어가** 태블릿 표시와 실제 이동이 어긋난다(15회 중 3회 재현).
> 먼저 들어온 요청이 잠금 안에서 status 를 moving 으로 바꾸므로 뒤따라온 요청은 거부된다.

### 루틴 ④ 경유지 순회 + 확인 (Confirm) — LG 운영의 본체

```
for 각 경유지:
   ├─ status=moving, waypoint[i]=current
   ├─ safe_move(type="standard", 경유지 좌표)   ← 잭 든 채로 이동
   ├─ 도착 → current_poi_id 갱신
   ├─ ★ worker.confirm_event.clear()           ← 묵은 확인 신호 폐기
   ├─ status=awaiting_confirm
   └─ worker.confirm_event.wait()              ← 사람이 [확인] 누를 때까지 대기
             ▲
             │ POST /api/dispatch/robot/{robot_id}/confirm
        [로봇 부착 태블릿] 작업자가 화물 처리 후 [확인]
        (콘솔에서 대행 확인도 가능)
```
마지막 경유지에서 [확인] → 루프 종료 → 자동으로 종료 시퀀스.

> **`clear()` 를 왜 먼저 하나**: 작업자가 연타하거나 통신 재시도로 확인이 두 번 오면
> 이벤트가 켜진 채 남는다. 그러면 **다음 지점 도착 시 사람 확인 없이 그대로 출발**한다.
> 그래서 대기 직전에 반드시 비운다. `next_event` 도 같은 이유.

### 루틴 ⑤ 종료/복귀 (Return & Park)

```
status=returning   (이후 next/confirm 명령은 전부 무시)
   ├─ [리프팅+랙 있음] standby로 standard 이동 → jack_down (랙 반납)
   ├─ [리프팅+랙 없음] 그 자리에서 jack_down → standby 생략
   ├─ [서빙 로봇]      잭·standby 전부 생략
   ├─ 충전소 사전 접근 : "{충전소이름}-1" POI 로 standard 이동
   │                     (없으면 충전소 좌표 사용, 실패해도 진행)
   ├─ 2초 대기
   └─ 충전소 도킹     : type="charge", charge_retry_count=5
status=completed
```

> **왜 2단계 도킹인가**: 곧장 `charge` 를 주면 진입 각도가 안 맞아 실패하는 경우가 있어
> 충전소 앞 지정 지점(`-1` 접미사 POI)까지 일반 이동 후 도킹.

### 루틴 ⑥ 예약 대기열 + 이어받기 (LG 고유)

```
[예약 생성] dispatch_reservations (status=waiting, FIFO)
      ├─(A) 어떤 워커가 종료 → finally 에서 try_fulfill_reservations()
      │       → 먼저 예약한 순서대로 자동 호출
      └─(B) ★ 이어받기 — 경유지를 다 돌고 종료하려는 순간
              _take_next_reservation_if_continuable()
                조건: 종료명령 없음 + 배터리 ≥ min_battery + 점유 안 된 예약 존재
                만족 → **충전소도 안 가고 랙도 안 내려놓고** 바로 그 예약 위치로
```
매번 충전소를 왕복하면 사이클 타임이 길어지므로, 배터리가 충분하면 랙을 든 채
다음 일감을 바로 받는다. 이동 실패 시 예약을 `waiting` 으로 되돌려 다른 로봇이 가져가게 한다.

### 루틴 ⑦ 강제 종료 (force_clear)

```
POST /api/robots/remote/clear-dispatch/{ip}
   → abort_flag, end_flag = True, 두 이벤트 set
   → 워커가 깨어나 **복귀 시퀀스를 건너뛰고** 세션만 failed 마감
   → 로봇은 물리적으로 그 자리 그대로 (잭도 든 상태)
```
충전소로 보내려면 원격제어 [충전소 복귀]를 따로 눌러야 한다.

## 10. 상태 머신

`dispatch_sessions.status` 한 컬럼이 전체 흐름을 표현한다.

| 상태 | 뜻 | 다음으로 가는 트리거 |
|---|---|---|
| `starting` | 세션 생성 직후 | 워커 기동 |
| `picking_up` | standby에서 랙 정렬 + 잭업 중 | 잭업 완료 |

| `returning` | 복귀 시퀀스 중 | — (이후 모든 명령 무시) |
| `completed` / `failed` | 종료 | — |

```
starting → picking_up → moving → awaiting_next ──[출발]──┐
                                       ▲                 │

                                       │            └────┬────┘
                                       │                 │도착
                                       │         ┌───────▼────────┐
                                       └─────────│awaiting_confirm│
                                        (경유지    └───────┬────────┘
                                         전부       [확인] │ 마지막이면
                                         소진)      ┌──────▼──────┐
                                                    │  returning  │→ completed
                                                    └─────────────┘
```

2. `/device/info` 는 상세정보용으로 **타임아웃 3초만** 시도, 실패해도 온라인 판정에 영향 없음

## 12. 백그라운드 상시 루틴

| 루틴 | 주기 | 하는 일 |
|---|---|---|
| **boot_recovery** | 10초 | 로봇이 **오프라인→온라인**(=재부팅 완료)이면 ①current-map 설정 ②충전소 기준 위치재조정. 작업 중 로봇 제외 |

| **deadlock_monitor** | — | **비활성화됨** ("좁은 통로 없는 사이트" 사유로 main.py 주석 처리) |

### boot_recovery의 전제 — 꼭 기억할 것

> **"유휴 로봇 = 충전소에 도킹된 상태"** 라고 가정한다.

재부팅 감지 시 충전소 POI 기준으로 위치를 강제 주입한다. 충전소 POI에서 yaw 방향으로
`DOCKING_OFFSET`(0.3, CLAUDE.md 기재값) 앞선 지점, 헤딩은 POI 방향 그대로(180° 안 뒤집음).
따라서 **로봇이 충전소가 아닌 곳에 세워진 채 재부팅되면 완전히 틀린 위치가 주입된다.**

| 관제 로봇 위치 | **WS** `/api/map/ws/{ip}?topics=/tracked_pose` | 실시간 |
| 로봇 관리 페이지 | `GET /api/robots/live` | 10초 |
| 원격 조종(방향키) | `POST /api/robots/remote/twist/{ip}` | 누르는 동안 300ms |
| 백엔드 → 로봇 이동상태 | `GET /chassis/moves/{id}` | 2초 |
| boot_recovery | 온라인 점검 | 10초 |

`console/status` 응답 하나에 들어있는 것: POI 타일 상태 전체 + 우측 로봇 사이드바
(온라인/배터리/현재위치) + 점유 목록 + 미래 경유지 예약 배지 + 가용 로봇 수(타입별).
N+1 쿼리를 피하려고 한 번에 몰아 조회한다.

### VESA에서 고쳤으나 LG 코드에 그대로 남아있는 것 (코드 확인 완료)

| # | 내용 | 증상 |
|---|---|---|

| B | 충전독 도킹 중 맵핑 시 가드 없음 | 조용히 실패 |
| C | 빈 `/map` 토픽이 5cm 폴백을 영구 차단 | |

### 코드에서 추가로 확인한 것

- **deadlock_monitor 비활성** — 통로 교착 시 자동 양보 없음.
  zone_guard 60초 대기 + safe_move 재시도로만 버팀.
- **`awaiting_confirm` 에 타임아웃 없음** — `confirm_event.wait()` 에 timeout 인자가 없어
  사람이 안 누르면 무한 대기. (레거시 `wait_for_confirm` 은 30분 상한이 있지만
  배차 워커의 확인 대기는 상한 없음)

### 현장 리스크

- **LTE 유동 IP** — 라우터 재부팅마다 WAN IP 변경. 고정IP/DDNS 필수. (매핑 등 대용량은 WiFi 권장)
- **LG2 뒷다리 검출 편차** — 캐스터 간섭으로 depth ±수 cm. rack.specs 중앙값으로 완화하나
  근본 해결은 물리(캐스터 정리)
- **NEXT_PUBLIC_API_URL 은 빌드 시점에 코드에 박힌다** — 서버 IP가 바뀌면 프론트를
  `--no-cache` 로 재빌드해야 함. 환경변수만 바꿔서는 안 바뀜

## 부록: 왜 이렇게 나눴는지

| 분리 | 이유 |
|---|---|
| 프론트/백엔드 | DB 비번·로봇 IP를 사용자에게 노출하지 않기 위해. 화면이 3종류(관제/콘솔/태블릿)인데 **로직은 한 벌만** 유지하면 됨 |
| 백엔드/DB | 백엔드가 죽어도 데이터는 남음. 재시작 후 복구 가능 |
| 백엔드/로봇 | 로봇 펌웨어는 우리가 못 고침. 로봇은 "한 번에 한 명령"만 아는 단순 실행기로 두고 순서·판단은 백엔드가 짐 |
| 워커 스레드 분리 | 작업이 몇십 분 걸리는데 HTTP 요청을 붙잡고 있을 수 없음. 요청은 바로 응답하고 실제 일은 뒤에서 |

## 부록: 배포 시 위치

```yaml
backend:  ports "8002:8002"   ← Docker 컨테이너
frontend: ports "3002:3002"   ← Docker 컨테이너 (depends_on backend healthy)
DB:       192.168.0.21:3306   ← 컨테이너 아님, 별도 서버
로봇:      LTE 포트포워딩 8090  ← 현장
```

`.env` 값이 계층 간 연결선이다:
```
DB_HOST / DB_NAME       → 백엔드가 어느 DB를 볼지
NEXT_PUBLIC_API_URL     → 프론트가 어느 백엔드를 볼지 (빌드 시점 고정)
robots.ip_address (DB)  → 백엔드가 어느 로봇을 볼지
```
