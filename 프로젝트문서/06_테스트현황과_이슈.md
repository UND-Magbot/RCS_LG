#### U-1. 재시작 복구 후 원래 목적지로 마저 갈 수단 없음

- 이동 중 서버가 재시작되면 복구 로직이 로봇을 세우고 "그 자리에 도착"으로 기록한다.
  판정 반경이 1.5m(`RECOVER_POSE_MATCH_M`)라 **목적지까지 덜 간 상태인데 도착으로 뜰 수 있다.**
- 그런데 콘솔의 경유지 후보에서 **현재 POI 가 제외**되어 같은 곳으로 다시 보낼 수 없다.
  `dispatch_console.html` — `candidates = data.pois.filter(t => t.poi_id !== routeFromPoi && ...)`
- 백엔드 `send_route` 는 같은 POI 를 경유지로 받아준다(확인함). **콘솔에 버튼 하나만 추가하면 해결**:
  도착 타일에 `[여기로 다시 이동]` → `POST /api/dispatch/poi/{id}/route {"waypoints":[같은 id]}`
- 경유지 후보 필터를 푸는 방법도 있으나, 정상 상황에서 실수로 제자리 이동을 등록할 수 있어 **별도 버튼**이 낫다.

#### U-2. 도착 화면이 왜 달라지는지 안 드러남 ⭐ 사용자가 가장 헷갈려한 지점

같은 "도착"인데 **거기까지 간 방법**에 따라 화면이 달라진다. 규칙은 일관되지만 화면에 안 보인다.

| 어떻게 갔나 | 세션 상태 | 화면 | 코드 |
|---|---|---|---|
| **호출**로 감 (첫 목적지) | `awaiting_next` | 경유지 등록 / 종료 | `dispatch_service.py` L520-522 |
| **경유지**로 지정해서 감 | `awaiting_confirm` | 확인 / 종료 | 〃 L576 |
| **예약 이어받기**로 감 | `awaiting_next` | 경유지 등록 / 종료 | 〃 L615-618 |

설계 의도는 **"경로 등록 → 순회 → 종료" 가 1사이클**이고, 예약 이어받기는 새 사이클의 시작이라
다시 경로를 등록받는 것. 순회 중간에 경로를 못 바꾸는 이유는 **남은 경유지가 점유 상태로 잡혀 있어**
갈아끼우면 점유가 꼬이기 때문.

- 개선: 타일에 상태를 명시 — `"호출 도착 · 경로를 등록하세요"` / `"경유지 도착 · 확인하세요"`

#### U-3. 예약이 언제 소비되는지 예고가 없음

- 마지막 경유지에서 [확인]을 누르면 대기 예약으로 **예고 없이 이어서 출발**한다.
  운영자는 "이제 끝"이라 생각하고 눌렀는데 로봇이 다른 곳으로 간다.
- 콘솔은 예약 타일에 `"예약됨 · 로봇이 생기면 자동 호출"` 이라고만 띄운다 —
  **지금 이 로봇이 확인 누르는 순간 간다**는 사실이 어디에도 없다.
- 개선: 버튼 라벨에 다음 행선지 표시 `[확인 (다음: J3 으로 이어서 이동)]`,
  상단에 배너 `"대기 예약 1건: J3 — 현재 작업 종료 후 자동 진행"`

#### U-4. 마지막 경유지 확인 후 사람에게 선택권이 없음

- 마지막 [확인] → 대기 예약 있으면 그리로 자동 이동 / 없으면 자동 복귀. **"여기서 경로를 더 등록" 선택지가 없다.**
- 그래서 더 돌고 싶으면 미리 예약을 걸어두는 수밖에 없는데, 예약은 원래
  **"로봇이 바빠서 지금 못 오는 곳"** 을 대기열에 거는 기능이지 순회 경로를 만드는 수단이 아니다.
  (로봇이 1대라 항상 "바쁨"이 되어 예약으로 흘러가는 것뿐)
- 개선: 마지막 확인 화면에 `[확인하고 J3으로 계속]` / `[여기서 경로 추가]` / `[종료]`
- ⚠️ **이것만 워커 루프(`_worker_loop`) 수정이 필요**하므로 4건 중 가장 위험하다. 현장 안정화 후에 착수할 것.

#### 운영 우회 (수정 전까지)

순회 순서를 미리 아는 경우 **경유지를 처음에 한 번에 전부 등록**하면 된다.
그게 원래 설계 의도이고 조작도 적다(각 지점에서 [확인]만).
예약을 매번 거는 방식보다 흐름이 명확하다.

### 운영 중 발생 가능 (미대응)

- 운영 중 작업자가 잘못된 POI를 누르는 경우의 **백엔드 거부 로그/알림** 없음
- 태블릿 UI 폴링 2~3초 → 필요 시 WebSocket 전환 검토

### 2026-08-11 규명: 랙 위치에서 출발 못 하는 문제

- **증상**: 랙을 든 채 작업위치로 출발 못 함. `calculation_failed`(도로 미연결) 반복. 화면 안내 없음
- **원인**: 맵핑 당시 랙 위치(R1)에 랙이 놓여 있어 **랙 다리 4개가 지도에 영구 장애물로 기록**됨.
  로봇이 그 자리에서 출발하려 하면 **출발점이 팽창영역에 걸려** 경로 계산 실패
- **근거**: 지도 이미지 분석 결과 R1 반경 0.4m 내 비자유 셀 5개, 배치가 LG 랙 다리(폭 0.70·깊이 0.50)와 일치.
  연결성 계산 시 팽창 0 이면 전 POI 도달 가능하나 팽창 0.4m 면 **출발점 자체 차단**. 나머지 POI 6곳은 이상 없음
- **해결**: 랙을 치우고 맵 재작성 → 정상 동작
- **재발 방지**: **맵핑 시 랙·대차를 전부 치울 것** (→ [04](04_현장절차_맵핑과테스트.md) STEP 1)

### STEP 2 잔여 정리 — 하지 않기로 판정 (2026-08-11, 근거 있음)

- 콘솔 POI 목록은 `_current_area_active_pois()` 가 **메인 적용 영역 → 활성 맵 → 그 맵의 POI** 순으로만 조회.
  `/api/dispatch/console/status` 실호출 결과 **신 POI만 노출** — 구 POI 혼선 **재현되지 않음**
- `areas.is_main_floor` 중복은 **백엔드·프론트 어디에도 사용 로직이 없음**(타입 선언·응답 필드뿐) → 기능 영향 0
- ⚠️ 만약 정리한다면 **하드 삭제 금지**. `DELETE /api/map/areas/{id}` 는 docstring과 달리 실제로 하드 삭제이고,
  `dispatch_reservations.poi_id` 가 **ON DELETE CASCADE** 라 **예약 이력이 함께 소멸**함. 소프트 비활성화(`is_active=0`)로 할 것
