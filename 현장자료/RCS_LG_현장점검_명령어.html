PowerShell 의 curl 은 curl 이 아닙니다

curl 은 Invoke-WebRequest 의 별칭이라 옵션이 전혀 다릅니다. 이 문서의 curl 명령은 전부 curl.exe 로 적었습니다. 그대로 쓰세요.

MariaDB 경로는 버전마다 다릅니다

위 $MYSQL 이 없다고 나오면 실제 경로를 찾으세요.

Get-ChildItem "C:\Program Files\MariaDB*\bin\mysql.exe" | Select-Object FullName

01 — 확인 순서

아래 층이 안 되면 위층은 볼 필요가 없습니다

"온라인이 안 뜬다" 는 증상 하나에 원인이 일곱 군데 있습니다. 아래에서 위로 한 층씩 올라가면서 처음 실패하는 층이 곧 원인입니다. 순서를 건너뛰면 엉뚱한 곳을 고치게 됩니다.

02 — STEP 1 · IP 도달

내가 지금 어느 망에 붙어 있는지부터 확정합니다

1-1

내 PC 의 IP · 게이트웨이 · 어댑터

Get-NetIPAddress -AddressFamily IPv4 |
  Where-Object InterfaceAlias -notlike "*Loopback*" |
  Format-Table InterfaceAlias, IPAddress, PrefixLength, PrefixOrigin

Get-NetRoute -DestinationPrefix "0.0.0.0/0" |
  Sort-Object RouteMetric | Select-Object -First 1 InterfaceAlias, NextHop

Get-NetAdapter | Where-Object Status -eq "Up" | Format-Table Name, InterfaceDescription
통과 서버 PC IP = 192.168.39.110 · PrefixOrigin 이 Manual · 게이트웨이 192.168.39.1 · 활성 어댑터 1개
실패 PrefixOrigin = Dhcp 면 고정 IP 가 적용되지 않은 것입니다. 이 상태로 포트포워딩을 .110 으로 걸어두면 태블릿이 서버에 못 붙습니다. (2026-08-21 실측값은 DHCP 192.168.39.44 였습니다)
실패 활성 어댑터가 2개 이상이면 유선·WiFi 가 동시에 붙어 라우팅이 갈립니다. "됐다 안 됐다" 하는 증상의 단골 원인 — WiFi 를 끄고 다시 하세요.
1-2

ping — 라우터끼리 닿는가

ping -n 10 $ROBOT
ping -n 10 $SRV

# 손실률까지 숫자로 보고 싶으면
Test-Connection $ROBOT -Count 10 | Measure-Object -Property ResponseTime -Average
통과 10회 중 10회 응답. 응답시간이 들쭉날쭉하지 않을 것
주의 10회 중 1~2회만 오면 무선 구간 품질 문제입니다 (2026-08-21 현장과 같은 증상). 라우터 위치를 옮겨 신호세기를 확인하세요. LGIT 정상 장비 기준값은 −71 dBm 입니다.
ping 결과를 과신하지 마세요 — 두 방향 다 틀릴 수 있습니다

ping 이 돼도 로봇과는 무관합니다. ping 은 라우터 자신이 답하는 것이고, 포트포워딩은 거치지도 않습니다. 로봇이 꺼져 있어도 ping 은 성공합니다.

ping 이 안 돼도 통신 불가로 단정하면 안 됩니다. 포워딩 규칙에 ICMP 가 없으면 ping 만 막힙니다. ping 실패 → 그래도 STEP 2 의 TCP 를 반드시 해볼 것.

포트포워딩이 실제로 뚫려 있는지

2-1

포트가 열려 있는가

Test-NetConnection $ROBOT -Port 8090 -InformationLevel Detailed
Test-NetConnection $SRV   -Port 8002
통과 TcpTestSucceeded : True
실패 False → 라우터 포트포워딩을 확인합니다. 관리 페이지는 http://192.168.39.1:8090 (admin / uned123456). 지금 붙어 있는 WiFi 에 따라 다른 라우터에 접속됩니다 — 두 라우터의 LAN 주소가 둘 다 192.168.39.1 입니다.
라우터SSIDWAN 고정 IP포워딩 규칙

초기 PPT 자료와 반대입니다. 위 표가 2026-08-21 현장 실측 기준입니다. 규칙은 TCP · ICMP 두 줄씩 넣으세요 (LGIT 정상 장비 캡처 기준).

2-2

서버 쪽 방화벽 — 태블릿이 못 들어올 때

Get-NetFirewallRule -DisplayName "RCS*" | Select-Object DisplayName, Enabled, Direction

# 없으면 (관리자 PowerShell)
New-NetFirewallRule -DisplayName "RCS Backend 8002" -Direction Inbound -Protocol TCP -LocalPort 8002 -Action Allow -Profile Any
New-NetFirewallRule -DisplayName "RCS Frontend 3000" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow -Profile Any
"규칙이 안 보인다 = 막혀 있다" 가 아닙니다

프로그램 기준 규칙(python.exe 등)으로 이미 열려 있을 수 있습니다. 조회가 비어 있는 것은 없다는 증거가 아닙니다. 가장 확실한 확인은 실제로 다른 기기에서 접속해보는 것입니다.

04 — STEP 3 · 로봇 HTTP

★ "ping 은 되는데 온라인이 안 뜬다" 의 90%가 여기서 갈립니다

먼저 알아야 할 원리 — 관제의 온라인 판정은 딱 하나입니다

GET http://<로봇IP>:8090/chassis/current-map 에 응답이 오기만 하면 online 입니다. 상태코드는 보지 않습니다 — 맵이 설정 안 된 404 도 online 으로 칩니다. (robot_api/robot_live_service.py 의 fetch_robot_live())

/device/info 는 판정에 쓰지 않습니다. LTE 에서 응답이 커서 막히는 사례가 있어 일부러 뺐습니다. 그래서 device/info 가 실패해도 온라인은 뜰 수 있습니다.

3-1

온라인 판정과 완전히 똑같은 프로브 (작은 응답)

curl.exe -s -i --max-time 10 -H "Secret: $SECRET" "http://${ROBOT}:8090/chassis/current-map" |
  Select-Object -First 1
통과 HTTP/1.1 200 또는 404 — 줄이 하나라도 나오면 online 판정은 통과
실패 아무것도 안 나오거나 타임아웃 → 관제에서도 반드시 오프라인으로 뜹니다. 3-3 으로
3-2

로봇이 실제로 살아 있는가

curl.exe -s --max-time 10 -H "Secret: $SECRET" "http://${ROBOT}:8090/chassis/status"
통과 JSON 이 나오고 emergency_stop_pressed 가 false
확인 true 면 비상정지 버튼이 눌린 상태입니다. 통신 문제가 아니라 물리 버튼을 푸세요.
3-3

큰 응답도 통과하는가 — MTU 블랙홀 판별

작은 요청은 되는데 큰 응답만 잘리는 현상입니다. LTE 구간에서 자주 나옵니다.

curl.exe -s -o NUL -w "code=%{http_code} size=%{size_download} time=%{time_total}\n" `
  --max-time 15 -H "Secret: $SECRET" "http://${ROBOT}:8090/device/info"
3-1 (작은 응답)3-3 (큰 응답)해석 · 다음 할 일
OKOK 로봇·네트워크 정상. 원인은 서버 쪽 → STEP 4 로 올라가세요
OKsize=0 / 타임아웃 MTU 블랙홀. 라우터 MTU 를 1400 정도로 낮추세요.
단 관제 온라인은 정상적으로 뜹니다 — 판정은 작은 프로브만 쓰므로. 대신 맵 동기화·장비정보 조회가 실패합니다
FAILFAIL TCP 는 열렸는데 HTTP 응답이 없음 → 포워딩 대상 IP 가 로봇이 아닐 가능성. 로봇 라우터에 직접 붙어 192.168.39.100 으로 같은 명령을 해보세요

WebSocket — 배터리·주행상태가 안 보일 때

curl.exe -s -i -N --max-time 6 `
  -H "Connection: Upgrade" -H "Upgrade: websocket" `

06 — STEP 5 · DB 값

서버가 로봇의 어느 주소를 찌르고 있는지

STEP 3 에서 손으로 찌른 IP 와 DB 에 든 IP 가 다르면, 손으로는 되는데 관제는 오프라인으로 뜹니다. 이 항목이 "ping 은 되는데 온라인 안 뜬다" 의 두 번째로 흔한 원인입니다.

5-1

현재 등록된 값 보기

& $MYSQL @DB -e "SELECT id,name,ip_address,charging_id,standby_id,area_id,is_active FROM robots;"
통과 ip_address 가 STEP 3 에서 성공한 그 IP 와 글자 그대로 같을 것
5-2

IP 수정 — UPDATE 로만

& $MYSQL @DB -e "UPDATE robots SET ip_address='10.115.244.12' WHERE id=12;"

# 반드시 다시 확인 — charging_id / standby_id 가 살아 있어야 한다
& $MYSQL @DB -e "SELECT id,name,ip_address,charging_id,standby_id FROM robots;"
로봇 관리 화면의 "IP로 등록" 을 쓰지 마세요

register-by-ip 는 charging_id·standby_id 를 채우지 않습니다. 배차는 정상으로 보이는데 복귀만 조용히 멈춥니다 — 원인 찾기가 대단히 어렵습니다. IP 만 바꿀 때는 위의 UPDATE 를 쓰고, 수정 뒤 두 값이 NULL 이 아닌지 반드시 확인하세요.

쓰지 않는 로봇이 is_active=1 로 남아 있지 않은지

현장에 없는 로봇이 등록돼 있으면 계속 오프라인으로 뜨고 조회가 느려집니다. 가용 로봇 수 계산에는 영향이 없지만, 화면이 지저분해집니다.

& $MYSQL @DB -e "UPDATE robots SET is_active=0 WHERE id=13;"

6-2

★ 고쳤는데도 한동안 오프라인으로 보이는 이유 — 캐시

온라인 판정은 TTL 캐시를 탑니다

온라인이면 15초, 오프라인이면 60초 동안 이전 결과를 재사용합니다 (dispatch_service.py 의 LIVE_CACHE_TTL / LIVE_CACHE_TTL_OFFLINE). 게다가 화면 폴링은 비블로킹이라, 캐시가 만료돼도 기다리지 않고 직전 값을 즉시 돌려줍니다. (오프라인 로봇 때문에 콘솔이 20초씩 멈추던 것을 고친 결과입니다)

→ IP 를 고치거나 통신을 살린 뒤 최대 60초 + 폴링 한 주기는 오프라인으로 보이는 게 정상입니다. 2분이 지나도 안 바뀌면 그때 진짜 문제입니다. 백엔드를 재시작하면 캐시가 즉시 비워집니다.

08 — STEP 7 · J ↔ R 매핑

이게 없으면 배송 모드로 진입하지 않습니다

매핑은 코드가 아니라 DB job_points 테이블의 데이터 2줄입니다. DB 가 노트북마다 따로 있으므로 서버 노트북에서 다시 넣어야 합니다. 테이블 자체는 서버 기동 시 create_all 이 자동으로 만들어 주므로 수동 SQL 은 필요 없습니다 — 없는 건 데이터 2줄뿐입니다.

7-1

먼저 조회 — 이미 있으면 다시 넣을 필요 없습니다

Invoke-RestMethod "$API/api/dispatch/job-points" |
  Format-Table area_id, j_poi_name, r_poi_name, occupied
통과 J1→R1, J2→R2 두 줄. area_id 가 현재 맵의 area 와 같을 것
7-2

현재 area_id 와 POI id 확인

& $MYSQL @DB -e "SELECT id, area_id, mapping_id FROM robot_maps ORDER BY id DESC LIMIT 3;"

(Invoke-RestMethod "$API/api/dispatch/console/status").pois |
  Format-Table poi_id, poi_name, poi_type, paired_poi_name, rack_occupied

여기서 나온 poi_id 가 태블릿 설정에 넣을 POI ID 이기도 합니다.

7-3

등록

$u = "$API/api/dispatch/job-points"
$h = @{ "Content-Type" = "application/json" }

Invoke-RestMethod $u -Method Post -Headers $h -Body '{"area_id":29,"j_poi_name":"J1","r_poi_name":"R1"}'
Invoke-RestMethod $u -Method Post -Headers $h -Body '{"area_id":29,"j_poi_name":"J2","r_poi_name":"R2"}'

# 확인
Invoke-RestMethod $u | Format-Table area_id, j_poi_name, r_poi_name, occupied

29 자리에 7-2 에서 확인한 실제 area_id 를 넣으세요.

7-4

함정 세 가지

함정왜 위험한가대처
area_id 가 틀려도
"되는 것처럼" 보인다		 매핑 조회는 area 로 못 찾으면 이름만으로 폴백합니다. 옛 area 줄이 남아 있으면 그게 잡혀서 동작은 하지만, 의도한 설정이 아닙니다 7-1 의 GET 으로 area_id 를 눈으로 확인
등록해도 옛 줄이 안 사라진다 upsert 는 (area_id, j_poi_name) 이 정확히 일치할 때만 갱신합니다. area 가 다르면 새 줄이 추가되고 옛 줄은 그대로 남습니다 옛 줄 삭제:
Invoke-RestMethod "$API/api/dispatch/job-points/J1?area_id=26" -Method Delete
occupied=1 이면
호출 버튼이 안 나온다		 J 에 랙이 놓였다는 표시입니다. 랙 감지 센서가 없어 시스템이 스스로 못 풉니다. 라이다로도 판정 불가가 확정됐습니다(로봇이 자기가 든 랙을 인식) 태블릿 [확인] 또는
Invoke-RestMethod "$API/api/dispatch/poi/<POI id>/rack-cleared" -Method Post
롤백은 매핑 삭제 한 줄

매핑이 없으면 종전 인터랙티브 화면으로 그대로 돌아갑니다. 코드를 되돌릴 필요가 없습니다.

Invoke-RestMethod "$API/api/dispatch/job-points/J1?area_id=29" -Method Delete
Invoke-RestMethod "$API/api/dispatch/job-points/J2?area_id=29" -Method Delete
최종 통과 R1 호출 후 백엔드 로그에 [dispatch] 배송 모드 — robot=NN R1 → J1 이 찍힐 것. 이 줄이 없으면 매핑을 못 찾아 기존 모드로 빠진 것입니다 — area_id 를 다시 보세요

09 — STEP 8 · 맵 · POI · 랙

현장에서 맵을 새로 딴 뒤 반드시 다시 볼 것들

8-1

로봇이 어느 맵을 물고 있나

curl.exe -s -H "Secret: $SECRET" "http://${ROBOT}:8090/chassis/current-map"

& $MYSQL @DB -e "SELECT id,area_id,mapping_id,image_url FROM robot_maps ORDER BY id DESC LIMIT 5;"
실패 로봇 쪽 맵과 DB 쪽 맵이 다르면 관제 화면에 로봇이 엉뚱한 곳에 찍힙니다
8-2

POI 와 랙 규격

& $MYSQL @DB -e "SELECT id,name,poi_type,rack_size FROM map_pois WHERE is_active=1 ORDER BY name;"
통과 R1·R2 가 standby 이고 rack_size 가 채워져 있을 것
rack_size 는 두 종류입니다

LG = LG 에서 받은 초록 대차 · LG2 = 우리가 커스터마이징한 대차. 틀리면 정렬 단계에서 Wrong rack size 로 실패합니다. 규격값은 도면 치수가 아니라 라이다가 재는 다리 중심 간격에 맞춘 값입니다.

8-3

맵을 새로 딸 때 놓치기 쉬운 것

  1. 맵 뜰 때 R 자리에 랙을 두지 말 것. 랙 다리 4개가 지도에 영구 장애물로 박혀, 나중에 출발점이 팽창영역에 걸려 calculation_failed 가 납니다 (2026-08-11 실제 사례)
  2. 맵을 다시 만들면 area_id 와 POI id 가 전부 바뀝니다 → job_points 매핑(STEP 7)과 태블릿 POI ID(STEP 9)를 다시 넣어야 합니다
  3. charging_id·standby_id 가 NULL 이 되지 않았는지 확인 (STEP 5-2)
  4. 충전독에 도킹한 상태로 맵핑하면 조용히 실패합니다. 도킹을 풀고 시작하세요

10 — STEP 9 · 태블릿

서버 라우터를 바꿨다면 태블릿은 전부 다시 설정해야 합니다

서버 주소는 코드도 DB 도 아닌 기기 안에 저장됩니다

APK 는 서버 주소를 각 태블릿의 SharedPreferences("config") 에 넣습니다. 서버 라우터 WAN IP 가 바뀌면 태블릿 대수만큼 손으로 다시 넣어야 합니다. APK 재빌드는 필요 없습니다.

APK서버 주소ID 칸

태블릿 크롬에서 아래 주소가 열리면 네트워크·서버는 정상입니다. APK 문제인지 통신 문제인지 가장 빠르게 갈라주는 방법입니다.
