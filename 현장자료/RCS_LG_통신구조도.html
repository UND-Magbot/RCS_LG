RCS LG · LGIT L150

로봇·서버·태블릿은 서로 어떻게 통신하는가

PLTE 전용망부터 라우터 2대, 그리고 자체 USIM으로 올라오는 태블릿 2대까지 — 무엇이 어느 IP에 붙고, 어떤 프로토콜로, 얼마 주기로 말을 거는지 한 장에 정리했습니다.

기준일 2026-08-24 브랜치 feature/luke-lg 현장 실측 2026-08-20 · 08-21 정정 08-24 태블릿 연결 방식

01 — 전체 구조

라우터 두 대는 로봇과 서버를 위한 것이고, 태블릿은 그 밖에서 따로 올라온다

로봇은 돌아다니고 서버는 한자리에 고정돼 있습니다. 그래서 라우터를 각각 하나씩 두고, 둘 사이는 LG U+ M2M 전용 APN 망(PLTE)으로만 연결합니다. 태블릿은 어느 라우터에도 붙지 않습니다. 각자 USIM을 꽂고 자기 LTE로 직접 나갑니다.

02 — 방향

누가 먼저 말을 거는지가 모든 설정을 결정한다

고정 IP를 줄지, 포트포워딩을 걸지는 취향이 아니라 연결을 먼저 거는 방향에서 자동으로 결정됩니다. 태블릿은 항상 자기가 먼저 겁니다. 로봇은 항상 받기만 합니다.

03 — 포트포워딩

양쪽 라우터 모두 필요하다. 서로가 서로의 바깥에 있기 때문이다

포워딩이 필요한 조건은 하나입니다 — 라우터 안쪽 장비를 라우터 바깥에서 부를 때. 태블릿이 자체 LTE로 나가는 순간 태블릿은 서버 라우터의 바깥이 되고, 로봇은 원래부터 서버 라우터의 바깥이었습니다. 그래서 두 규칙이 모두 필요합니다.

이 규칙이 지금 어긋나 있습니다 08-21 실측

서버 라우터의 포워딩 대상은 192.168.39.110인데, 서버 PC 실측 IP는 192.168.39.44(DHCP)입니다. 태블릿이 자체 LTE를 쓰는 구성에서는 콘솔·로봇 부착 태블릿 두 대가 모두 이 포워딩에 걸려 있으므로, 이 상태로는 태블릿 화면이 아예 뜨지 않습니다. 서버 PC를 39.110으로 고정하거나, 포워딩 대상을 39.44로 바꿔야 합니다.

04 — 고정 IP

라우터에서 DHCP를 끄는 것만으로는 고정 IP가 되지 않는다

03의 39.44 ↔ 39.110 불일치를 없애는 작업입니다. 여기서 가장 자주 어긋나는 지점이 하나 있습니다 — DHCP를 끄는 것과 고정 IP를 넣는 것은 서로 다른 작업인데, 하나만 해도 되는 것처럼 보인다는 점입니다.

세 가지를 구분해야 합니다

하는 일어디서고정이 되나비고
DHCP Disable 라우터 관리 페이지 안 됨 자동 할당만 멈춘다. 주소는 여전히 장비에서 넣어야 한다
DHCP 예약 (MAC 고정 할당) 라우터 관리 페이지 조건부 DHCP를 끄면 성립하지 않는다. LG 표준과 양립 불가
장비에 직접 입력 서버 PC 어댑터 설정 됨 이 현장에서 쓸 방법. LG 표준이 요구하는 방식
LG 자료에 적힌 그대로입니다 docs/07:237

DHCP 사용 : Disable — 자동 할당을 끄고 장비마다 고정 IP 직접 입력. 이어지는 문장이 "LG 표준은 DHCP를 끄는 방식이다. 서버·로봇 IP를 각 장비에서 직접 넣어야 한다"입니다. DHCP Disable은 전제 조건이지 수단이 아닙니다.

적용됐는지 확인하는 방법

docs/07:115가 지정한 확인 방법은 PrefixOrigin입니다 — Manual이면 적용, Dhcp면 미적용. 어느 어댑터에 걸렸는지도 같은 줄에서 보입니다.

확인 항목성공실패일 때 의미
PrefixOrigin Manual Dhcp — 고정이 이 어댑터에 안 걸렸다
IPv4 주소 192.168.39.110 다른 값 — 프로필·어댑터를 잘못 골랐을 가능성
InterfaceAlias 실제 연결에 쓰는 어댑터 이더넷에 걸었는데 WiFi로 통신 중이거나 그 반대
ping 192.168.39.1 응답 있음 대역·게이트웨이가 틀렸다

왜 .44가 나왔나 — 후보

당시 어느 프로필·어댑터에 값을 넣었는지 기록이 없어 단정할 수 없습니다. 아래는 전부 추정이며, 위의 PrefixOrigin 확인 한 번으로 갈라집니다.

순위후보왜 그럴듯한가
1 다른 SSID 프로필에 넣었다 두 라우터 LAN이 둘 다 192.168.39.1이라 잘못 붙어도 대역이 맞아 보인다. Windows의 IP 할당은 SSID 프로필 단위다
2 유선인데 무선 프로필에 넣었다 docs/07:110이 직접 지적 — "기존에 본 .44는 WiFi 값일 수 있으므로 유선 연결 후 다시 실측해야 한다"
3 저장이 실패했다 서브넷 칸이 접두사 길이(24)를 요구하는데 255.255.255.0을 넣으면 막힌다. 저장 실패 시 조용히 DHCP가 유지된다
4 다른 어댑터 줄을 읽었다 어댑터 이름이 … NIC #2 — 같은 NIC가 두 번 열거돼 있어 39.x가 여러 줄 나올 수 있다
5 IP 충돌 가능성 낮음 충돌 시 Windows는 DHCP로 되돌아가지 않고 해당 어댑터의 IPv4를 죽인다 — 증상 모양이 다르다
순서를 지켜야 합니다 — DHCP Disable은 마지막입니다

먼저 끄면 다른 장비를 붙일 때 주소를 못 받아 작업이 막힙니다. ① 랜선 연결 + WiFi 끄기(동시 연결이면 라우팅 메트릭이 꼬여 "됐다 안 됐다" 증상이 납니다) → ② 이더넷에 .110 / 24 / GW 192.168.39.1 입력 → ③ PrefixOrigin = Manual 확인 → ④ 게이트웨이 ping → ⑤ 라우터 포워딩 대상이 .110인지 재확인 → ⑥ 그 다음에 DHCP Disable.

IP를 맞춰도 이것이 남아 있으면 여전히 안 뜹니다 docs/07:122

LG 라우터의 기존 포워딩 표에 8002가 이미 등록돼 있습니다 (8002 → 192.168.101.2, LG 정상 장비 캡처). 남아 있으면 태블릿 요청이 우리 서버가 아니라 LG 장비로 배달됩니다. 현장에서 포워딩 표를 열면 이것부터 확인해야 합니다.

이 페이지의 이전 판은 여기가 틀렸습니다 08-24 정정

이전 판은 태블릿이 라우터 WiFi에 붙는다고 적었습니다. 근거로 삼은 docs/02_네트워크.md가 그렇게 기술하고 있었기 때문인데, docs/07 머리말에 "02의 LTE 설정값은 이 문서가 우선한다"고 명시돼 있었고 현장 운용도 USIM LTE입니다. 낮은 우선순위 문서를 인용한 것이 원인입니다.

왜 라우터 WiFi가 아니라 자체 LTE인가

태블릿(LG-P530L)은 Nano-SIM 슬롯이 있고, 태블릿용 M2M USIM 6장이 번호·일련번호까지 배정돼 발급돼 있습니다. 라우터에 얹는 구성은 문서상 "LTE가 끝내 안 될 때의 우회안"으로만 적혀 있습니다.

  • 콘솔 태블릿은 라우터 커버리지 밖일 수 있다 — 서버 PC 옆이 아니라 작업자 동선에 놓입니다. 자체 회선이면 위치 제약이 없습니다.
  • 로봇 라우터는 로봇 전용으로 남는다 — 태블릿 트래픽이 로봇 제어 회선에 얹히지 않습니다.
  • 대신 리스크가 하나 생깁니다 — 태블릿 LTE는 08-20 현장에서 연결/끊김 반복, APN 유지 실패, IP 고정 실패로 기록됐습니다. 작업장 안에서 위치를 옮겨도 동일해 전파가 아닌 단말 호환성으로 판정됐고, LGIT가 plte망 지원 모델을 확인 중입니다. 미해결

LG 측이 말한 "간혹 끊기나 접속은 가능"이 이 기록과 일치합니다. 즉 태블릿 끊김은 소프트웨어가 아니라 단말·회선 쪽 문제일 가능성이 큽니다(추정).

참고로 로봇이 라우터를 쓰는 이유는 다릅니다. 로봇은 USIM 슬롯이 아예 없어 WiFi만 지원하므로, 라우터가 WiFi ↔ LTE 번역기 역할을 해야 합니다. 로봇은 어쩔 수 없어서 라우터를, 태블릿은 자기 회선을 씁니다.

06 — 프로토콜

WebSocket은 로봇 실시간 데이터에만, 나머지는 전부 HTTP

서버 → AutoXing 클라우드 HTTPS + X-Token 없음 timeout 5초 AxClient.py:20
WebSocket은 "상시 연결"이 아닙니다

로봇 상태 조회용 WebSocket은 연결 → 토픽 구독 → 데이터 받으면 즉시 close하는 단발성입니다. 지속적으로 물고 있는 것은 관제 웹화면의 로봇 위치 스트림(/tracked_pose)뿐이고, 이것도 화면을 닫으면 끊깁니다. 이동 명령 자체는 WebSocket이 아니라 HTTP입니다.

태블릿에는 WebSocket이 한 줄도 없습니다

태블릿이 부르는 주소는 tablet-status, confirm, end 세 개뿐이고 모두 서버 :8002입니다. 로봇 포트 :8090을 부르는 코드는 0건입니다. 그리고 tablet-status는 DB만 조회하므로, 로봇 통신이 나빠져도 태블릿 화면은 영향받지 않습니다.

07 — 장애 동작

끊김은 자동 복구된다. 단 "시작할 때 끊겨 있으면" 예외다

사람이 안 껐는데도 재로드가 일어나는 경우

트리거현재 상태결과
화면 회전 · 크기 변경 방어됨 configChanges 등록 재로드 안 일어남
절전(Doze) 진입 방어됨 충전 중 + 화면 상시 점등 진입 조건 미성립
WebView 렌더러 크래시 미처리 onRenderProcessGone 없음 앱 전체 종료 → 수동 재실행
태블릿 자체 재부팅 미처리 부팅 리시버 없음 앱이 안 뜸 → 수동 실행
다크모드 자동 전환 · 언어 변경 미방어 uiMode 누락 액티비티 재생성 → 페이지 재로드
시스템 WebView 자동 업데이트 미방어 프로세스 재시작 → 페이지 재로드
반대로, 이것들은 마음껏 껐다 켜도 됩니다

로봇(태블릿과 통신하지 않음), LTE 라우터, 서버 PC — 전부 재부팅해도 태블릿이 다음 폴링에서 알아서 다시 붙습니다. 유지해야 하는 것은 태블릿 앱 하나뿐입니다.

08 — 데이터 사용량

회선이 나뉘어 있어 여유롭다. 위험한 것은 태블릿이 아니라 관제 화면이다

관제 모니터링 화면을 24시간 열어두지 마십시오. 로봇 위치 WebSocket이 초당 10회씩 좌표를 받아오는데, 이것 하나가 태블릿 전체를 합친 것보다 데이터를 많이 씁니다. 보지 않을 때 창을 닫는 것만으로 월 수 GB가 절약됩니다. 태블릿은 각자 USIM 회선을 쓰므로 한 대당 월 1GB 수준이고, 로봇 회선에 합산되지 않습니다.
