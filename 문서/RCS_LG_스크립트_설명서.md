## 1. `robot_check.py` — 로봇 상태 진단

### 무엇을 하나

REST 로는 못 읽는 값들을 WebSocket 으로 모아 한 화면에 보여줍니다.
**테스트 시작 전에 반드시 한 번 돌리세요.**

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py           # 한 번
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --watch   # 3초마다
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --rack    # 랙 검출까지
```

### 출력

```
==================================================================
  로봇 192.168.30.100   14:39:35
==================================================================
  위치추정  [문제]  lidar_matched=False  score=0.306
            reliable=True quality=10 wheel_slipping=False
            ↳ 로봇이 자기 위치를 잘못 알고 있을 수 있습니다.
  섀시      [정상]  비상정지=False 제어모드=auto 바퀴과부하=False
  잭        [정상]  내려감   state=hold progress=0.0 weight=0
  현재위치  (+0.765, -28.552)  ori=+245.8도
            R1 까지 165cm, 방향차 +151.3도
  랙 위치   R1  (-0.015, -30.008) ori=+94.5도  rack_size=LG2
==================================================================
```

### 항목별 의미

| 항목 | 정상 | 문제일 때 |
|---|---|---|
| **`lidar_matched`** | `True` | ★ `False` 면 **로봇이 자기 위치를 잘못 앎.** 이 상태로는 어떤 테스트도 무의미 |
| `lidar_matching_score` | 높을수록 좋음 | 2026-08-13 문제 상황은 0.21~0.37 |
| 섀시 | auto / 비상정지 False | 비상정지·원격모드면 이동 불가 |
| 잭 `progress` | 0.0 = 내려감 | **1.0 = 올라감.** 이 상태로 이동하면 랙이 끌려감 |
| 잭 `weight` | 0 = 빈 상태 | 65~69 = 랙 적재 중 |
| 랙검출 (`--rack`) | 검출 > 0 | **로봇이 랙 아래에 있어야만 잡힘** |

> `현재위치` 가 안 나오는 것은 정상입니다. `/tracked_pose` 는 로봇이 정지 중이면 발행되지 않습니다.

## 2. `rack_bench.py` — 랙 인식 전용 벤치

### 왜 따로 만들었나

배차(세션·워커·경유지)를 거치지 않고 **랙 인식만** 반복합니다.
백엔드가 필요 없고, `zone_guard`·워커 상태 같은 부수효과가 섞이지 않습니다.

**★ 핵심 설계: `align_with_retry` 를 쓰지 않습니다.**
백엔드의 그 함수는 실패 시 재로컬화 → 후진 0.5m → 측면 우회로 4번까지 시도합니다.
그걸 쓰면 1차에 실패해도 3차에 우연히 성공해 **"잘 됩니다"로 보입니다.**
여기서 재려는 건 **1차 성공률**이라, `align_with_rack` 을 딱 1회만 보냅니다.
(`--retry` 옵션을 주면 4단계를 켜되, **몇 차에 성공했는지 따로 기록**합니다)

### 실행

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\rack_bench.py --cond B --trials 20 --retry
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--trials` | 20 | 한 세트당 반복 횟수 |
| `--retry` | 꺼짐 | 4단계 회복 재시도 켜기 (실운영과 동일) |
| `--fail-limit` | 3 | 연속 **최종 실패** 이 횟수면 중지 (1차 실패는 안 셈) |
| `--backoff` | 2 | 반납 후 후진 거리(m) |
| `--cond` | B | 조건 라벨 (A=체인 현상태 / B=기둥 밀착 / C=제거) |
| `--dry-run` | — | 연결·POI 확인만 |

### 조작

| 키 | 동작 |
|---|---|
| `Enter` | **자동 반복 시작** — N회 돌고 멈춤 → 랙 자세 입력 → 다음 세트 |
| `Space` | 수동: 랙 진입 ↔ 반납 토글 |
| `d` | 랙 치수 측정 (15초) |
| `s` / `2` | 로봇의 현재 규격 조회 / LG2 주입 |
| `w` / `e` | `leg_size` ∓5mm 조정 후 주입 |
| `x` | 이동 취소 (비상) |
| `q` | 종료 + 결과 집계 |

### 세트 = 랙 한 자세

세트가 시작될 때마다 **랙 자세를 직접 타이핑**합니다.

```
  다음 세트의 랙 자세를 적어주세요.
  예)  정위치  /  오른쪽으로 조금 돌림  /  왼쪽으로 많이 돌림

  랙 자세 > _
```

> 자세를 안 적으면 나중에 **어느 자세가 문제였는지 알 수 없습니다.**
> 2026-08-12에 4시간·120회를 돌리고도 50%가 나온 세트의 자세를 몰라 재현을 못 했습니다.
>
> 로봇 자세로 각도를 자동 기록하려 했으나 `/tracked_pose` 가 **정지 상태에서 발행되지 않아**
> 120건 전부 실패했습니다. 라벨이 유일하게 확실한 방법입니다.

**허용 각도를 재려면** — 랙 다리 간격 0.64m 기준, 한쪽 다리만 옮깁니다.

| 옮기는 거리 | 각도 |
|---|---|
| 2.2 cm | 약 2° |
| 5.6 cm | 약 5° |
| 11 cm | 약 10° |
| 17 cm | 약 15° |

**작은 각도부터** 하세요. 큰 것부터 하면 전부 실패해 아무 기준도 안 남습니다.

### 결과표

```
  세트  랙 자세          1차  2차  3차  4차  최종실패  1차성공률    최종성공률   평균시간
  1    정면              19   1   0   0      0     95%(19/20)  100%(20/20)    30s
  2    왼쪽 5도           17   2   1   0      0     85%(17/20)  100%(20/20)    32s
  3    왼쪽 10도           9   4   3   0      4     45%(9/20)    80%(16/20)    58s

  최종 실패 4건 — 실패 순간 로봇이 랙을 봤는가:
    세트3 [왼쪽 10도] 4차까지 시도 — 검출 0/77회
    세트3 [왼쪽 10도] 4차까지 시도 — 검출 11/84, 중앙 0.710 x 0.580
```

**읽는 법**
- **1차 성공률** = 랙 인식이 얼마나 깨끗한가 (자세의 좋고 나쁨)
- **최종 성공률** = 실운영에서 실제로 성공하는 비율 ← 현장에서 중요한 숫자
- **뒤 단계(3·4차)에 몰리면** 지금은 되지만 여유가 없다는 뜻
- **"랙을 봤는가"** 가 원인을 가릅니다
  - `검출 0` → 랙을 **아예 못 봄** (위치·자세 문제)
  - `검출 있음 + 치수 큼` → **봤는데 뭔가를 다리로 오인** (체인 등 간섭물)

### 실패 분류

| 분류 | 의미 | 성공률 집계 |
|---|---|---|
| `ok` | 성공 | 포함 |
| `rack` | 진짜 랙 인식 실패 (`fail_reason=501`) | 포함 |
| `timeout` | 시간 초과 | 포함 |
| `jack` | 잭 상태 문제 (`fail_reason=506`) | **제외** |
| `comm` | 통신 두절 | **제외** |

**506(`jack is in up state`)은 랙 인식 실패가 아닙니다.** 잭이 올라가 있어 이동이 거부된 것입니다.
이걸 랙 실패로 세면 성공률이 왜곡됩니다.

## 3. `auto_cycle.py` — 고정 경로 배차 사이클

### 무엇을 하나

콘솔에서 사람이 하던 것과 **똑같은 API** 를 호출합니다. 백엔드 코드는 안 건드립니다.

```
호출(J1) → 랙 픽업(align + jack_up) → J1 도착
  → 경유지 J2,J3,J4 등록 + 출발
  → 각 도착마다 dwell 초 후 자동 [확인]
  → 마지막 확인 → 복귀(랙 반납 + 충전소) → 다음 사이클
```

### ★ 진짜 목적은 "랙 반납 정확도"

매 사이클마다 랙을 내려놓고 다시 집습니다. 반납 위치가 조금씩 밀리면
**사이클이 갈수록 픽업이 어려워집니다.**

```
  사이클  픽업+이동   →J2   →J3   →J4   복귀   합계
  1           28      45    38    41    112    264
  2           31      44    39    40    115    269
  3           71      46    38    42    118    315
  ------------------------------------------------
  픽업 소요 추세: 28초 → 71초  (증가 ↑)
  ⚠️ 랙 반납 위치가 밀리고 있을 가능성
```

**픽업 시간이 우상향하면** 몇 사이클마다 사람이 랙을 맞춰줘야 하는지가 정해집니다.

> 근본 원인 후보: 복귀 시 랙 반납이 `standard` 이동입니다
> (`dispatch_service._return_to_standby_and_park`).
> `standard` 는 **로봇**을 POI에 세우는 것이라 **랙**은 그만큼 어긋난 자리에 놓입니다.
> `to_unload_point` 로 바꾸는 개선이 검토 중입니다 (미적용).

### 실행

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --dry-run     # 연결 확인
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --rounds 1    # 1사이클, 지켜보며
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --rounds 10   # 무인 반복
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--rounds` | 1 | 반복 횟수 |
| `--call` | J1 | 호출할 POI **이름** |
| `--route` | J2,J3,J4 | 경유지 POI **이름** 순서 |
| `--dwell` | 5 | 도착 후 자동 확인까지 대기(초) |
| `--rest` | 10 | 사이클 사이 휴식(초) |
| `--pickup-timeout` | 300 | 단계별 한도 — **전부 추정치라 실측 후 조정 필요** |
| `--move-timeout` | 300 | |
| `--return-timeout` | 420 | |

> **★ POI 를 id 가 아니라 이름으로 지정합니다.**
> 2026-08-12 하루에만 POI id 가 두 번 바뀌었습니다(985 → 988 → 1009).
> 이름은 안 바뀌므로 맵을 다시 따도 스크립트를 고칠 필요가 없습니다.

### 안전

⚠️ **[확인] 버튼은 원래 "이 지점 작업이 끝났고 출발해도 안전하다"는 사람의 승인**입니다.
이 스크립트는 그걸 시간(`--dwell`)으로 대체하므로 **테스트 전용**입니다. 현장 운영에 쓰지 마세요.

**첫 회차는 반드시 옆에서 지켜보고, `Ctrl+C` 로 비상정지가 실제로 되는지 확인하세요.**

## 4. `random_cycle.py` — 랜덤 배차 사이클

### 왜 필요한가

정해진 순서만 돌면 **안 밟히는 경로**가 있습니다. 특히 **예약 이어받기**
(`_take_next_reservation_if_continuable`)는 실기에서 거의 안 돌려본 코드라
여기서 버그가 나올 가능성이 높고, **그걸 찾는 것이 이 테스트의 목적**입니다.

### 흐름 (콘솔 실제 화면 기준)

```
1. 호출 POI 랜덤 (J1~J4)
2. 랙 픽업 → 도착 → awaiting_next
3. ★ 랜덤 분기 ①  — 콘솔에 [경유지 등록] [종료] 두 버튼이 있는 지점
     (a) 경유지 1~3개 랜덤 등록 → 진행
     (b) 바로 [종료] → 복귀              ← "한 번은 그냥 복귀"
4. 각 경유지 도착 → 랜덤 대기 → [확인]
     (낮은 확률로 도중에 [종료])
5. ★ 랜덤 분기 ②  — 마지막 확인 **전에** 확률 p 로 다른 POI 예약
     예약 있음 → 백엔드가 자동 이어받기(충전소·랙반납 생략) → 3번으로 (루프)
     예약 없음 → 복귀 → 사이클 종료
```

> ⚠️ **마지막 [확인] 뒤에 "복귀할지 더 할지" 고르는 화면은 없습니다** (코드·화면 확인함).
> 더 진행하려면 **예약이 미리 걸려 있어야** 합니다. 그래서 분기 ②가 예약을 겁니다.
>
> 콘솔의 선택 화면은 **`awaiting_next` 시점**(호출 지점 도착 직후)에 있습니다.

### 실행

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --dry-run
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --seed 42 --cycles 3
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --seed 42 --cycles 20
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--seed` | 42 | **★ 반드시 고정.** 재현 불가하면 원인 분석이 불가능 |
| `--cycles` | 3 | 사이클 수 |
| `--route-prob` | 0.8 | 분기①에서 [경유지 등록]을 고를 확률 |
| `--reserve-prob` | 0.5 | 마지막 확인 전 예약을 걸 확률 (= 이어받기 유발) |
| `--abort-prob` | 0.1 | 경유지 도중 [종료]를 누를 확률 |
| `--max-waypoints` | 3 | 한 구간의 최대 경유지 수 |
| `--max-legs` | 4 | 한 사이클의 최대 구간 수 (무한루프 방지) |

### 불변식 검사 — 백엔드 결함 후보 찾기

매 시도마다 아래를 확인하고, 위반하면 결과에 표시합니다.

- **보낸 경유지 순서 == 실제 방문 순서**
  (2026-08-11에 동시 [출발] 시 이게 어긋나는 결함을 실제로 잡았습니다)
- **`is_last` 표시가 실제와 일치**

```
  ⚠️ 불변식 위반 2건 — 백엔드 결함 후보:
    - [사이클3] 경유지 순서 불일치 — 보낸 것=J3, 실제 도착=J4
```

### 결과표

```
  #   호출   구간                이어받기   총시간   종료 사유
  1   J2    J4→J1                    1      412    예약 없음 → 자동 복귀
  2   J1    (없음)                   0       98    랜덤: 경유지 없이 종료
  3   J3    J1→J2→J4 / J3            2      680    최대 구간 4 도달

  종료 사유 분포:
     3회  랜덤: 경유지 없이 종료
     2회  예약 없음 → 자동 복귀
     1회  예약 있었으나 이어받기 안 됨    ← 원인 확인 필요
```

**"예약 있었으나 이어받기 안 됨"** 이 나오면 원인을 봐야 합니다:
- 배터리가 `min_battery` 미만 (백엔드가 충전 우선으로 판단)
- 그 POI 가 점유됨
- 이어받기 로직 결함 ← 이걸 찾는 게 목적

> 종료 시 **이 스크립트가 건 예약을 자동으로 정리**합니다. 안 하면 다음 실행에 영향을 줍니다.

## 6. 세 스크립트 공통 — 안전 장치

| 상황 | 동작 |
|---|---|
| **비상정지(E-STOP)** | **실패로 세지 않고 대기.** 해제하면 자동으로 이어짐 (최대 5분) |
| **통신 두절** | 대기 후 재개. 성공률 집계에서 제외 |
| **이동 명령 전** | ★ **잭 상태를 로봇에 직접 확인** → 올라가 있으면 먼저 내림 |
| `x` 키 | 현재 이동 취소 |
| `q` 키 | 자동 반복 중단 |
| `Ctrl+C` | 이동 취소 → 세션 정리 → 스냅샷 저장 → 종료 |

### E-STOP 을 "대기"로 처리하는 이유

백엔드도 사실상 같게 동작합니다. `safe_move` 가 이동 실패 시 **5초 간격으로 최대 200회(≈17분) 재시도**하므로
세션이 죽지 않습니다. 다만 백엔드는 E-STOP 인지 **모르고** 재시도할 뿐이라 화면에 사유가 안 뜹니다.
스크립트는 사유를 정확히 알려주고, 백엔드의 17분보다 먼저 끊도록 **5분**으로 제한합니다.

### ★ 잭 판정 기준은 `progress` 입니다 (`weight` 아님)

```
랙 적재:   progress 1.0, weight 65
내려놓음:  progress 0.0, weight  0
잭만 올림: progress 1.0, weight  0~26   ← weight 로는 구분 불가
```

2026-08-13에 `weight` 로 판정했다가 **"잭은 올라갔는데 랙을 못 받친"** 경우를 '내려감'으로 오판했고,
그 상태로 후진해 **랙을 끌고 간 사고가 두 번** 있었습니다.

또 하나: **HTTP 타임아웃 = 명령 실패가 아닙니다.**
`jack_up` 의 응답을 못 받아도 명령은 실행됐을 수 있습니다. 예외가 나면 단정하지 말고
**로봇에 실제 상태를 물어봐야** 합니다.
