## 1. 충전 도킹은 어떻게 동작하는가

### 2단계 구조 (우리 코드)
```python
# dispatch_service.py — 충전소 복귀
safe_move(ip, "standard", C1-1 좌표, max_attempts=12, timeout=60)   # ① 사전 접근
time.sleep(2)
safe_move(ip, "charge",   C1 좌표, charge_retry_count=5)             # ② 도킹
```

`_find_charge_approach_poi()` 는 **`"{충전소이름}-1"` 이름으로만** 접근점을 찾는다.
거리·방향 검증이 없고, 없으면 충전소 좌표를 그대로 쓴다.

### 로봇이 실제로 하는 일
실패 코드 목록이 곧 절차다 (`moves.md` MoveFailReason):
```
①  우리가 준 좌표(C1) 근처로 이동
②  센서로 실제 충전독을 탐지        ← 실패 101 charge_dock_detection_error
③  탐지한 실제 위치로 정렬 이동      ← 좌표 무효 103 invalid_charge_dock
④  후진 접촉 · 도킹 신호 확인        ← 실패 102 charge_dock_signal_error
⑤  충전 전류 확인                   ← 없으면 105 no_charge_current
    재시도 한도 초과 → 100 charge_retry_count_exceeded
```

**즉 C1 좌표는 "이 근처에 독이 있다"는 힌트이고, 로봇이 센서로 찾아 스스로 정렬한다.**
근거: C1이 실제 독과 55cm 어긋난 상태에서도 도킹이 성공했다.

**"앞으로 나왔다 다시 후진"은 ②③의 재시도**다. 우리가 `charge_retry_count=5` 로 지정하므로
2~3번 만에 들어가는 것은 실패가 아니라 설계 범위 안이다.

### C1-1 은 멀리 찍는다
**SDK·REST 어느 문서에도 접근점 거리 규정이 없다** — 접근점은 우리가 만든 개념이다.

| C1 → C1-1 | 결과 |
|---|---|
| 36cm | 재시도 잦음 (정렬할 거리가 부족) |
| **1.2m** | **한 번에 도킹** ← 2026-09-03 확인 |

지켜야 할 것:
- **일직선** — 독·C1·C1-1이 한 줄 (실측 이탈 0.4cm)
- **각도는 독을 등지는 방향** — 충전 접점이 뒤에 있어(`charge_contact_position: back`) 후진 도킹한다.
  C1·C1-1·도킹 중인 로봇의 heading이 모두 같아야 한다 (실측 0.55 / 0.58 / 0.56)

## 2. ★ 도킹 상수 — 하나를 둘로 분리 (2026-09-03 수정)

### 무엇이 문제였나
`DOCKING_OFFSET = 0.3` 하나가 세 곳에서 **부호도 반대, 대상도 다르게** 쓰이고 있었다.

```
[충전독] ←── 55.1cm ──→ [C1] ←─ 8.3cm ─ [도킹한 로봇 중심]
   ↑ map.py:245 (C1 − off)      ↑ map.py:2002 / boot_recovery:216 (C1 + off)
```

**55cm와 8cm짜리 서로 다른 값에 같은 0.3을 쓰고 있었다.** 값이 `0.9 → 0.0 → 0.3` 으로
두 번 뒤집힌 이력도 이 때문으로 보인다(한쪽을 맞추면 다른 쪽이 틀어짐).
현재 값 0.3은 "VESA 버전 최신 상태 반영" 커밋으로 넘어온 것이라 LG 환경 실측 근거가 없었다.

### 실측 (S300, 도킹 상태에서 2회 · 재현 확인)
| | 측정 방법 | 값 |
|---|---|---|
| 충전독 본체 | `GET /services/query_pose/charger_pose` | (0.375, 5.136) |
| 로봇 중심 | WS `/tracked_pose` | (0.770, 5.388) |
| DB C1 | — | (0.838, 5.435) |

→ **C1→충전독 55.1cm · C1→로봇중심 8.3cm · 충전독→로봇중심 46.8cm** (일직선, 검산 일치)

### 수정 내용 (`map.py:127`)
```python
CHARGER_BEHIND_POI = 0.55   # C1 → 충전독 본체 (뒤).  map.py:245
DOCK_POSE_OFFSET   = 0.0    # C1 = 로봇 도킹 위치.    map.py:2002, boot_recovery:216
```

| 대상 | 수정 전 오차 | 수정 후 |
|---|---|---|
| 충전독 overlay (로봇에 등록) | 25.4cm | **1.3cm** |
| 위치재조정 · 재부팅 위치 주입 | 38.4cm | **8.2cm** |

`DOCK_POSE_OFFSET = 0.0` 은 예전 커밋 `f4942d2` 가 *"POI 좌표 = 도킹 위치"* 라며
0.0으로 바꿨던 판단과 같다. 그게 맞았는데 이후 VESA 값이 덮은 것으로 보인다.

### ★ 코드만 고치면 안 된다 — 맵 동기화 필요
충전독 좌표는 **맵 동기화 때 overlay로 전송**된다. 코드를 고쳐도 동기화를 안 하면
로봇은 옛 좌표를 그대로 갖고 있다.

### 기종이 바뀌면 (줄자 불필요)
```powershell
(Invoke-RestMethod "http://<로봇IP>:8090/device/info").robot.charge_contact.pose_2d
```
```
CHARGER_BEHIND_POI = |pose_2d[1]| + 0.099 + (C1↔로봇 오차)
S300: 0.369 + 0.099 + 0.083 = 0.551
```
`0.099` = 충전독 본체 두께(46.8 − 36.9). **같은 충전기를 쓰면 그대로 쓴다.**
다른 충전기면 도킹 1회 후 `charger_pose` 로 재확인.

## 3. 도킹 실패 진단

### 도구
```powershell
python scripts\dock_log.py 192.168.30.110              # charge 이동 이력
python scripts\dock_log.py 192.168.30.110 --all        # 모든 이동
```
DB 충전소 좌표와 대조해 **몇 m 어긋났는지 계산**해준다.

### 왜 도구가 필요한가
- **백엔드 로그에는 실패 사유가 없다** — `[dock] 도킹 명령 전송` 까지만 남는다
- `GET /chassis/moves` 는 **목표 좌표를 안 준다** → `/chassis/moves/{id}` 로 재조회해야 한다

### 실제 사례 (2026-09-03)
```
4161 실패 → (-0.963, 0.360)  101 charge_dock_detection_error   ← 더 이전 맵 좌표
4165 실패 → ( 0.286, 5.034)  103 invalid_charge_dock           ← 맵 29의 C1
4172 성공 → ( 0.852, 5.430)                                    ← 맵 30의 C1
4153 실패 → 506 jack_in_up_state                               ← 랙을 든 채 도킹 시도
```
**맵을 새로 만들 때마다 POI id·좌표가 바뀌는데 로봇이 옛 좌표로 시도**해서 실패했다.

### 실패 코드 읽는 법
| 코드 | 뜻 | 원인 |
|---|---|---|
| `101` | 그 자리엔 갔는데 **센서가 독을 못 봄** | 각도 틀림 / 너무 멂 / 반사판 가림·오염 |
| `103` | **그 좌표에 등록된 독이 없음** | POI 좌표가 실제와 다름 (맵 갱신 후 단골) |
| `100` | 재시도 초과 | 위 둘이 반복됨 |
| `506` | 잭이 올라간 상태 | **랙을 든 채로는 도킹 불가** |

## 4. 맵 blocking (LGIT 요청 3번) — ⚠ 2026-09-03 작성, 아래 "확인 필요"는 §8 에서 해결됨

### 사양 (`overlays.md`)
| 종류 | 형태 | 동작 |
|---|---|---|
| **Virtual wall** | `LineString`, `lineType:"2"` | 가로지르지 못하게 막음. *"전역 경로 계산을 유도(guide)하는 데 자주 쓴다"* |
| **Virtual region** | `Polygon`, `regionType:"1"` | 더 강력. **들어가면 어느 방향으로도 못 움직임** |
| **Free space** | `Polygon`, `regionType:"12"` | 반대로 뚫어줌. 맵 생성 후 잡장애물 제거용 |
| **LiDAR Deceitful Area** | `Polygon` | 라이다 오인식 구역 |

LG 요구("지정 통로 1.2m 외 전부 blocking")에 그대로 대응 —
통로 양옆을 **virtual wall**, 완전 금지 구역은 **virtual region**.

### ★ 우리 코드에 이미 구현돼 있다 — 이름이 `firewall`
`virtual` 이 아니라 **`firewall`** 로 되어 있어 검색에서 놓치기 쉽다.

```
models/map.py        MapPolygon.shape_type == "firewall" / MapLine.line_type == "firewall"
crud/map.py:526      get_firewall_lines()
routers/map.py      _build_firewall_overlay_features()  → overlay LineString  (2026-09-04 이후 lineType="2")
routers/map.py       sync 시 로봇 전송 + 기존 가상벽 보존
frontend             맵 편집기 "가상벽" 도구(2026-09-04 폴리라인·통로모드로 개편), MonitoringMapCanvas 에 렌더링
```

**→ 요청 3번은 신규 개발이 아니라 기존 기능 검증·보완** — 이 판단은 맞았다.

**"확인 필요"였던 것 — 해결됨.** 아래 원래 있던 의문은 §8 에서 실기로 확인했다:
코드는 `type="1"` 을 썼는데(규격에 없는 값) 문서·SDK·로봇 실탑재 코드 전부 LineString 은
`lineType` 만 읽었다. `lineType:"2"` 로 고치고 rb-admin 색상(청록→빨강)으로 실증했다 — §8 참조.

### ★ 회피 금지 = `detour_tolerance: 0`
`moves.md` 에 **"Follow Given Route Strictly"** 항목이 별도로 있다:

> When `route_coordinates` is provided and `detour_tolerance=0`, the robot follows the route
> as closely as possible and **does not attempt to evade obstacles (it will only stop in front of them).**

LG 요구("사람이 접근하면 회피하지 않고 정지 후 직진만, 턴도 지정 경로 안에서")와 **글자 그대로 일치.**

```json
{ "type": "along_given_route",
  "route_coordinates": "x1,y1,x2,y2,...",
  "detour_tolerance": 0 }
```

## 5. 안전거리 (YELLOW/RED ZONE 관련) — ⚠ 2026-09-03 조사 시점 값. **최신 확정값은 §7, 적용 이력은 §11**

### `robot.footprint_expansion` — 이것이 정지 여유 거리
`GET /system/settings/schema` 에서 확인한 정의:
```
robot.footprint_expansion
  description  Additional expansion of robot footprint, unit: meter
  type number,  default 0.0
```
조사 당시(09-03) 현재값은 `0.0`(여유 없음)이었다.
**2026-09-04 에 `0.10` 으로 실제 적용 완료 — §11 참조.** (아래 예시의 `0.3` 은 조사 당시 예시값일 뿐,
최종 채택값이 아니다. §10 계산 결과 0.3 은 랙 든 상태로 1.4m 통로도 못 지나 폐기됐다.)

**미터 단위로 로봇 풋프린트를 부풀린다.** 로봇은 자기 풋프린트가 장애물에 닿으면 멈추므로
이 값이 곧 정지 여유다.

```bash
curl http://<ip>:8090/system/settings/user                        # 조회
curl -X PATCH -H "Content-Type: application/json" \
     -d '{"robot.footprint_expansion": 0.10}' \
     http://<ip>:8090/system/settings/user                        # 변경 (§11 에 실제 적용된 값)
```
**rb-admin 화면도 같은 API를 쓴다.**

⚠ `user` 설정은 로봇에 영구 저장된다. **맵 동기화(POI 동기화) 는 이 값을 건드리지 않는다** —
동기화가 PATCH 하는 건 overlay 와 `rack.specs` 뿐이라 확인 결과 무관했다.

### 함께 볼 설정
```
robot.make_the_robot_circular   현재 False
  "Treat the robot as circular for motion planning.
   This provides safer obstacle clearance
   but may prevent navigation through narrow passages."
```
로봇을 원형으로 취급해 더 안전하지만 **좁은 통로를 못 지난다.** LG 통로 1.2m / 로봇 폭 0.46m
라 여유는 있으나 회전 반경 기준이 되므로 신중해야 한다.

### 그 외 설정값 (S300 실측, 09-03 조사 시점 — `max_forward_velocity` 는 09-04 에 0.7 로 실제 하향됨)
```
control.max_forward_velocity        1.2 → 0.7 (2026-09-04 적용 완료, §11)
control.max_forward_decel          -2.0
control.remote_mode.max_forward_velocity  0.8
bump_based_speed_limit.enable       True     bump_tolerance 0.5
weight_based_speed_limit.enable     True     min_linear 0.4 / min_angular 0.4
position_quality_based_speed_limit  False
navigation.track_smoother.smooth_radius   0.45
safety.ignore_objects_under_rack    True
```

### ★ 사람/물체 구분은 불가
`/vision_detected_objects` 에 `person=1` 라벨이 있으나 **Experimental** 이고
S300은 `supportsVisionBasedDetector: false` → **미지원.**

**사람이든 상자든 라이다에 잡히면 동일하게 "장애물"이다.** LG 요구("사람이 오면 무조건 정지")는
"무엇이든 앞에 있으면 멈춤"으로 구현된다. 결과는 같지만 LG 설명 시 이 차이는 짚어야 한다.

## 6. 관련 함정 (재발 방지)

### 맵을 새로 만들면 충전소 설정이 끊긴다
- `charging_id` 는 FK `ON DELETE SET NULL` 이라 **`NULL` 이 된다** → 복귀가 조용히 멈춤
  (`[delivery] 충전소 POI 없음 — robot=N`)
- `standby_id` 는 **옛 값이 그대로 남는다** → 엉뚱한 맵의 좌표를 가리킴
- 충전소 좌표도 바뀌므로 **도킹이 옛 좌표로 시도돼 실패**

→ **맵 갱신 후 체크리스트**
1. 관제 로봇 상세에서 충전소·랙 위치 다시 지정
2. 맵 동기화 (충전독 overlay 갱신)
3. `python scripts\dock_log.py <ip>` 로 좌표 일치 확인

### 원격 모드에 갇히면 자동 명령이 전부 취소된다
```
isRemoteMode: True → move ... cancelled
```
콘솔 원격제어 모달은 **[✕]로 닫을 때** 자동 모드로 되돌린다. 모달을 안 닫거나
페이지가 죽으면 로봇이 원격 모드로 남아 배차·복귀가 전부 무시된다.

복구: `POST /api/robots/remote/control-mode/{ip}` body `{"mode":"auto"}`

### 백엔드를 재시작하면 콘솔·태블릿도 새로고침
서버가 죽은 동안 화면의 폴링이 멈춰 껍데기만 남는다. 버튼은 눌리는데 요청이 안 나가고
"저장 실패"만 뜬다. **F5 하면 즉시 정상화.**

## 7. Yellow / Red Zone 설계 확정 (2026-09-04, 최종 갱신)

LGIT 요청 4번. **로직 본체 구현은 2026-09-08(월) 예정.**
로봇 설정 2개(`footprint_expansion`, 주행속도)는 **2026-09-04 실제 적용 완료** — §11 참조.

### 왜 로봇 설정만으로는 안 되는가

`robot.footprint_expansion` 은 **사방으로 균일하게** 부푼다. 전방 1.0m 를 얻으려고 1.0 을 주면
외곽이 `0.46 + 1.0×2 = 2.46m` 가 되어 **통로에 진입 자체가 불가**해진다.
→ **전방(Yellow/Red)은 서버가 라이다로 직접 판정해야 한다.**

### ★ 통로 폭 재확정 — 1.2m → 1.4m 권장 (§10 참조)

L-150 실사양(740×500×1240mm) 확보 후 재계산한 결과, **랙을 든 상태로 코너를 돌려면 1.2m 는
여유가 5cm 뿐이라 위험하고 1.4m 를 권장한다.** 아래 수치는 이 결론에 맞춰 갱신했다.

```
로봇+랙 결합 크기(§10)   0.88m(좌우) × 0.74m(앞뒤)
좌우 물리 여유 상한       (1.4 − 0.88) / 2 = 0.26m   ← 직진 기준
                          회전(코너)까지 고려하면 0.15m 선이 안전
```

### 역할 분담 (최종)

| 방향 | 값 | 담당 | 수단 |
|---|---|---|---|
| 전방 | Yellow **3.0m** 감속 / Red **1.0m** 정지 | **서버** | 라이다 포인트 밴드 판정 |
| 좌우(판정 밴드 반폭) | **0.6m** (통로 반폭. 실제 벽 없는 가상벽 구간 기준) | 서버 | 통로 밖은 무시 — §9 참조, 물리 벽이 있는 구간은 0.45 로 낮출 것 |
| 좌우(근거리 하한) | **0.45m** | 서버 | 이 안쪽은 판정 안 함 — 자기가 든 랙을 장애물로 오인 방지 |
| 좌우(물리 여유) | **0.10~0.15m** | **로봇** | `robot.footprint_expansion`. 2026-09-04 **0.10 적용 완료**(실측 검증) |

**측면 안전거리는 통로 폭에 종속된다.** 1.4m 통로·LG 랙(0.88) 기준 물리 여유 상한은 **0.26m**(직진)이며,
회전 여유까지 감안해 **0.10~0.15m** 를 쓴다. LG 회신에 명시할 것:
*"통행 폭 1,400mm(회전 구간 포함) 기준 측면 여유는 최대 260mm이며, 전방 1,000mm 와 같은 값을
측면에 그대로 적용할 수 없다."*

### ★ 판정 밴드는 "벽 필터"가 아니라 "통로 밖 무시" 용도 (2026-09-04 재확인)

가상벽으로 만든 통로는 **넓은 매핑 구역 안에 선만 그은 것** — 통로 밖에 물리적 벽이 없다.
그래서 밴드를 좁히는 원래 근거("물리 벽을 걸러낸다")는 성립하지 않는다.
그런데 밴드를 없애면 **통로 밖의 실제 작업자·지게차까지 전부 감지 대상**이 되어 오작동한다
(로봇은 가상벽 때문에 못 나가는데 감속·정지만 계속 발생).
→ **밴드는 유지하되 통로 폭과 같게(0.6m)** 잡는 것이 맞다. 물리 벽이 있는 구간에서만 0.45 로 낮춘다.

### 판정 영역은 부채꼴이 아니라 직사각형 밴드

부채꼴로 하면 멀어질수록 좌우로 벌어져 통로 벽(또는 밴드 경계)이 계속 잡히고 **로봇이 내내 감속**한다.

```
로봇 기준 좌표에서
  0.45 < x ≤ 3.0m   AND   |y| ≤ 0.6m   → Yellow(감속)
  0.45 < x ≤ 1.0m   AND   |y| ≤ 0.6m   → Red(정지)
```
`x` 하한 0.45 는 자기가 든 랙(중심 기준 ±0.30, §10)을 걸러내기 위함.
`y` 반폭 0.6 은 통로 폭에 종속 — 통로가 바뀌면 같이 조정한다.

### 숫자 근거 (실측 기반)

```
정지거리 = (라이다 주기 + 명령 지연) × v + v²/(2a)
         = (0.53 + 0.15) × 0.7 + 0.49/(2×2.0)
         = 0.49 + 0.12 = 0.61m       → Red 1.0m 이면 여유 0.39m
```
| 실측 항목 | 값 | 출처 |
|---|---|---|
| `/scan_matched_points2` | **1.86 Hz (0.53초)** | 2026-09-04 단독 구독 실측 |
| `control.max_forward_decel` | -2.0 m/s² | settings schema |
| 주행 속도 | **0.7 m/s** — 2026-09-04 로봇에 실제 적용 완료 | `control.max_forward_velocity` |

**라이다 주기는 못 올린다** — `/horizontal_laser_2d/matched` 0.77Hz, `/maps/1cm/1hz` 1.0Hz 로
`/scan_matched_points2` 가 가장 빠르다. 단독 구독해도 동일하므로 대역폭 경합이 아니라 전송 제한.
주기 조절 설정은 문서·스키마 어디에도 없다.
→ **정지거리의 80%(0.49m)가 이 지연이다.** 더 짧은 Red 는 불가.
※ 로봇 자체 정지(`footprint_expansion`)는 이 지연과 무관하다. 느린 건 서버 판정 경로뿐이다.

### 설정 외부화 (월요일 작업 — 아직 파일 미생성)

음성과 같은 방식 — `BackEnd/static/system_settings.json`. **DB 마이그레이션 불필요,
현장에서 파일만 고치고 서버 재시작하면 반영된다.**

```json
"safety_zone": {
  "enabled": true,
  "warn_distance_m": 3.0,
  "stop_distance_m": 1.0,
  "band_half_width_m": 0.6,
  "band_min_distance_m": 0.45,
  "normal_speed_mps": 0.7,
  "warn_speed_mps": 0.3,
  "resume_delay_sec": 3.0,
  "static_alert_sec": 60.0
}
```
`resume_delay_sec` / `static_alert_sec` 이 LGIT 요청의 **"동적이면 3초 뒤 출발 / 정적이면 1분 뒤 알림"** 을
담당한다. 로봇은 동적·정적을 구분하지 못하므로 **지속 시간으로 사후 판정**한다.

로봇 쪽 설정은 이미 적용됨(§11): `PATCH /system/settings/user {"robot.footprint_expansion": 0.10}`

### 미검증 — `scripts/safety_probe.py` (아직 미작성)로 확인할 것

위 정지거리는 **계산값**이다. 실측 도구가 아직 없다.
`footprint_expansion` 을 바꿔가며 장애물 앞 실제 정지 위치를 라이다+포즈로 기록해
"0.10 설정에서 실제 몇 cm 에 서는가"를 수치로 뽑아야 LG 에 자신 있게 낼 수 있다.

### 이건 안전 인증이 아니다

ISO 3691-4 는 보호영역을 **IEC 61496-3 인증 안전 라이다 + PL d(ISO 13849-1 Cat.3)** 로 요구한다.
우리 라이다는 항법용(bluesea50c)이고 REST/SDK 어디에도 안전존(OSSD) API 가 없다.
→ **소프트웨어 기반 보조 정지**임을 LG 회신에 명시할 것.
참고로 업계 통상값은 경고영역 4~8m / 보호영역 1~3m 로, LG 요청값(1.5m/0.5m)보다 오히려 크다.

## 8. 가상벽(맵 blocking) 실증 — 요청 3번 (2026-09-04)

### 원인 — overlay 속성 체계가 도형마다 다르다

| geometry | 읽는 키 |
|---|---|
| Point | `properties.type` (9 충전소 / 36 도킹점 / 34 랙점) |
| **LineString** | **`properties.lineType`** (2=virtualWall, 1=virtualTrack — 뜻이 다름) |
| Polygon | `properties.regionType` |

우리 코드는 LineString 에 `properties.type="1"` 을 넣고 있었다 — **규격에 없는 값**이라 로봇이 무시.
근거 3중 확인: 규격 문서 `overlays.html` / 벤더 SDK `mapInfo.ts` / **로봇 실제 탑재 rb-admin 번들
직접 분석**(`parsePolyline`은 `lineType`만 읽고, 렌더 색상은 `virtualWall(2)`일 때만 빨강).

**실기 검증**: `type:"1"` → rb-admin 청록색(미분류) / `lineType:"2"` → **빨간색(가상벽 인식)**.

### ★ PATCH 만으로는 로봇에 반영되지 않는다

```
PATCH 후   GET /maps/2   → overlays_version 217 (저장본, 최신)
           WS /map/info  → overlays_version 216 (로봇이 실제 쓰는 것, 옛것)
```
`PATCH /maps/{id}` 는 맵 레코드만 고친다. `POST /chassis/current-map` 으로 재선택해야
로봇이 다시 읽는다(포즈 저장/복원 필요 — `_reselect_current_map_keep_pose()`).

### 코드 수정 (`BackEnd/app/routers/map.py`)

- `_build_firewall_overlay_features()`: `"type":"1"` → `"lineType":"2"`
- 신규 `_is_firewall_feature()`: 가상벽 판정을 `LineString + lineType` 기준으로. 레거시 `type=="1"` 도
  같이 잡아 교체(재전송 시 중복 누적 방지)
- `_sync_patch_to_robot()`: `_reselect_current_map_keep_pose()` 호출 추가(리로드 누락 보완)

### 검증 도구

```powershell
python scripts/wall_probe.py show      # 로봇 overlay 덤프 (저장본/라이브 비교)
python scripts/wall_probe.py fix       # 레거시 type:"1" → lineType:"2" 일괄 교정
python scripts/wall_probe.py reload    # current-map 재선택 (포즈 보존)
python scripts/wall_probe.py clear     # 로봇 overlay 에서 가상벽만 제거
python scripts/wall_probe.py restore <백업파일>
```

### 아직 안 한 것 — 실제 차단 검증

지금까지는 "로봇이 형식을 인식한다"(색 확인)까지만 했다. **경로계획을 실제로 막는지**는
아직 미검증이다. 방법: 통로를 **최단 직선에서 벗어나게**(ㄱ자) 그린 뒤 통로 끝으로 이동 명령 —
`fail_reason` 9(길 미연결)/5/6/8 이 나오면 성공, 무시하고 직선으로 질러가면 실패.
직선 통로로 테스트하면 벽 유무와 무관하게 같은 경로가 나와 판정이 안 된다.

## 9. 맵 동기화 결함 2건 + 버튼 분리 (2026-09-04)

가상벽을 고쳐도 동기화하면 사라지는 현상의 원인.

### 결함 ① 재시작 후 복구가 작업위치(type 34)만 했다

```
17:21:48  [sync:full] 서비스 재시작 요청 완료 (60-90초)
17:21:51  [sync-overlays] overlay PATCH "완료"     ← 3초 뒤. 재시작 중이라 무효
```
재시작 후 90초 뒤 도는 복구 스레드가 **type 34(Shelves Point)만** 재적용하고 있었다.
충전소·가상벽은 복구 대상이 아니라서 재시작 직후 로봇이 제 맵을 다시 읽을 때 사라졌다.
실측: `overlays_version` 이 218 → **216 으로 롤백**.
→ **overlay 전체**(충전소+가상벽+Shelves Point) 재적용으로 수정. 고정 `sleep(90)` 대신
`/device/info` 가 응답할 때까지 폴링(최대 180초)한 뒤 적용.

### 결함 ② `effective_robot_map_id` UnboundLocalError

대입(1384줄)이 사용처(1250줄)보다 뒤에 있어 `try` 블록이 항상 실패 →
"로봇 기존 오버레이 보존" 로직이 **한 번도 동작한 적이 없었다**(로그의 `기타=0` 이 증거).
대입을 사용처 앞으로 이동.

### 동기화 버튼 분리 — 맵 동기화 / POI 동기화

기존엔 버튼 하나가 항상 `method:"full"`(맵 전체 PUT + 로봇 재시작)을 했다. 백엔드에 overlay 전용
경로(`sync-overlays`)가 이미 있었는데 프론트가 그 값을 안 보내 쓸 방법이 없었다.

| 버튼(상단 툴바) | 하는 일 | 소요 |
|---|---|---|
| **POI 동기화** | 충전소·작업위치·**가상벽** | 수 초 |
| **맵 동기화** | SLAM 맵 자체 교체 + 재시작 | 60~90초 |

**가상벽만 고칠 때는 POI 동기화를 쓴다.** 90초 → 수 초.

## 10. 랙 규격 오설정 + L-150 통로 폭 (2026-09-04)

### rack.specs 가 S300 으로 잘못 나가고 있었다

맵 POI 의 `rack_size` 미지정 시 폴백이 `S300` 이라, LG 랙(0.70/leg 0.05 round)인데
로봇엔 **S300 규격(0.765/leg 0.04)** 이 들어가 있었다 — 랙 인식 실패 원인.

### LG margin 0.05 → 0.09

LG 랙 실물 최대 폭 **870mm 실측**(캐스터 바깥 회전 상태). 기존 margin 0.05 는 풋프린트를
0.80m 로 봐서 7cm 부족 → 캐스터가 랙 밖으로 튀어나와 장애물로 잡힘(LG2 와 동일 문제).
`(0.87-0.70)/2=0.085` → 0.09. `width/depth`(다리 중심 간격)는 그대로, 실물과의 차이는 margin 으로.

→ 랙 든 실효 폭 **1.15m → 1.08m** 개선. 맵 POI 를 `rack_size=LG` 로 지정 후 POI 동기화 완료.

### footprint_expansion 이 0인데 왜 랙 들고 잘 피했나

- `0` = "회피 안 함"이 아니라 "추가 여유 0". 로봇은 자기 외곽이 안 닿게 정상 회피한다.
- 랙을 들면 footprint 가 **자동으로 랙 크기까지 커진다**(`supportsDynamicFootprints: true`, 문서 근거 —
  실기 미확인, §7 다음 확인 목록 참조).
- 게다가 S300 규격(0.95)이 실제 LG 랙(0.88)보다 커서 **실제보다 크게 잡고 다녔다** — 그래서 여유 있게 피함.

**`footprint_expansion` 으로 랙 크기를 덮으면 안 된다.** 랙 크기는 `rack.specs` 담당, expansion 은
그 위에 얹는 여유일 뿐. 0.3 을 주면 `0.88+0.6=1.48m` 라 1.4m 통로도 못 지난다.

### L-150 제원 확보 → 통로 1.4m 권장

제품 사양표: **740×500×1240mm**, Minimum Passage Width 70cm(= 폭 0.50+여유 0.20, expansion 0.10과 일치).

```
L-150 폭 0.50 길이 0.74   LG랙 실물 폭 0.88 깊이 0.68
결합 크기 폭 0.88 길이 0.74   ← 좌우만 커진다(로봇이 앞뒤는 더 김)
외접원 반경 0.575 → 제자리 회전 지름 1.150m
```
| 통로 | 직진(e=0.10) | 코너 회전 | 제자리 회전 |
|---|---|---|---|
| 1.2m | OK | 여유 5cm | 불가 |
| **1.4m** | OK | **여유 25cm** | OK |

**코너가 있으면 1.4m 권장** — `smooth_radius 0.45` 로 호를 그리며 돌아 계산보다 더 필요하다.
코너 내접원 공식 `r ≤ 0.586×W`(교차부가 통로보다 넓어 제자리 회전보다 유리).

### 맵 편집기 마커도 실제 규격으로 수정

작업위치 마커가 S600(0.83×0.87) 하드코딩이었다 → POI 의 `rackSize` 기반 실제 결합 크기로 변경.
`frontend/lib/constants/footprint.ts` 신설. **백엔드 `rack_specs.py` 와 값이 같아야 하니 랙 규격
바꿀 때 두 파일 다 고칠 것.**

## 12. ★ `footprint_expansion` 0.10 철회 (2026-09-07)

**§11 에서 넣은 0.10 을 0.0(기본값)으로 되돌렸다.** 좁은 지점 테스트를 안 하고 넣은 값이었다.

`footprint_expansion` 은 **사방으로 균일하게** 부풀린다 — 폭 +0.20 m, **외접원 반경 +0.115 m**.
2026-09-07 에 막힌 지점이 전부 그 10 cm 대에 걸려 있었다.

| 실패 지점 | 실제 여유 | 필요(exp 0.1) | 필요(exp 0) |
|---|---|---|---|
| 충전소 출발 | 0.639 m | 0.519 → **12 cm** | 0.404 → 23.5 cm |
| W7 (랙 적재) | 0.630 m | 0.671 → **−4 cm** ❌ | 0.556 → +7.4 cm |
| 충전소 탈출로 | 0.631 m | 0.519 → **11 cm** | 0.404 → 22.7 cm |
| J1 랙 밑 이탈 | 0.415 m(반폭) | 0.330 → **8.5 cm** | 0.230 → 18.5 cm |

```
robot.footprint_expansion  0.10 → 0.0
실측: expanded_footprint 폭 0.660 → 0.460,  외접원 0.519 → 0.404
```

**`0` 은 "회피를 끈다"는 뜻이 아니다.** 로봇은 여전히 자기 외곽이 안 닿게 정상 회피한다.
`expansion` 은 그 **위에 더 얹는 여유**일 뿐이다.

> 잃은 안전 여유는 아래 §13(Yellow/Red)이 **동적으로** 메운다.
> 상시 몸집을 키우는 것과 달리 앞에 뭔가 있을 때만 반응하므로 통로를 못 지나가는 부작용이 없다.

## 13. Yellow / Red 안전거리 — 구현 (2026-09-07)

설계는 §7 에 있다. 여기는 **구현과 실기에서 드러난 함정**을 적는다.
`app/services/safety_zone.py` · 설정 `GET·PATCH /api/settings/safety` ·
UI 는 배차 콘솔 원격제어 모달(APK 재빌드 불필요).

### 13-1. ★ 데이터 주기가 가정과 완전히 달랐다

**이게 "추가하고 나서 생긴 문제" 대부분의 뿌리다.** 2026-09-07 실측:

```
/tracked_pose          1.02 Hz   ← 초당 1회. 0.7 m/s 면 1초에 70 cm 이동
/scan_matched_points2  1.73 Hz   (stamp 있음, 맵 좌표)
/planning_state        0.08 Hz   ← 12초에 1건
/robot_model           0.08 Hz   ← 12초에 1건
```

| 증상 | 원인 |
|---|---|
| **"아무것도 없는데 0.4 m 앞 정지"** | 낡은 포즈로 맵 좌표 스캔을 변환 → 이미 지나친 벽이 아직 앞에 있는 것으로 계산 |
| **"랙을 장애물로 인식"** | `/robot_model` 12초 지연 → 랙을 든 직후 옛 풋프린트(앞끝 0.379)를 써서 랙(0.475)이 무시범위 밖 |
| **랙 정렬이 계속 취소됨** | `/planning_state` 12초 지연 → 정밀 동작 예외가 제때 안 걸림 |

**대응**
- 포즈를 버리지 않고 **전진 속도로 외삽**한다(연속 포즈 델타를 헤딩에 투영). 한계 `POSE_MAX_AGE_SEC = 1.2`
  (처음 0.5 로 뒀더니 스캔 절반이 버려져 실효 지연 1.15초 → 정지거리 1.03 m > Red 1.0 m 가 됐다)
- 회전 중에는 헤딩이 바뀌어 외삽이 틀리므로 하지 않는다
- 이동 정보는 WS 대신 **REST `GET /chassis/moves/current` 를 1초 캐시**로 읽는다
- `SELF_CLEARANCE_M` 을 0.25 로 — 풋프린트가 12초 늦게 갱신돼도 `0.379+0.25=0.629 > 0.475` 라 자기 랙이 안 잡힌다

### 13-2. 정밀 동작 중에는 적용하지 않는다

```python
PRECISE_ACTIONS = {"align_with_rack", "charge", "to_unload_point"}
```

랙·충전독에 **일부러 다가가는** 동작이다. 그 대상을 장애물로 보면 동작이 끝나지 않는다.
`deadlock_monitor` 가 같은 이유로 이 동작들을 제외하는 것과 같은 취지.

문자열은 실기 확인했다 — `/planning_state.action_type` 이 이동 `type` 을 그대로 쓴다
(`align_with_rack` 32건 / `along_given_route` 12건 / `standard` 11건 / `charge` 5건 관측).

### 13-3. ★ 정지는 '속도 0' 으로. 이동을 취소하면 안 된다

처음엔 RED 에서 `jack_service.pause_robot_job()` 을 썼는데 이건 **진행 중인 이동을 취소**한다.
그러면 `safe_move` 가 재시도하면서 처음 만든 `route_coordinates` 를 그대로 다시 쓰는데,
그 사이 로봇은 앞으로 가 있다 → **경로 시작점으로 되돌아가려 해서 우회**가 생겼다.

```
Yellow → max_forward_velocity = slow_speed
Red    → max_forward_velocity = 0.0     ← 로봇이 0 을 받아주는 것 실기 확인
해제   → DB robots.max_speed 로 복구
```

이동 명령과 경로가 살아 있어 **장애물이 비키면 그 자리에서 이어서 간다.**

### 13-4. 채터링 · 코너 정지

- **히스테리시스 0.30 m** — 나갈 때는 들어올 때보다 멀어야 한다.
  없으면 `0.99 → 1.16 → 0.91` 처럼 임계값 근처에서 흔들릴 때 초 단위로 왕복한다(실측).
- **회전 중에는 RED 을 걸지 않는다** (`TURN_RATE_RAD_S = 0.25`, 서행까지만).
  코너를 돌 때 전방 밴드가 벽을 훑어 로봇이 아예 멈춰버렸다.
  회전에는 정지거리 개념이 안 맞는다 — 앞으로 나아가지 않기 때문이다.
- **(제거) RED 15초 쿨다운** — RED 이 이동을 취소하던 시절의 안전장치였다.
  지금은 영구 정지 위험이 없고, 오히려 **앞 0.14 m 인데 '서행' 으로 강등**돼 위험했다.

### 13-5. 밴드는 자기 몸 기준으로만 넓힌다

```python
near      = max(설정 near_min, 자기앞끝 + 0.25)
band_half = max(설정 band_half_w, 자기반폭)      # ← 여유를 더하지 않는다
far       = yellow + 자기앞끝 + 0.30
edge      = raw − 자기앞끝                       # 판정·표시는 앞끝 기준
```

- `band_half` 에 `+0.25` 를 더했더니 랙 적재 시 **0.725 m(좌우 1.45 m)** 가 되어
  1.4 m 통로에서 벽이 상시로 잡히고 코너에서 멈췄다. 하한만 자기 반폭으로 둔다.
- **옆·뒤에 거리 존을 두면 안 된다.** 실측: 좌 0.96 m / 우 1.20 m / 뒤 0.39 m —
  가만히 서 있어도 상시 걸린다. 옆·뒤 장애물은 **로봇 자체 회피**가 담당한다
  (랙을 들면 footprint 가 0.46→0.95 로 커져 그 몸으로 전방향 회피).
- **거리는 앞끝 기준**이다. 중심 기준이면 랙을 들었을 때 랙이 10 cm 앞으로 나온 만큼
  실제 여유가 줄어드는데 설정값은 그대로라 위험하다.

### 13-6. 설정

`static/system_settings.json` 의 `safety` 키 (DB 마이그레이션 불필요).

| 항목 | 기본 | 범위 |
|---|---|---|
| `enabled` | **false** | — |
| `yellow_m` | 3.0 | 0.5 ~ 10 |
| `red_m` | 1.0 | **0.7** ~ 5 |
| `slow_speed` | 0.3 | 0.1 ~ 1.2 |
| `band_half_w` | 0.6 | 0.2 ~ 2.0 |
| `near_min` | 0.45 | 0 ~ 1.0 |
| `clear_hold_sec` | 1.5 | 0 ~ 10 |

- `red_m` 하한 0.7 은 물리 한계다 — 0.7 m/s 정지거리가 0.61 m
- `red_m ≥ yellow_m` 이면 400 으로 거부
- `GET /api/settings/safety/status` 로 로봇별 현재 존 확인 (콘솔이 1초마다 폴링)

### 13-7. 다시 켤 때 순서

1. 작업 없이 **로봇 앞에 직접 서서** 정상→서행→정지 전환 확인
2. 한 사이클 돌리며 로그 확인 — 랙 정렬 진입 시 `[safety]` 무반응 / 랙 들고 주행 중 자기 랙 무시 / 랙 밑 이탈 시 무반응
3. 이상하면 콘솔에서 체크 해제 — 걸린 제약이 자동으로 풀린다

### 13-8. 남은 것

- **후진 밴드** — `backward_movement_behavior = "when_necessary"` 라 후진은 실제로 발생한다.
  후방 최근접이 0.39 m 로 가깝다. 별도 설정값으로, 앞보다 짧게(Yellow 1.5 / Red 0.7 정도).
- **회전 판정** — 제자리 회전 시 외접원(랙 적재 0.672 m) + 여유 안에 점이 있으면 정지.
  거리 존과는 별개 로직.
- 둘 다 **전방이 안정된 뒤**에 붙인다.

## 14. 작업지점 판정 제외 + 속도 재전송 (2026-09-07 저녁)

§13 을 붙인 뒤 코드를 다시 훑어보니, **켜면 작업이 멈출** 자리가 남아 있었다.
실기 재검증 전에 미리 막았다.

### 14-1. ★ 작업지점 주변에서는 판정하지 않는다

문제는 이거였다. 작업지점 주변에서 로봇이 하는 동작은 전부 **대상에 일부러
다가가거나 그 자리에서 빠져나오는** 동작인데, 이동 `type` 이 그냥 `standard` 라
`PRECISE_ACTIONS`(align/charge) 처럼 종류로 뺄 수가 없다.

| 동작 | 거리 | 코드 |
|---|---|---|
| 랙 밑에서 전진 이탈 | 1.05 m | `dispatch_service.RACK_ESCAPE_M` |
| 랙 인식 실패 후진 재시도 | 0.50 m | `jack_service.ALIGN_BACKOFF_M` |
| 랙 인식 실패 측면 우회 | 0.30 m | `jack_service.ALIGN_LATERAL_OFFSET_M` |

이걸 장애물로 보고 멈추면 **로봇이 랙 밑에 남거나** 정렬 복구가 통째로 막힌다.

→ **위치로 뺀다.** R/J·충전소·대기장소(`poi_type ∈ jack/standby/charging`) 반경
안에서는 존을 `SKIP` 으로 두고 아무 제약도 걸지 않는다.
**경유지(W1~Wn, `poi_type = waypoint`)는 제외 대상이 아니다** — 통로 한복판이라
거기서까지 끄면 기능 자체가 무의미하다.

#### 반경을 정하는 건 이탈 거리가 아니다

랙을 가지러 갈 때 **앞에 있는 게 바로 그 랙**이다. 반경이 이보다 작으면 로봇이
반경 밖에서 멈춰버려 **반경 안으로 들어오지도 못한다.** 이게 반경을 결정한다.

```
반경 = red_m + 로봇 앞끝(0.379) + 랙이 로봇 쪽으로 나온 길이 + 여유(0.05)
```

| 랙 | 앞쪽 돌출(반깊이+여유) | 필요 반경(red 1.0) |
|---|---|---|
| **LG** (현장) | 0.340 | 1.72 |
| **LG2** (현장) | 0.353 | 1.73 |
| **S300** (현재 테스트) | 0.475 | 1.85 |
| S600 (미사용) | 0.535 | 1.91 |

지금은 S300 으로 테스트 중이라 `RACK_FRONT_M = 0.475` → **반경 1.90 m**.
이탈 1.05 · 후진 0.5 · 측면 0.3 은 전부 이 안에 들어온다.

> **★ 현장 이관 시** — `safety_zone.RACK_FRONT_M` 을 **0.353(LG)** 으로 낮추면
> 반경이 자동으로 **1.78 m** 가 된다. **이 상수 하나만 고치면 되고** 다른 곳은
> 건드릴 필요가 없다.

경계에서 켜졌다 꺼졌다 하지 않도록 나갈 때는 `WORK_SKIP_HYST_M`(0.20 m)만큼
더 나가야 한다 — 진입 1.90 / 이탈 2.10.

#### 맞바꿈 — 알고 써야 한다

이 반경 안에서는 **작업자가 로봇 앞에 서 있어도 서행/정지가 걸리지 않는다.**
J 는 사람이 랙에서 물건을 빼는 자리라 사람이 있는 게 정상이다.
그 구간은 **로봇 자체 회피**가 담당한다(이 기능과 무관하게 항상 동작).
사람이 이동하는 **통로 구간에서는 서행/정지가 그대로 동작한다.**

#### 콘솔 표시

존을 4번째 상태 `skip` = **"작업지점(해제) · R1"**(회색)으로 표시한다.
이걸 "정상"으로 두면 감시 중인 줄 알고 "왜 안 멈추지"를 또 추적하게 된다.
어느 작업지점 때문에 껐는지 이름까지 같이 보여준다.

### 14-2. 걸어둔 속도를 주기적으로 다시 보낸다

전이할 때 한 번만 보내면 **"화면엔 정지, 실제로는 주행"** 이 되는 경로가 둘 있다.

| 경로 | 내용 |
|---|---|
| ① POST 실패 | `_set_speed` 가 실패를 warning 만 찍고 넘어갔다. 존은 RED 인데 로봇은 그대로 달린다 |
| ② 콘솔 속도 슬라이더 | `POST /api/robot/speed` 가 로봇에 직접 속도를 쓴다. RED 중에 만지면 그 속도로 즉시 출발하는데 safety 는 다시 안 쏜다 |

고친 것 두 가지:

- `_set_speed` 가 **성공 여부를 돌려준다.** 실패하면 **존을 바꾸지 않고** 다음 틱
  (약 0.6초)에 다시 시도한다 → 표시 상태와 실제 로봇 속도가 어긋나지 않는다
- YELLOW/RED 인 동안 `SPEED_REASSERT_SEC`(3초)마다 같은 값을 다시 보낸다(멱등)

### 14-3. 일부러 넣지 않은 것

- **RED 20초 지속 시 알람** — 필요는 한데 이번엔 보류(사용자 판단)
- **정지 상태에서 속도를 0 → 0.3 으로 완화** — 검토했다가 **철회.**
  존은 RED 인데 실제 속도는 0.3 이 되어 **표시와 실제가 어긋난다.**
  관제 화면에서 "정지 중"으로 보이는데 로봇은 움직일 수 있는 상태가 된다.
  정지는 진짜 정지여야 한다. 벽 앞에서 굳는 문제는 알람 + 사람 개입으로 푼다

### 14-4. 아직 확인 안 된 것 — 이것부터 볼 것

**`max_forward_velocity: 0` 이 원격 조종(twist)·후진·제자리 회전까지 막는가?**

- **막지 않는다면** → 사람이 원격으로 로봇을 뺄 수 있으므로 추가 작업 불필요
- **막는다면** → 벽 앞에서 RED 로 굳었을 때 사람이 할 수 있는 게
  「사용」 체크 해제뿐인데, 그건 **전 로봇 공통 설정**이라 다른 로봇 안전까지 꺼진다.
  → 원격 조종 중에는 그 로봇만 감시를 놓고 존을 `manual`("수동 조작 중")로
  표시하는 처리를 붙여야 한다

확인법: 로봇 앞에 서서 `정지` 를 만든 뒤 콘솔 원격 조종으로 전진/후진/회전을 눌러본다.

### 14-5. 반경 여유가 5 cm 다 — 실기에서 볼 것

S300 기준 계산이 딱 맞아떨어진다.

```
랙이 RED 를 유발하기 시작하는 거리 = 1.85 m
제외 반경                         = 1.90 m
여유                              = 0.05 m
```

**랙이 POI 보다 5 cm 이상 앞(로봇 쪽)에 놓여 있으면** RED 가 제외 반경 **밖에서**
걸려 로봇이 반경 안으로 못 들어온다. 실기에서 R 접근이 멈추면 이걸 의심할 것.
고치는 법은 한 줄 — `WORK_SKIP_MARGIN_M` 을 `0.05 → 0.15` (반경 2.00).

## 15. 현장 1차 테스트 반영 (2026-09-08)

서버 노트북에 적용하고 돌려보니 **벽 때문에 멈추는** 문제가 나왔다. 그 조치.

### 15-1. ★ 맵에 이미 있는 벽은 장애물로 보지 않는다

**증상** — 주행 중·회전 중에 **글로벌 맵에 그려진 벽면**을 보고 그냥 정지.

**원인** — 라이다는 벽도 똑같이 찍는다. 서버 안전거리에 "새로 생긴 것"과
"원래 있던 것"을 구분하는 로직이 아예 없었다.

**조치** — 맵(점유 격자 PNG)과 대조해 **이미 그려진 벽이면 건너뛴다.**
9/4 에 맵 편집기 벽 스냅용으로 만든 `map_image.snap_to_wall()` 을 그대로 쓴다.

```
밴드 안 점을 가까운 순으로 훑는다 (최대 12개)
  → 맵 벽에서 0.25m 안 → 알던 벽. 건너뛰고 다음 점
  → 아니면            → 새 장애물. 정상 판정
```

**★ 충돌 위험이 늘지 않는다 — 정지 장치가 둘이기 때문이다.**

| | 무엇 | 벽 처리 |
|---|---|---|
| ① 로봇 자체 회피·정지 | 자기 외곽 기준, **항상** 동작 | **그대로.** 벽에 안 부딪히게 하는 건 원래 이쪽 일 |
| ② 서버 안전거리 | 그보다 더 일찍·더 멀리서 줄이는 **보조** | ← 여기서만 벽을 뺀다 |

무시 범위는 **벽 표면에서 0.25 m 안쪽뿐**이다. 사람이 벽 앞에 서 있으면
(몸이 보통 벽에서 0.2~0.5 m 떨어진다) 그대로 잡힌다.

> `WALL_TOLERANCE_M` 은 **위치추정 오차를 흡수하는 값**이기도 하다.
> 맵과 실제가 어긋난 만큼 벽이 '새 장애물'로 보이므로, 오정지가 남으면 조금 키운다.
> 키울수록 벽 근처 물체를 놓치므로 무작정 키우면 안 된다.

### 15-2. 회전 중 RED 금지 규칙을 **제거**했다

원래 "회전 중이면 RED 대신 서행" 예외가 있었다. 코너에서 밴드가 **맵의 벽**을 훑어
멈추던 것을 막으려던 규칙이다.

**15-1 로 그 원인이 사라졌다.** 예외를 남겨두면 회전 중에 사람이 앞에 있어도
서행까지만 걸려 **오히려 위험하다.** → 제거. **회전 중에도 정지한다.**

(`TURN_RATE_RAD_S` 는 이제 포즈 외삽을 쉬는 기준으로만 쓴다.)

### 15-3. 동적 즉시 재출발 / 정적 20초 지속 알림 — **2026-09-08 LG 통화로 확정**

통화로 세 가지가 정해졌다. 그 전 문서(§7)의 "동적 3초 / 정적 60초 알림" 은 **폐기**한다.

| 항목 | 확정 |
|---|---|
| **회피** | **하지 않는다.** `detour_tolerance: 0` 유지 |
| **동적** | 장애물이 사라지면 **대기 없이 즉시 출발** (`clear_hold_sec` = **0**) |
| **정적** | 20초 이상 막혀 있으면 **태블릿에 알림창을 지속적으로** 띄운다 |

#### "지속적으로" 를 어떻게 구현했나

알림을 **상태로** 들고 있고, 화면이 그걸 폴링한다. 치우면 상태가 사라지고 배너도 없어진다.

```
safety_zone._alerts        정지 중인 로봇을 담아둔다 (메모리)
  → GET /api/dispatch/poi/{id}/status  의 safety_alerts   ← 위치별 태블릿(2초 폴링)
  → GET /api/settings/safety/alerts                        ← 콘솔(3초 폴링)
```

- **태블릿** : 화면 상단에 빨간 배너가 깜빡이며 **치울 때까지 계속** 떠 있다
- **콘솔** : 같은 내용을 상단 배너로
- **알람 이력**(`alarm_logs`) : 그대로 매번 쌓으면 목록이 도배되므로 **60초에 한 번만** 기록
- 배너는 정지가 풀리면 **자동으로 사라진다** (서버가 목록에서 빼므로)
- 연결이 끊기거나 기능을 꺼도 배너를 내린다 — 유령 배너가 남지 않게

#### `clear_hold_sec = 0` 의 부작용

깜빡임(점 하나에 정지↔해제 왕복) 방지가 이 값의 원래 역할이었다.
0 으로 두면 **히스테리시스(`HYSTERESIS_M` 0.30 m)만 남는다.**
경계에서 흔들리는 건 히스테리시스가 막지만, 완전히 사라졌다 나타나는 노이즈는 못 막는다.
실기에서 정지/출발이 덜컹거리면 **0.3~0.5 정도만 다시 주면 된다.**

### (폐기) 15-3 이전 안 — 동적 3초 / 정적 20초 1회 알림

LGIT 요청 원문은 **"동적이면 3초 뒤 출발 / 정적이면 알림"** 이다.
로봇은 동적·정적을 구분하지 못하므로 **지속 시간으로 사후 판정**한다.

| 상황 | 동작 | 값 |
|---|---|---|
| 장애물이 사라짐 | 3초 뒤 재출발 | `clear_hold_sec` 1.5 → **3.0** |
| 정지가 계속됨 | 관제에 알림 1회 | `STATIC_ALERT_SEC` = **20초** (요청 원문은 60초) |

알림은 `alarm_logs` 에 `error_code = SAFETY-STATIC` 으로 쌓인다. 모니터링 알람
목록에 그대로 뜬다. **로봇을 멈추지 않는다** — 이미 멈춰 있고 알리기만 한다.
장애물이 치워지면 자동으로 다시 출발하고, 알림은 정지가 풀릴 때까지 한 번만 낸다.

> `clear_hold_sec` 은 **서버에 이미 저장된 값이 있으면 기본값이 안 먹는다.**
> `static/system_settings.json` 의 `safety.clear_hold_sec` 을 직접 3.0 으로 고칠 것.

### 15-4. 회피는 넣지 않았다 (검토 후 보류)

"10초 뒤 회피" 안이 나왔으나 아래 이유로 2차로 미뤘다.

1. **LG 요청과 충돌** — "사람이 접근하면 회피하지 않고 정지 후 직진만" 이 원문이고
   `detour_tolerance: 0` 이 그 요구에 맞춘 설정이다
2. **회피하려면 서버 안전거리가 물러나야 한다** — 회피 명령을 내도 장애물은 앞에
   있으므로 다시 RED → 속도 0 → 무한 루프. 정지와 회피는 같은 순간에 공존 못 한다
3. **15-1·15-2 를 넣으면 회피가 필요한 상황이 얼마나 남는지 모른다** —
   15-3 의 알림 발생 횟수가 곧 그 계측기다. 그 숫자를 보고 결정한다

### 15-5. 회피 — LG 통화로 **최종 제외** (2026-09-08)

전화 통화에서 **"회피는 하지 않는다"** 로 확정됐다. `detour_tolerance: 0` 을 그대로 둔다.
막히면 정지하고, 20초 넘으면 사람을 부른다. 검토 과정은 15-4 참조.
