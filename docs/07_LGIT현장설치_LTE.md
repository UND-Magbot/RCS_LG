### ★ 방향성 실패의 재해석 — "로봇 라우터 인바운드 차단"설은 기각

`.12→.11` ping 성공이 증명하는 것은 단순히 "로봇이 나간다"가 아니다. **ping 은 왕복**이라,
성공 1회가 아래를 동시에 증명한다.

| 단계 | 증명되는 것 |
|---|---|
| `.12` 송신 | 로봇 라우터 아웃바운드 정상 |
| `.11` 수신 | `.11` 방향 인바운드 도달 정상 |
| `.11` 응답 | **서버 라우터는 외부 ICMP 에 응답하도록 열려 있다** |
| reply 가 `.12` 도착 | **`.11 → .12` 방향으로 패킷이 실제 전달된다** |

따라서 **"그 방향 전파가 죽었다"는 설명은 약하다.** RF 문제라면 같은 링크를 쓰는 양방향이
**둘 다 확률적으로** 깨져야 하는데, 한 방향 100% / 반대 0% 로 갈리는 것은 **방화벽·정책의
시그니처**다. 그리고 이번에 서버 쪽에서 `.12` 로 ping 이 들어갔으므로 **로봇 라우터가 인바운드
ICMP 에 응답한다는 것도 확인**됐다.

> `07:44` 의 *"로봇 라우터에 붙으면 정상 → 로봇·로봇 라우터 정상"* 판정은 **로봇 LAN 안쪽에서
> 한 테스트**라 로봇 라우터의 **WAN 인바운드는 검증 대상이 아니었다.** 그 판정을 근거로
> "구간 단절"로 좁힌 것은 논리 비약이었다.

### 유선(LAN) 운영으로 결정

서버 PC 는 자리가 고정이라 유선이 모든 면에서 유리 — 끊김 없음, IP 유지, AP isolation 무관.
로봇·태블릿은 이동하므로 무선 유지.

**유선 전환 시 주의**
1. Windows 는 **이더넷과 WiFi 가 별개 어댑터**라 IP 를 따로 받는다. 기존에 본 `.44` 는 WiFi 값일
   수 있으므로 **유선 연결 후 다시 실측**해야 한다
2. **WiFi 를 끈다** — 동시 연결이면 라우팅 메트릭이 꼬여 "됐다 안 됐다" 증상이 난다
3. 서버 PC 는 **고정 IP**. `PrefixOrigin` 이 `Manual` 인지 확인 (`Dhcp` 면 미적용)

### STEP 5. 포트포워딩 — **코드가 아니라 라우터 설정이다**

> **백엔드는 이미 `0.0.0.0:8002` 로 열려 있어 어디서 들어오든 받는다.**
> 문제는 라우터가 밖에서 온 요청을 안쪽으로 전달하지 않는다는 것이다.
> **코드 수정이 아니라 라우터 관리 페이지에서 규칙을 등록하는 작업이다.**

#### 로봇용 라우터 — 8090 (기존)

```
서버 → 로봇라우터 WAN IP : 8090
          └[포워딩]→ 로봇 192.168.211.100 : 8090
```
서버는 로봇의 **내부 IP 를 모른다.** 다른 라우터 안쪽이기 때문이다. 그래서 WAN IP 로 부른다.

#### 서버용 라우터 — 8002 (★ 신규)

```
태블릿 → 서버라우터 WAN IP : 8002
            └[포워딩]→ 서버PC 192.168.211.110 : 8002
```

**이전 구성에는 없던 규칙이다.** 태블릿이 서버 라우터 WiFi 에 붙는 전제였기 때문이다.
태블릿이 자체 LTE 로 나가면 **밖에서 들어오게 되므로** 이 규칙이 필요하다.

#### 등록할 규칙 — **TCP·ICMP 두 줄씩**

| 라우터 | IP 주소 | LAN | WAN | 프로토콜 | 용도 |
|---|---|---|---|---|---|
| **로봇용** | 로봇 IP | 8090 | 8090 | **TCP** | 서버가 로봇 제어 |
| 로봇용 | 로봇 IP | 8090 | 8090 | ICMP | ping 진단 (권장) |
| **서버용** | 서버PC IP | 8002 | 8002 | **TCP** | 태블릿이 콘솔 접속 |
| 서버용 | 서버PC IP | 8002 | 8002 | ICMP | ping 진단 (권장) |

**LAN 포트와 WAN 포트는 같은 번호를 넣는다.** 두 라우터에 각각 걸며, 한 라우터에 둘 다 거는 게 아니다.

PPT 의 22 / 40000 / 40001 · 7777 은 LG 기존 AMR 업체용이다. 우리가 쓸 게 아니다.
3000 포트는 정적 빌드(8002 통합)를 쓰므로 **불필요**.

#### TCP 와 ICMP 의 차이

| | 용도 | 없으면 |
|---|---|---|
| **TCP** | 실제 통신 — 배차·화면·로봇 제어 | **시스템이 안 돈다** |
| **ICMP** | `ping` 진단 | **시스템은 돈다.** `ping` 테스트만 안 됨 |

**TCP 만으로 시스템은 정상 동작한다.** 사무실(비 plte망)에서 TCP 만으로 됐다면 plte망에서도 같다 —
포트포워딩은 라우터 기능이라 망 종류와 무관하다.

**ICMP 는 등록해두는 편이 좋다.** 문제가 생겼을 때 `ping` 으로 어디서 끊겼는지 찾을 수 있어 진단이 쉬워진다.
2026-08-20 현장에서 ping 이 실패한 것도 ICMP 규칙이 없던 상태였다(§0-A).

#### 왜 서버 라우터에도 포워딩이 필요한가

포워딩이 필요한 조건은 하나다 — **라우터 안쪽 장비를 라우터 바깥에서 부를 때**.

```
서버 → 로봇   : 로봇이 남의 라우터 안에 있음  →  로봇용 라우터 8090
태블릿 → 서버 : 서버가 남의 라우터 안에 있음  →  서버용 라우터 8002
```

**서버 포워딩은 태블릿 때문이다.** 로봇 때문이 아니다 — 로봇은 서버에 먼저 연결하지 않고,
항상 서버가 로봇을 부른다.

| 태블릿 연결 방식 | 서버 라우터 8002 포워딩 |
|---|---|
| 자체 LTE (USIM) | **필요** |
| 로봇용 라우터 WiFi | **필요** |
| **서버용 라우터 WiFi** | **불필요** — 같은 LAN 이라 `192.168.x.110:8002` 직접 접속 |

> **태블릿 LTE 가 막혀 있으면** 콘솔 태블릿을 서버용 라우터 WiFi 에,
> 로봇 부착 태블릿을 로봇용 라우터 WiFi 에 붙이는 우회가 가능하다.
> 라우터가 로봇에 얹혀 같이 이동하므로 연결이 끊기지 않는다.

```
2) 고정 IP JSON 입력 (한 줄, 중괄호 필수, 직선따옴표만)
   {"ipv4.method":"manual","ipv4.address":"192.168.39.100/24","ipv4.gateway":"192.168.39.1","ipv4.dns":"192.168.39.1"}
3) ★ 저장된 WiFi 목록에서 사무실 s300 삭제
```

**3번을 빼먹으면 재부팅 때 사무실 망을 찾다가 연결이 끊긴다** (2026-08-13 사고 원인).
JSON 오타가 나면 **submit 전체가 막혀 WiFi 설정도 적용되지 않는다.**

> 로봇에 접속이 안 되면 → [02 §6-1 핫스팟 진입](02_네트워크.md) 참조. 고정 IP 를 잘못 줘도 복구된다.

**확인** : 라우터 LAN 안에서 `http://192.168.211.100:8090/chassis/status` 응답

### 4-3. DB 로봇 IP — ★ 가장 중요

```
관제 화면 → 로봇 관리 → 해당 로봇 → IP 수정
   192.168.30.100  →  <로봇 라우터의 WAN IP>     (예: 10.115.244.__)
```

⚠ **로봇의 내부 IP(`192.168.211.100`)를 넣으면 안 된다.**
서버는 다른 라우터 안쪽 주소를 모른다. 라우터 WAN IP 로 불러야 포워딩을 타고 들어간다.

화면으로 안 되면 SQL 로:

```sql
UPDATE robots SET ip_address='10.115.244.__' WHERE id=12;
```

**확인** : 관제에 로봇 **온라인** + 배터리 표시

### 4-8. 순서 (의존관계)

```
① 라우터 LAN·DHCP 설정        ← 먼저. 대역이 정해져야 나머지가 정해진다
② 서버 PC 고정 IP
③ 로봇 WiFi + 고정 IP
④ 포트포워딩 (로봇 8090 / 서버 8002)
⑤ 백엔드 기동 → DB 로봇 IP 를 라우터 WAN IP 로
⑥ 태블릿 서버주소
⑦ 방화벽 확인
```

**④를 ⑤보다 먼저** 해야 한다. 포워딩 없이 DB 만 고치면 "로봇 오프라인" 으로만 보여 원인을 찾기 어렵다.

### 4-9. 단계별 확인 명령 (복붙용)

```powershell
# 서버 PC 자기 IP
ipconfig

# 라우터까지
ping 192.168.211.1

# 로봇 라우터까지 (전용망 통신 판정)
ping <로봇라우터 WAN IP>

```

**각 명령이 실패하는 지점이 곧 원인 지점이다.** 위에서부터 순서대로 하면 어디서 끊겼는지 바로 나온다.

## 5. 현장 체크리스트 (인쇄용)

```
□ STEP 1  라우터 2대 APN/IMS/DHCP/WiFi 설정 → WAN IP 획득

□ STEP 3  재부팅 3회 → 고정 IP 유지
□ STEP 4  로봇 WiFi 변경 + 고정 IP + 옛 WiFi 삭제
□ STEP 5  포트포워딩  로봇 8090 / 서버 8002
□ STEP 6  서버 PC 유선 연결 + 고정 IP + 백엔드 기동
□ STEP 7  DB robots.ip_address = 로봇라우터 WAN IP
□ STEP 8  태블릿 APN + 서버주소
□ STEP 9  배차 전체 흐름
```

## 6. 막혔을 때

| 증상 | 확인 |
|---|---|
| WiFi 가 안 뜸 | `QCMAP_WIFION.html` 로 WiFi Enable (§2-2). 유선으로 관리페이지 접속 가능 |
| WAN IP 안 뜸 | APN 오타 / CTN 미등록 / 신호 없음 |
| 라우터 간 ping 실패 | 장비 간 격리 → 통신사 해제 요청 |
| 서버→로봇 8090 안 됨 | 로봇 라우터 포트포워딩 규칙 / 로봇 내부 IP 확인 |
| 태블릿에서 콘솔 안 뜸 | 서버 라우터 8002 포워딩 / 앱 서버주소 / 태블릿 APN |
| 관제에 로봇 오프라인 | DB IP 가 **WAN IP** 인지 (내부 IP 아님) |
| 로봇이 엉뚱한 망에 붙음 | 로봇 저장 WiFi 목록에서 옛 망 삭제 |
