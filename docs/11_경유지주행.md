# 11. 경유지 주행 — 로봇에게 경로 탐색을 맡기지 않는다

> **2026-09-07 구현 · 실기 동작 확인.** 랙 픽업 → J 배송 → 복귀까지 경유지 경로로 주행.
> 배경은 현대글로비스 RCS(`UND-Magbot/HyunDai-Project`) 의 Convoy 방식 참고.

## 1. 왜 만들었나

가상벽으로 통로를 만들어 로봇을 가두는 방식은 **통로가 조금만 좁아도 못 지나간다.**
2026-09-07 하루에만 같은 원인으로 세 번 멈췄다.

| 시점 | 상황 | 실측 |
|---|---|---|
| 아침 | 충전소에서 4.5 m 떨어진 R1 을 `align_with_rack` 으로 직접 | 경로 최소 여유 **0.212 m** (필요 0.519) |
| 낮 | 랙 적재로 로봇이 커짐 | W7 자리 여유 **0.630 m** (필요 0.671) |
| 오후 | 충전소 주변 가상벽 | 탈출로 최대 **0.631 m** (필요 0.519 + 플래너 마진) |

전부 `alert 1007 planningStuckInMoving` — **"갈 공간이 없다"** 였다.

경로를 직접 주면 탐색 실패라는 실패 모드 자체가 없어진다.

## 2. 이동 타입 — 우리가 쓰는 네 가지

`/chassis/moves` 는 `type` 만 다르고 전부 같은 API 다.

| 타입 | 하는 일 | 경로 지정 |
|---|---|---|
| `standard` | 목표까지. **길은 로봇이 알아서** | 불가 |
| `along_given_route` | 목표까지. **준 좌표열대로** | `route_coordinates` |
| `align_with_rack` | 목표까지 + 랙 다리를 라이다로 찾아 그 아래 정렬 | **불가 (아래 ★)** |
| `charge` | 충전독까지 가서 도킹 | 불가 |

### ★ `align_with_rack` 은 route_coordinates 를 받지 않는다

2026-09-07 실기 확인. `POST` 는 **201 로 받지만** 로봇이 저장한 이동 기록에
`route_coordinates` / `detour_tolerance` 필드가 **아예 없다**(조용히 무시).

```
저장된 키: charge_retry_count, creator, fail_reason, id, properties, rack_area_id,
          state, target_accuracy, target_ori, target_x, target_y, target_z,
          type, use_target_zone
```

그래서 **'경유지로 랙 근처까지 → 짧은 거리만 align' 2단 구조가 반드시 필요하다.**
다시 시도하지 말 것.

## 3. 경유지 = 맵의 `W1`, `W2` … POI

`app/services/waypoint_route.py`

- 이름이 `^W\d+$` 인 활성 POI 를 **번호순**으로 모은다. 번호 순서가 곧 통로 순서다.
- 맵 편집기에서 「포인트」로 찍으면 `POI_NAME_PREFIX.waypoint = "W"` 라 자동으로 W1, W2 … 가 된다.
- `C1-1`(충전소 접근점)은 정규식에 안 걸리므로 체인에서 제외된다.
- **로봇에 동기화하지 않는다.** 백엔드가 우리 DB(`MapPOI`)에서 직접 읽는다.

### `plan(area_id, 출발, 목표)` 가 하는 일

1. 출발점에 가장 가까운 W(i), 목표에 가장 가까운 W(j) 를 찾아 i~j 구간을 자른다 (역방향이면 뒤집기)
2. **이미 그 자리에 서 있는 앞쪽 경유지**는 버린다 (`ARRIVED_EPS 0.30`)
3. **목표에서 출발점보다 더 먼 앞쪽 경유지**도 버린다 — 뒤로 갔다 되돌아오는 낭비 방지
4. **목표와 같은 자리인 마지막 경유지**도 버린다 — 좌표 중복 방지
5. 남으면 `("along_given_route", {route_coordinates, detour_tolerance: 0})`
   하나도 안 남으면 **`("standard", {})` — 기존 동작 그대로**

> 경유지가 0개면 도입 전과 완전히 같게 동작한다. 점진 도입이 가능하다.

### ⚠ 번호가 순서다 — 중간 삽입 금지

중간에 경유지를 추가하려고 `W11` 로 이름 붙이면 **번호순 정렬 때문에 맨 뒤로 밀린다.**
2026-09-07 실측: `W10(17.2, 3.0) → W11(6.6, 0.6)` 로 **11 m 를 되돌아가고**,
그 직선이 가상벽을 관통해(최소 여유 0.005 m) 이동이 막혔다.

중간에 넣으려면 **뒤 번호를 다시 매겨야 한다.**

### `_approach_before_align()` — 랙 앞까지 데려다주는 단계

`align_with_rack` 은 경로 지정이 안 되므로, 먼 거리를 그것 하나로 시키면 못 간다.
랙 POI 에 가장 가까운 경유지를 **접근점**으로 삼아 거기까지 경유지 경로로 간 뒤 정렬한다.

```
[전] 충전소 ───── 4.5 m, align_with_rack 하나로 ─────→ R1     실패
[후] 충전소 ─① along_given_route(경유지) ─→ W2 ─② align_with_rack ─→ R1
                                          1.83 m
```

**★ 접근점 도착 방향은 접근점이 '진입축' 위에 있느냐로 갈린다** (2026-09-07 저녁 개정).

진입축 = 랙 POI 의 각도(`ori`)가 만드는 직선. 판정 허용치 `APPROACH_AXIS_TOL_RAD` = 45°.

| 접근점 위치 | 도착 방향 | 이유 |
|---|---|---|
| **진입축 위** | **랙 각도 `poi["ori"]`** | 랙 각도는 *랙 밑에 들어갔을 때의 최종 자세*다. 접근점에서 미리 그 자세면 접근점→랙이 **회전 없는 직선 이동**이 된다 |
| 축 밖 | 랙을 바라보는 쪽 | 랙 각도를 주면 접근점에서 크게 돌고 align 이 또 돌아 **제자리 회전 2회**. 실측: R1 214.9°, W2→R1 −15.5° → **130° 헛회전** |

```python
to_rack = math.atan2(poi["y"] - ap["y"], poi["x"] - ap["x"])
off = abs((to_rack - poi["ori"] + math.pi) % (2 * math.pi) - math.pi)
on_axis = min(off, math.pi - off) < APPROACH_AXIS_TOL_RAD   # 앞/뒤 둘 다 축 위
face = poi["ori"] if on_axis else to_rack
```

**접근점이 랙의 앞쪽이든 뒤쪽이든 도착 각도는 같다** — 이동 방향만 후진/전진으로 갈린다.
그래서 `min(off, π-off)` 로 양쪽을 다 축 위로 본다.

### 개정 경위 (2026-09-07 저녁 현장)

작업지점 앞 진입축 위에 경유지(W7·W8)를 찍었는데도, 로봇이 접근점에서 **랙을 쳐다본 뒤
다시 돌아** 진입 지점으로 가서 후진했다. 낮에 넣은 "랙을 바라보는 쪽" 규칙이 그 배치에서는
정반대로 작용한 것이다. 낮 규칙은 접근 경유지가 축 **밖**(W2, 90° 틀어짐)일 때 맞았다.

> **경유지의 `angle` 은 읽지 않는다.** `chain()` 은 이름·x·y 만 가져온다.
> 도착 방향은 **작업지점(R) 의 각도**에서 나오므로, 맵에서 경유지 각도를 맞출 필요가 없다.

로그로 어느 분기를 탔는지 남는다:

```
[route] R2 접근(W8) — 진입축 위(벗어남 3°) → 도착 방향 124.9° (랙 124.9°)
```

## 8. 미확인 / 남은 것

1. **`route_coordinates` 에 로봇 현재 위치를 넣을지** — 현대 프로젝트는 안 넣는다.
   `fail_reason 401` 이 실제로 나오면 넣는다.
2. **분기(갈림길) 미지원** — 지금은 `W1→W2→…→Wn` 한 줄 체인이다.
   현장이 구역A ↔ 구역B 일자 통로라 충분하다고 봤다.
   갈림길이 필요해지면 현대 방식(POI 를 선으로 잇는 그래프 + BFS)으로 확장해야 한다.
   참고: `HyunDai-Project/BackEnd/app/robot_api/route_utils.py`
3. **정지점 vs 통과점 분리** — 현대의 `_build_segments` 는 `stop_names` 에 든 POI 에서만
   정지하고 나머지는 좌표열로 통과시킨다. 우리는 이미 한 명령으로 통과하므로 같은 효과다.

## 9. 번호순 체인 → 자동 연결 그래프 (2026-09-08 개편)

### 왜 바꿨나

현장에서 "경유지를 W1 부터 찍으면 그 번호대로 무조건 지나가야 하는 구조" 라는 지적이 나왔다. 맞다.

| 예전 문제 | |
|---|---|
| 번호를 잘못 매기면 되돌아간다 | 실측: W10 → W11 로 **11 m 역주행** |
| 중간에 하나 넣으려면 | **뒤 번호를 전부 다시** 매겨야 한다 |
| 갈림길 | 표현 불가 |

### 바뀐 것 — 번호는 그냥 이름이다

경유지끼리 **가깝고 그 사이에 벽이 없으면** 자동으로 이어 그래프를 만들고,
출발 → 목표 최단경로를 뽑는다. 찍는 순서·번호와 무관하다.

```
노드 : 출발 · 목표 · 경유지 전부
간선 : 거리 안 + 벽 없음   (벽 검사는 맵 PNG 로)
경로 : 다익스트라 최단
```

| 상수 | 값 | 뜻 |
|---|---|---|
| `LINK_MAX_M` | 8.0 m | 경유지끼리 이어볼 최대 거리 |
| `START_LINK_MAX_M` | 15.0 m | 출발·목표에서 경유지로 붙을 최대 거리 |
| `DIRECT_MAX_M` | 3.0 m | 이 안이고 벽도 없으면 경유지를 안 쓴다 |
| `LOS_CLEAR_M` | 0.70 m | 1차 — 랙 적재 로봇 외접원(0.672)이 지나갈 폭 |
| `LOS_CLEAR_RELAXED_M` | 0.45 m | 2차 — 1차로 길이 없을 때만 |

**★ `DIRECT_MAX_M` 이 없으면 경유지가 영영 안 쓰인다.** 직선이 언제나 최단이라
출발–목표가 바로 이어져 버리기 때문이다. 가까울 때만 직접 가게 막아둔 것이다.

**★ 여유는 2단계다.** 0.70 m 로 길이 안 나오면 0.45 m 로 한 번 더 본다.
통로가 1.4 m 면 중앙선에서 벽까지 0.7 m 라 아슬아슬해서, 엄격한 값만 쓰면
길이 끊겨 `standard` 로 떨어지고 **예전 문제가 그대로 돌아온다.**
완화해서 잡으면 로그에 남는다 — 그게 뜨면 그 통로가 빠듯하다는 뜻이다.

### 폴백 3단계 — 어디서도 막지 않는다

```
경유지 0개              → standard (도입 전과 동일)
맵 이미지 없음          → 예전 번호순 방식 (벽을 못 보면 그래프가 의미를 잃는다)
그래프에서 경로 못 찾음 → standard + 경고 로그
```

두 번째가 중요하다. 벽을 못 보면 "직선이 항상 최단" 이 되어 경유지가 통째로
무시된다. 그럴 바엔 예전 동작이 낫다. **맵 이미지가 있어야 제대로 돈다.**

### 중간에 경유지를 추가해도 된다

이제 이름을 아무거나 붙여도 된다(`W\d+` 형식만 맞으면). 위치만 맞으면
그래프가 알아서 잇는다. **뒤 번호를 다시 매길 필요가 없다.**

### 아직 안 고친 것 — 모니터링 화면

관제 화면은 아직 **경유지를 번호순으로 이어 선으로** 그린다. 실제 경로와 다를 수
있다(그래프는 번호를 안 본다). 표시만의 문제이고 주행에는 영향이 없다.
다음 프론트 빌드 때 "선 없이 마커만" 으로 바꾸면 된다.

### 9-0. ★ 최종 확정 — 경유지는 '통로' 다. 전부 거쳐 간다 (2026-09-08 현장 확인)

앞서 "벽만 없으면 건너뛰어도 된다" 로 만들었는데 **틀렸다.**
경유지는 최적화 힌트가 아니라 **사용자가 "이 길로만 다녀라" 고 지정한 통로**다.

현장 배치 (ㄱ자):

```
J1 — R2 — W1 — W2 — W3 ┐
                        C1(충전소, 코너)
                        └ W4 — W5 — R1 — J2
```

요구되는 동작 — **번호 오름차순이 아니라 통로를 따라가는 순서**다(역순 포함).

| 상황 | 경로 |
|---|---|
| C1 에서 R2 호출 | C1 → **W3→W2→W1** → R2 → **W1→W2→W3→W4→W5** → J2 → **W5→W4** → C1 |
| C1 에서 R1 호출 | C1 → **W4→W5** → R1 → **W5→W4→W3→W2→W1** → J1 → **W1→W2→W3** → C1 |
| 복귀 중 W2 를 지난 지점에서 R2 예약 | 되짚어서 **W2→W1** → R2 |

#### 어떻게 만들었나

```
① 통로     : 정렬 순서로 **인접한 경유지끼리만** 잇는다 (W1—W2—W3—…)
             벽 검사를 하지 않는다. 사용자가 다니라고 찍은 길이므로 우리가 판단할 게 아니다
② 진입·이탈: 출발·목표는 **가장 가까운 경유지 2개**에만 붙는다 (ENTRY_CANDIDATES)
             어디로 들어가고 나올지는 최단경로가 정한다
③ 코앞    : 목표가 DIRECT_MAX_M(2.0m) 안이고 벽도 없으면 경유지를 안 거친다
```

#### ②가 왜 '2개' 인가 — 두 번 틀렸다

**모든 경유지에 붙이면** 직선이 항상 체인보다 짧아(삼각부등식) 목표 근처 경유지로
바로 점프한다. 실제로 그렇게 만들었더니 **경유지가 1개만** 나왔다.

**거리로 자르면**(예: 4 m 이내) 간격이 좁을 때 후보가 여럿 들어와서
**코너 경유지를 건너뛴다.** 실측 — 2 m 간격 15개 배치에서 `C1 → R2` 가
코너의 `W10` 을 빼고 `W9` 에 붙었다. 그 직선은 **코너를 가로질러 벽을 통과**한다.

→ **가장 가까운 2개**로 고정했다. 로봇은 보통 두 경유지 **사이**에 있으므로
  · 목표 쪽으로 가는 쪽을 최단경로가 고르고
  · 코너에 있으면 양쪽 갈래의 입구가 하나씩 후보가 된다 (C1 → W10 / W11)
  3개 이상으로 늘리면 다시 건너뛰기 시작한다.

`ENTRY_PENALTY`(1.2)는 진입·이탈 구간에 붙이는 가중치다. 거리가 비슷할 때
**체인을 타는 쪽을 선호**하게 만든다.

#### ★ 번호는 통로를 따라 **한 방향으로 연속**해서 매겨야 한다

연결 관계(누가 누구의 이웃인가)가 번호에서 나오기 때문이다.

```
올바름 :  W1 … W10 ┐            잘못됨 :  W10 … W1 ┐
          (J1 끝→코너) C1                  (J1끝←코너) C1
          W11 … W15 ┘                      W11 … W15 ┘
                                    → W10—W11 이 맵을 가로지르는 간선이 된다
```

**실측 — 잘못 매기면 이렇게 된다.**
C1 에서 양쪽으로 번호를 매긴 배치에서 `R2 → J2` 가 `W10→W11→…` 로 나왔다.
W10(J1 끝) 에서 W11(코너) 로 **20 m 를 직선으로 건너뛴다.** 그 사이 W9~W1 을
전부 무시하고 맵을 가로지른다.

> 중간 번호를 지우는 건 괜찮다. 정렬 목록에서 이웃끼리 다시 이어진다.
> 실측 — W5·W6 을 지워도 `… W8→W7→W4→W3 …` 로 체인이 유지됐다.

#### 검증 (2026-09-08)

사진 배치(5개)와 실제 규모(15개, J1 쪽 10 + J2 쪽 5) 두 가지로 15개 시나리오 확인.

| 상황 | 5개 배치 | 15개 배치 |
|---|---|---|
| C1 → R2 | `W3→W2→W1` | `W10→W9→…→W1` |
| C1 → R1 | `W4→W5` | `W11→W12→…→W15` |
| J2 → C1 | `W5→W4` | `W15→W14→W13→W12→W11` |
| R2 → J2 | `W1→…→W5` | `W1→…→W15` |
| R1 → J1 | `W5→…→W1` | `W15→…→W1` |
| 복귀 중 되짚기 | `W2→W1` | `W12→W11→W10→…→W1` |

**J2 → C1 은 반대쪽(W3,W2,W1)으로 갔다 오지 않는다** — 최단경로라 짧은 쪽으로만 간다.

#### 번호는 여전히 '순서' 다 — 다만 방향은 자유다

`W1—W2—W3—W4—W5` 라는 **연결 관계**는 번호가 정한다. 그래서 통로를 따라 번호를
매겨야 한다. 하지만 **어느 방향으로 갈지, 어디서 들어가고 나올지는 자동**이다.
중간 번호(예: W3)를 지워도 정렬 목록에서 이웃끼리 다시 이어지므로 체인이 안 끊긴다.

### 9-1. ★ 현장에서 경유지가 통째로 안 쓰인 건 (2026-09-08)

경유지를 찍었는데 로봇이 다 무시하고 그냥 주행했다.

**원인 — 벽 검사가 선분의 양 끝까지 봤다.**

출발점은 **로봇이 지금 서 있는 자리**다. 충전소에 도킹해 있거나 작업지점에 서 있으면
벽이 코앞(0.7 m 안)이다. 목표점(R/J)도 마찬가지다. 그래서

```
출발점 자기 자신에서 이미 "벽이 0.70m 안" 판정
   → 출발점에서 나가는 모든 연결이 막힘
   → 경로 없음 → standard 폴백 → 경유지 0개 사용
```

**조치 — 양 끝 `skip_ends_m`(0.80 m) 는 검사하지 않는다.**

로봇이 이미 거기 있다는 건 그 자리가 갈 수 있는 곳이라는 뜻이다. 우리가 알고 싶은 건
**가는 길 중간에 벽이 있느냐** 뿐이다. 0.80 은 랙 적재 외접원(0.672)보다 크게 잡았다.

> 부작용 — 선분이 1.6 m 보다 짧으면 검사할 중간 구간이 없어 **무조건 통과**로 본다.
> 아주 가까운 두 경유지 사이에 얇은 벽이 있으면 못 걸러낸다. 경유지를 벽 건너편에
> 나란히 찍지만 않으면 문제되지 않는다.

### 9-2. 조용히 빠져나가던 경로에 로그를 넣었다

경유지가 안 쓰여도 흔적이 없어 원인을 못 짚었다. 세 곳 다 로그를 남긴다.

| 로그 | 뜻 | 볼 것 |
|---|---|---|
| `경유지(W1,W2…)를 하나도 못 찾음` | POI 이름/area 문제 | 이름이 `W+숫자` 인지, 로봇 area 와 맵 area 가 같은지 |
| `현재 위치를 못 읽어 경유지를 건너뜀` | 포즈 조회 실패 | 로봇 통신 |
| `경유지 그래프에서 경로를 못 찾음` | 벽에 막힘 | 경유지 배치·벽 여유 |
| `경유지 N개 중 M개 사용` | **정상** | M이 0이 아니면 동작 중 |
