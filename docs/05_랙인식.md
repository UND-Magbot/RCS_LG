## 1. rack.specs — 규격을 어떻게 정하는가

정의 위치: `BackEnd/app/constants/rack_specs.py`
펌웨어는 `align_with_rack` 시 **라이다로 잰 다리 간격**과 등록된 spec 을 비교해 매칭합니다.
백엔드가 할 수 있는 일은 **이 규격을 넣어주는 것뿐**이고, 인식 알고리즘 자체는 펌웨어 안에 있습니다.

### 핵심 원칙 ★

> **`width`/`depth` 는 "도면 치수"가 아니라 "라이다가 재는 다리 중심 간격(detected)"에 맞춘다.**

`Wrong rack size: detected(a,b), configed(c,d)` 오류는 spec 값이 실측과 안 맞을 때 납니다.
→ **로그의 detected 값을 그대로 넣으세요.** 검출이 흔들리면(캐스터 간섭 등) **관측 범위의 중앙값**을 씁니다.

### 필드

| 필드 | 뜻 | 함정 |
|---|---|---|
| `width`/`depth` | 랙 다리 **중심 간 거리**(m) | **도면 치수가 아님.** 라이다 측정값(detected)을 넣어야 함 |
| `leg_shape`/`leg_size`/`foot_radius` | 다리 검출 기준 | **실제 다리 지름에 맞춰야** 옆 캐스터를 다리로 오인식 안 함 (25mm → 0.025 / 0.0125) |
| `margin[4]` | 랙 풋프린트(장애물 제외 영역) | 캐스터가 다리 밖으로 튀어나와 장애물로 잡히면 margin 을 키워 랙 일부로 포함 |
| `alignment` | 정렬 기준 (`center`) | 다른 값이 뭐가 되는지 문서에 없음 → AutoXing 문의 |
| `alignment_margin_back`, `extra_leg_offset`, `cargo_to_jack_front_edge_min_distance` | 진입 여유 | 현재 전 사이즈 동일값 |

### 등록된 4종 (코드 실측값, `LG` 는 2026-09-04 갱신)

| 이름 | width × depth | margin | leg_shape | leg_size | foot_radius |
|---|---|---|---|---|---|
| `S300` | 0.765 × 0.765 | 0.0925 | other | 0.04 | 0.02 |
| `S600` | 0.83 × 0.87 | 0.1 | other | 0.05 | 0.025 |
| **`LG`** | **0.70 × 0.50** | **0.09** | round | 0.05 | 0.02 |
| **`LG2`** | **0.64 × 0.545** | **0.08** | round | **0.025** | **0.0125** |

**LG margin 0.05 → 0.09** (2026-09-04, 상세는 [docs/10 §10](10_충전도킹과_안전설정.md))
- 실물 최대 폭 **870mm 실측**(캐스터를 바깥으로 최대한 돌린 상태)
- 기존 0.05 는 풋프린트를 `0.70+0.10=0.80m` 로 봐서 **7cm 부족** → 캐스터가 랙 밖으로 튀어나와
  장애물로 잡히던 문제(LG2 에서 겪은 것과 동일 원인)
- `(0.87-0.70)/2=0.085` → 여유를 두어 0.09
- ⚠ `frontend/lib/constants/footprint.ts` 에도 같은 값이 있다 — **랙 규격을 바꾸면 두 파일 다 고칠 것**

**LG2 값이 그렇게 정해진 이유** (2026-08-06 실측)
- 도면은 다리 중심 665 × 600mm 였지만, 라이다 실측은 그와 다름 → 실측 기준으로 재설정
- `depth` 가 캐스터 간섭으로 **0.52~0.57 로 흔들림**(약 5cm). 펌웨어 크기매칭 허용오차가 5cm 미만이라
  고정값 하나로 양쪽을 못 맞춤 → **중앙값 0.545**(0.52·0.57 양쪽 오차 0.025 로 균등). `width 0.64` 는 안정적
- 초기값 0.47/0.37 은 **중앙에 늘어진 체인이 라이다에 잡혀 나온 가짜값**이었음
- `leg_size` 0.05 → **0.025**: 실측 다리 지름 25mm. 0.05 는 옆 캐스터 브래킷을 다리로 오인식하던 원인
- `margin` 0.05 → **0.08**: 캐스터가 다리 라인 밖으로 튀어나와 장애물로 잡히던 문제 완화

### 전송 규칙 — 사용하는 사이즈만

```python
build_rack_specs_for_map(db, map_id)   # 그 맵의 standby/jack POI 가 가진 rack_size 종류만
```
- spec 이 여러 개면 펌웨어가 **엉뚱한 spec 과 매칭을 시도해 실패**합니다
- POI 에 `rack_size` 가 비어 있으면 무시. 하나도 없으면 폴백 `S300` 1개
- **전송 시점은 맵 동기화 때뿐**입니다. `rack_specs.py` 만 고치고 백엔드를 재시작해도 로봇에 반영되지 않습니다
- 프론트 POI 편집에서 선택: `S600 / S300 / LG / LG2` (`frontend/lib/types/map.ts`, `POIEditPopup.tsx`)
  ⚠️ **기본값이 `S600`** 이라 랙 위치를 새로 만들면 반드시 바꿔야 합니다

### `Wrong rack size` 가 뜨면 — 순서대로

1. 로그의 **`detected(a,b)` 값을 그대로** `rack_specs.py` 에 반영 (도면 치수 아님)
2. `leg_size` 가 실제 다리 지름과 맞는지 (LG2 = 25mm → 0.025). 크면 **캐스터를 다리로 오인**
3. 랙 중앙의 **늘어진 물체** 확인 (라이다에 가짜 depth 생성) → §8
4. 검출이 흔들리면 관측 범위 **중앙값** 사용
5. 캐스터가 장애물로 잡히면 `margin` 확대 (0.05 → 0.08)
6. 고친 뒤 **맵 동기화**를 다시 하고, 로봇에 규격이 1개만 들어갔는지 확인 ([04 STEP 5](04_현장절차_맵핑과테스트.md))

> ⚠️ 단, 실패 유형이 **"치수 불일치"가 아니라 "검출 0"** 이면 위 항목을 아무리 만져도 해결되지 않습니다.
> 그게 §2 부터의 이야기입니다.

## 2. 문제 — 랙이 조금 틀어지면 못 찾는다

> 질문: **"랙이 조금 틀어지면 인식이 안 되는데, 각도를 보정해서 우리가 직접 맞출 수 없나?"**
> 결론: **현재 방식으로는 불가능.** 다만 확정은 아니고 맵 재작성 후 재확인이 필요함(§6)
>
> 이 조사는 **같은 시도를 반복하지 않기 위한 기록**입니다.

정면으로 놓으면 잘 되는데, 랙이 조금 틀어지면 정렬이 실패합니다.

```
정자세 / 정면      20/20, 16/16   = 100%
왼쪽으로 조금 틀음  4/7            = 57%
```

**실패할 때의 모습이 특이합니다.**

```
성공: 랙 검출 13/13, 17/17, 21/21  →  0.640 x 0.545 (설정값과 소수점까지 일치)
실패: 랙 검출 0/0                  →  MoveFailReason::rack_detection_error
```

**치수가 틀려서 실패하는 게 아니라 "랙을 아예 못 보는" 것**입니다.
그래서 `leg_size`·`margin` 같은 규격 파라미터를 아무리 만져도 해결되지 않습니다.

### 왜 각도가 문제인가

`align_with_rack` 은 **POI에 등록된 위치·방향(`ori`)을 기준으로 다리 4개가 이루는 사각형**을 찾습니다.
랙이 회전하면 그 사각형이 예상 방향과 어긋나고, 펌웨어는
**"치수가 틀리다"가 아니라 "랙이 없다"** 로 판단합니다.

## 3. 시도 — 실제 랙 각도를 읽어 보정할 수 있는가

### 발견: `/detected_rack` 이 랙의 위치·각도를 직접 준다

```json
{
  "topic": "/detected_rack",
  "rack_detected": true,
  "frame": "map",
  "rack_box": {
    "pose": {"pos": [-0.07, -30.003], "ori": 1.534},
    "width": 0.646, "height": 0.57
  },
  "rack_box_aligned": {
    "pose": {"pos": [-0.07, -30.003], "ori": 1.534},
    "width": 0.64, "height": 0.545
  }
}
```

**`frame: "map"` 으로 랙의 절대 위치와 각도를 줍니다.** `base_link`(로봇 기준) 프레임도 함께 옵니다.

### 측정 안정성 — 충분히 좋음

10개 샘플 기준:
```
흔들림   x 0.6cm  /  y 0.9cm  /  ori 0.52도
```
**보정에 쓰기에 충분한 정밀도**입니다.

### 그래서 세운 계획

```
1. 로봇을 랙이 보이는 위치로 이동
2. /detected_rack 으로 랙의 실제 pose 측정
3. POI 좌표 대신 실측 pose 를 목표로 align_with_rack 호출
   → 랙이 6도 틀어져 있으면 6도 틀어진 목표로 정렬
```

R1 POI 는 계속 쓰되(어디로 갈지 · 어떤 규격인지 · 배차 연동),
**최종 정렬 목표만 실측값으로 교체**하는 방식입니다.

## 4. ★ 막힌 지점 — 순환 문제

**랙 검출은 로봇이 랙 아래로 들어가야 작동합니다.**

거리별로 붙여가며 검출을 시도한 결과:

| 로봇 위치 (R1 접근선 상 뒤로) | 이동 | 검출 |
|---|---|---|
| 2.0 m | 성공 | **0** |
| 1.5 m | 성공 | **0** |
| 1.0 m | 성공 | **0** |
| 0.6 m | 성공 | **0** |
| 0.3 m | 성공 | **0** |
| 0.0 m (R1 정중앙) | 성공 | **0** |

로봇을 랙 **정면 1.65m 앞에서 바라보게** 세워도 검출 0이었습니다.
반면 로봇이 **랙 아래에 있을 때**(`base_link` 기준 2.3cm)는 즉시 검출됐습니다.

### 제조사 문서와도 일치

> 로봇을 랙 앞에 정렬 → 감지 시작 → **로봇을 천천히 랙 아래로 이동시키면 값이 갱신됨**

### 그래서 계획이 성립하지 않습니다

```
측정하려면  →  랙 아래로 들어가야 함
들어갔으면  →  이미 정렬이 성공했거나 실패한 뒤

즉, "미리 재서 보정"이 원리적으로 불가능
```

### 실패 로그도 같은 얘기

| 실패 유형 | 랙 검출 | 보정 가능? |
|---|---|---|
| `501` 랙 인식 실패 (진짜) | **0 / 0** | ❌ 보정할 재료가 없음 |
| `506` 잭 up 거부 | 2 / 2 | ⭕ 값은 있으나 랙 문제가 아님 |

**진짜 실패했을 때는 검출 데이터 자체가 없습니다.**

## 5. 다른 방법도 확인했지만 없음

### `rack.specs` 에 회전 허용 파라미터가 없다

로봇에 들어가는 규격 필드 전체:
```
width, depth, margin[4], alignment, alignment_margin_back,
extra_leg_offset, leg_shape, leg_size, foot_radius,
cargo_to_jack_front_edge_min_distance
```

**회전 허용오차에 해당하는 항목이 없습니다.**
`alignment: "center"` 외에 어떤 값이 가능한지도 문서에 없습니다.

→ **AutoXing 문의 항목**입니다. 기존 문의 목록(`rack_area_id` 미사용, `detectRackSize` REST 없음)에 함께 올리면 됩니다.

### 인식 알고리즘 자체는 못 건드린다

`align_with_rack` 은 **로봇 펌웨어 안에서** 동작합니다.
백엔드가 하는 일은 규격(`rack.specs`)을 넣어주고 이동 명령을 보내는 것뿐입니다.
우리가 다리 검출 로직을 바꿀 방법이 없습니다.

## 6. ⚠️ 이 결론의 한계 — 재확인 필요

**§4의 거리별 시험은 `lidar_matched=False` 상태에서 진행됐습니다.**

```
lidar_matched: False
lidar_matching_score: 0.21 ~ 0.37
good_constraint_count: 0
```

즉 **로봇이 자기 위치를 잘못 알고 있었을 가능성**이 있습니다.
"R1 정중앙으로 이동"했다고 로봇이 보고했지만 실제로는 다른 곳에 서 있었을 수 있습니다.
그러면 "0.3m 앞에서도 검출 0" 이라는 결과가 **거리 때문이 아니라 로봇이 엉뚱한 데 있어서**일 수 있습니다.

### 다만 결론 자체는 다른 근거로도 지지됩니다

거리 시험을 빼도 아래 3가지는 위치추정과 무관하게 성립합니다:

1. **제조사 문서**가 "랙 아래로 이동시키면 값이 갱신됨"이라고 명시
2. **정렬 성공 시** 검출 패킷이 13~21개 — 접근·진입 과정에서만 발생
3. **로봇이 랙 아래에 있을 때**는 즉시 검출됨(`base_link` 2.3cm)

**"유력하지만 확정은 아님"** 으로 두는 게 정확합니다.

### 맵 재작성 후 반드시 다시 확인할 것

```
1) 맵 재작성 → 위치재조정 → lidar_matched=True 확인
2) 랙을 R1 정위치에 놓기
3) robot_check.py --rack 으로 거리별 재측정
     2.0m / 1.0m / 0.5m / 0.0m
4) 어느 거리에서든 검출되면 → §3 계획이 되살아남
```

**이걸 안 하고 "보정은 불가능"으로 못 박으면, 실제로는 가능한 길을 버리게 됩니다.**

## 7. 그래서 지금 할 수 있는 것 (우선순위 순)

### 7-1. 물리 가이드 ★ 가장 확실

```
랙 자리(R1)에 L자 앵글 / 스토퍼 2개를 설치해
랙이 항상 같은 자세로 밀착되게 만든다
```

현장 운영에서는 **어차피 필요합니다.** 사람이 랙을 아무렇게나 놓으면 로봇이 못 집는데,
"잘 놓으세요"라는 지시로는 유지되지 않습니다.
**얼마나 정밀하게 만들지는 허용 각도를 재야 정해집니다** (7-3).

### 7-2. 랙 반납 정확도 개선 — `to_unload_point`

`dispatch_service._return_to_standby_and_park` 가 복귀 시 랙을 내려놓을 때 `standard` 이동을 씁니다.

```python
jack_service.safe_move(
    worker.robot_ip,
    "standard",              # ← 로봇을 POI에 세움 (랙이 아님)
    standby["x"], standby["y"], standby["ori"],
)
```

`standard` 는 **로봇**을 그 좌표에 세웁니다. 랙은 로봇 위에 얹혀 있어서
**랙의 중심은 다른 곳에 놓입니다.**

같은 저장소의 `jack_service.run_jack_job` 은 내려놓을 때 이걸 씁니다:
```python
safe_move(ip, "to_unload_point", dropoff["x"], dropoff["y"], ...)
```

**`to_unload_point` 는 "랙이 그 자리에 놓이도록" 로봇을 배치하는 이동 타입**입니다.
배차 복귀 경로만 `standard` 를 쓰고 있습니다.

> 이게 [06_테스트현황과_이슈.md](06_테스트현황과_이슈.md) 의 **버그 D** 입니다 (VESA 실측 오차 0.717m).
> 매 사이클 조금씩 어긋난 자리에 반납되고, 누적되면 다음 픽업이 실패합니다.

**변경은 한 줄이지만 검증이 필요합니다.** 미해결 이슈에
`to_unload_point J1 이동 미작동` 건이 남아 있어, 이 POI 타입(standby)에서 동작하는지 먼저 확인해야 합니다.
**미적용 상태입니다.**

### 7-3. 허용 각도 측정

"몇 도까지 되는가"를 알아야 가이드 사양과 현장 운영 기준이 정해집니다.
`rack_bench.py` 로 세트를 나눠 측정합니다 — 방법·각도 환산표·결과 읽는 법은
**[04 §7-2](04_현장절차_맵핑과테스트.md)** 에 있습니다. (각 세트 10회면 충분)

## 8. 접지 체인 — 별개 문제

LG2 랙에 달린 금속 체인은 **접지용**이라 제거할 수 없습니다(바닥에 닿아 있어야 함).

### 확정 사항

**체인이 수직으로 늘어져 바닥까지 닿는 이상, 라이다 평면을 반드시 통과합니다.**
위에서 아래까지 모든 높이를 지나가므로 **높이를 조절해 피하는 방법은 원리적으로 없습니다.**
→ 남는 방법은 **수평 위치를 진짜 다리와 겹치게** 만드는 것뿐입니다.

| 방법 | 내용 | 효과 |
|---|---|---|
| 기둥에 밀착 | 케이블타이로 기둥에 바짝 고정, 끝은 바닥에 닿게 | 다리가 25→30mm 정도로 굵어 보이는 수준 |
| **수직 구간 제거** | 기둥 아래까지 밀착시켜 내린 뒤 바닥에 눕힘 | 라이다 평면을 지나는 게 아예 없어짐 |

**둘 다 접지 기능은 유지됩니다.**

> 케이블타이는 **바짝** 조여야 합니다. 헐거우면 로봇이 지나갈 때 흔들려 기둥에서 떨어지고,
> 그러면 **가끔만 실패**하는 형태가 됩니다. 이게 제일 잡기 어려운 증상입니다.

### ⚠️ 기존 문서 정정 (2026-08-12 확인)

여러 문서에 있던 **"랙 중앙의 체인은 물리적으로 제거"** 권고는 **이 랙에 적용 불가**입니다.
당시엔 접지용인 줄 모르고 뗐던 것으로 보입니다.

## 10. ★ 랙 밑에서 빠져나오는 거리 (2026-09-07 사고)

### 무슨 일이 있었나

J1 에 랙을 반납하고 앞으로 나온 뒤, 다음 이동이 **살짝 후진하면서 랙 다리에 접촉**했다.

원인은 `dispatch_service.RACK_ESCAPE_M = 0.7` 이 **모든 규격에서 부족**했다는 것이다.
로봇은 랙의 `depth` 축을 따라 들어가고 나온다. **로봇 뒤끝이 앞쪽 다리를 지나야** 완전히 빠져나온 것이다.

```
필요 = depth/2 (+ margin: 캐스터가 튀어나온 몫) + 로봇 뒤끝(0.369, /robot_model 실측)
```

| 규격 | depth | margin | 다리까지 | 캐스터까지 | 필요(다리) | 필요(캐스터) | 0.7 로 충분? |
|---|---|---|---|---|---|---|---|
| S300 | 0.765 | 0.0925 | 0.383 | 0.475 | 0.752 | 0.844 | ❌ 다리부터 충돌 |
| S600 | 0.870 | 0.100 | 0.435 | 0.535 | 0.804 | 0.904 | ❌ 다리부터 충돌 |
| **LG** | 0.500 | 0.090 | 0.250 | 0.340 | 0.619 | 0.709 | 다리 OK / **캐스터 접촉** |
| **LG2** | 0.545 | 0.080 | 0.273 | 0.353 | 0.641 | 0.722 | 다리 OK / **캐스터 접촉** |

```
이탈 0.7 m 후 로봇 뒤끝 = 0.7 − 0.369 = 0.331 m (랙 중심 기준)
  S300 다리 0.383 → 5 cm 안쪽   ★ 충돌 (실제로 부딪힘)
  LG   캐스터 0.340 → 0.9 cm 안쪽  ★ 접촉 가능
  LG2  캐스터 0.353 → 2.2 cm 안쪽  ★ 접촉 가능
```

> **현장 랙(LG·LG2)도 안전하지 않았다.** 기둥은 피하지만 **캐스터가 1~2 cm 안쪽**이다.
> `margin` 이 곧 캐스터가 다리 라인 밖으로 튀어나온 몫이고, 캐스터는 회전하므로
> 자세에 따라 닿는다. 정렬 오차(`alignment_margin_back` 0.02)까지 감안하면 더 그렇다.
> 눈에 띄게 부딪히지 않아 그동안 못 알아챘을 가능성이 크다.

### 수정 — 규격표에서 계산한다

상수로 박지 않고 `RACK_SPECS` 에서 **가장 깊은 규격 기준**으로 계산한다.
규격을 추가하거나 margin 을 바꿔도 자동으로 따라간다.

```python
ROBOT_REAR_M = 0.369                    # /robot_model 실측 (footprint y 최소 -0.369)

def _rack_escape_distance() -> float:
    rear = max(depth/2 + margin  for 모든 RACK_SPECS)     # S600 기준 0.535
    return round(rear + ROBOT_REAR_M + 0.15, 2)          # 0.15 = 여유

RACK_ESCAPE_M = _rack_escape_distance()   # = 1.05 m  (전 0.7)
```

```
이탈 후 뒤끝 = 1.05 − 0.369 = 0.681 m
가장 깊은 캐스터(S600 0.535) 대비 여유 0.146 m → 4 규격 전부 통과
```

### ⚠ 부작용 확인 필요

이탈이 **0.35 m 길어졌다.** J 지점 앞 1.05 m 에 벽·설비가 없어야 한다.
막히면 이탈이 실패하고 재시도가 도는데, `fail_reason` 이 로그에 남으므로 바로 확인된다
(`docs/11` §7).
