# 1. 기초 개념 — 이것만 알면 나머지가 읽힙니다

## 1-1. IP 주소 = 네트워크 안의 "집 주소"

```
192.168.30.100    ← 로봇
192.168.30.2      ← 개발 PC
192.168.30.1      ← 공유기(문지기)
```

앞의 `192.168.30` 이 **동네 이름**, 마지막 `.100` 이 **집 번호** 입니다.

**동네가 다르면 서로 못 갑니다.**
2026-08-13에 로봇이 `192.168.39.54`(LTE 동네), PC가 `192.168.30.2`(사무실 동네)에 있어서
아무리 불러도 응답이 없었던 게 정확히 이것입니다.

## 1-2. 포트 = 한 집 안의 "창구 번호"

같은 컴퓨터 안에서도 프로그램마다 창구가 다릅니다.

```
192.168.30.100 : 8090   ← 로봇 제어 API
192.168.30.2   : 8002   ← 백엔드
192.168.30.2   : 3000   ← 프론트(관제화면)
192.168.30.2   : 3306   ← MariaDB
```

주소가 같아도 **창구 번호가 다르면 다른 프로그램** 입니다.

## 1-3. 공유기 = 동네 문지기

한 공유기에 붙은 기기들은 같은 동네 주민이 되어 **자유롭게 서로 통신**합니다.

## 1-4. 자동 IP(DHCP) vs 고정 IP

| 방식 | 설명 | 문제 |
|---|---|---|
| **자동 (DHCP)** | 공유기가 남는 번호를 알아서 배정 | **껐다 켤 때마다 번호가 바뀔 수 있음** |
| **고정 (Static)** | "나는 무조건 .100번" 하고 못 박음 | 겹치지 않게 관리 필요 |

### 왜 로봇은 고정이어야 하나

우리 시스템은 **로봇 주소를 DB에 적어둡니다.**

```
robots 테이블
  id=12,  name=B682406903516UI,  ip_address=192.168.30.100
```

백엔드는 로봇을 부를 때마다 이 주소로 명령을 보냅니다.
**IP가 바뀌면 없는 주소로 계속 전화를 겁니다.** 관제 화면에는 "오프라인"으로 뜹니다.

### 고정하는 방법 2가지 (하나만 하면 됨)

**① 로봇 자체에 박아넣기** ← 현재 방식
```
로봇 wifi_setup 에서 고정 IP JSON 입력 (§6 참조)
```
장점: 공유기를 안 건드려도 됨

**② 공유기에서 예약 (DHCP 예약)**
```
공유기 설정 → "이 MAC 을 가진 기기에는 항상 .100 을 줘라"
```
장점: 로봇 설정을 안 건드려도 됨 / 단점: 공유기 관리자 접속 필요

# 2. 현재 사무실 구성

```
        s300 공유기 (192.168.30.1)
                 │
    ┌────────┬───┴────┬─────────┐
   개발PC    로봇    태블릿    기타
   .2       .100      .x        .x
```

**전부 같은 동네(`192.168.30.x`)** 라서 서로 자유롭게 통신합니다.

| 항목 | 값 |
|---|---|
| 게이트웨이 | `192.168.30.1` |
| 공유기 MAC (5GHz BSSID) | `b0:38:6c:77:fc:80` |
| 로봇 IP | `192.168.30.100` (고정) |
| 서브넷 | `192.168.30.0/24` |
| SSID | **`s300`** — 5GHz(채널 149) / 2.4GHz **둘 다 같은 이름** |

> 2.4GHz 는 원래 `iptime` 이었으나 2026-08-13 에 `s300` 으로 통일했습니다(§4 참조).

**가장 단순하고 빠릅니다. 개발·테스트에는 이 구성이 최선입니다.**
단, 공유기 WiFi 가 닿는 범위 안에서만 동작합니다.

# 3. 현장(LG) 구성 — LTE 라우터 2개

현장에는 우리가 쓸 공유기가 없습니다. LTE 로 각자 연결합니다.

## 3-1. APN 이 뭔가

**APN = LTE 기기가 통신사 망에 들어갈 때 쓰는 "관문 이름"** 입니다.

```
일반 스마트폰     APN: lte.lguplus.co.kr           → 인터넷
우리 LTE 라우터   APN: m2m-router.lguplus.co.kr    → M2M 전용 관문
```

**M2M** = Machine to Machine. 기계끼리 통신하는 용도의 회선 상품입니다.

### 회선 성격 (2026-08-03 실측)

```
APN      : m2m-router.lguplus.co.kr
받는 IP  : 10.x.x.x   ← 공인 IP 가 아니라 통신사 내부 주소 (CGNAT)
```

| 항목 | 가능 여부 |
|---|---|
| 인터넷에서 우리 라우터로 **직접 접속** | ❌ 불가 (공인 주소가 없음) |
| **같은 APN 을 쓰는 장비끼리** 통신 | ⭕ **가능** ← 이 성질이 핵심 |

실증 (2026-08-03):
```
서버PC 라우터(WAN 10.240.x)  →  로봇 라우터(WAN 10.230.x)   ping 성공
```

## 3-2. ★ APN 망 = 통신사가 운영하는 거대한 공유기

**사무실의 s300 공유기와 같은 역할**입니다. 이렇게 보면 이해가 쉽습니다.

```
[사무실]                          [현장]
    s300 공유기                      LTE M2M APN 망
         │                                │
    ┌────┴────┐                    ┌──────┴──────┐
   PC       로봇                서버라우터    로봇라우터
 30.2      30.100               10.240.x     10.230.x
    └─ 서로 통신 ─┘                 └─ 서로 통신 ─┘
```

**"같은 APN 을 쓴다" = "같은 공유기에 붙는다"**
붙는 방법이 WiFi 비밀번호가 아니라 **USIM** 일 뿐입니다.

### 주소는 오히려 달라야 정상입니다

```
사무실:  PC .2 / 로봇 .100
현장  :  서버 10.240.x / 로봇 10.230.x
```

같으면 충돌합니다. 한 동네에 같은 번지가 둘일 수 없는 것과 같습니다.

> 앞자리(`10.240` vs `10.230`)까지 다른 건 통신사 망이 워낙 커서 구역을 나눠 쓰기 때문입니다.
> 통신사가 그 사이 길을 열어주므로 서로 통신됩니다.
>
> **사무실 공유기 = 아파트 한 동** (모두 같은 앞자리)
> **APN 망 = 도시 전체** (구역이 달라도 도로가 연결돼 있음)

## 3-3. 왜 라우터가 2개인가

```
┌──────────── LG U+ M2M 전용 APN 망 ────────────┐
│                                               │
│  TC700_5168495              TC700_5170086     │
│  WAN 10.115.244.11          WAN 10.115.244.12 │
│  (서버PC + 태블릿용)         (로봇용)          │
│       │                          │            │
│  LAN 192.168.39.1           LAN 192.168.39.1  │
│       │                          │ +포트포워딩 │
│       ↓                          ↓            │
│  서버PC 192.168.39.110    로봇 192.168.39.100 │
│  (백엔드 8002)             (제어 API 8090)     │
└───────────────────────────────────────────────┘
```

**① 로봇은 돌아다닙니다**
공장 안을 계속 이동하므로 WiFi 하나로 전체를 덮을 수 없습니다.
**라우터를 로봇에 얹으면** 어디로 가든 LTE 로 항상 연결됩니다.

**② 서버 PC 는 한자리 고정입니다**
로봇을 따라다닐 필요가 없습니다.

**③ 각자 회선이면 서로 독립적입니다**
한쪽에 문제가 생겨도 다른 쪽은 살아 있습니다.

> **로봇이 USIM 을 직접 못 꽂기 때문**에 라우터가 필요합니다.
> 로봇은 WiFi 만 되므로, 라우터가 `WiFi ↔ LTE` 번역기 역할을 합니다.

> 양쪽 LAN 이 둘 다 `192.168.39.x` 인 건 **문제없습니다.**
> 서로 다른 라우터 안쪽이라 섞이지 않습니다. 아파트 두 동에 똑같이 101호가 있어도 되는 것과 같습니다.

**태블릿은 서버 PC 쪽 라우터**에 붙입니다. 태블릿은 로봇에 직접 접속하지 않고 백엔드 화면(8002)만 보기 때문입니다.

## 3-4. ★ 포트포워딩 — 사무실과 현장의 진짜 차이

### 사무실 — 로봇이 공유기에 직접 붙음

```
   s300 공유기
        │
       로봇 192.168.30.100    ← 로봇 자신이 주소를 가짐

PC → 192.168.30.100:8090 → 바로 도착 ✅
```
**로봇이 동네 주민이라 직접 찾아갈 수 있습니다. 포트포워딩 불필요.**

### 현장 — 로봇이 라우터 뒤에 숨음

```
   APN 망
      │
 로봇라우터 (WAN 10.230.x)   ← 주소는 라우터가 가짐
      │
    로봇 (192.168.39.100)    ← 라우터 안쪽. 밖에서 안 보임

서버 → 10.230.x:8090 → [포워딩 규칙] → 로봇 192.168.39.100:8090
```

로봇 라우터에 이 규칙을 겁니다 (2026-08-03 설정 완료):
```
외부 8090  →  192.168.39.100 : 8090  (TCP)
```

> 아파트로 치면 **경비실에 "8090호 택배는 100동으로" 라고 등록**해두는 것입니다.

### 헷갈리기 쉬운 3가지

**① 포트포워딩은 "들어오는 쪽"에만 겁니다**
로봇 라우터는 손님을 받으므로 규칙이 필요합니다.
서버 라우터는 나가기만 하므로 **아무 설정도 필요 없습니다.**

**② 서버가 접속하는 주소는 `192.168.39.100` 이 아닙니다**
```
❌ 서버PC → 192.168.39.100:8090
     서버PC 는 다른 라우터 안쪽이라 이 주소를 모릅니다.
     (자기 동네에도 192.168.39.110 이 있어 더 헷갈립니다)

⭕ 서버PC → 로봇라우터WAN(10.230.x):8090
     → 라우터가 알아서 안쪽 .100 으로 전달
```

**③ DB 에 넣는 로봇 주소도 WAN IP 입니다**
```
robots.ip_address = 로봇 라우터의 WAN IP   (예: 10.230.x)
```
`192.168.39.100` 을 넣으면 안 됩니다.
2026-08-04 일지: *"현재 WAN IP 로 재설정 후 재검증"*

## 3-5. 유동 IP 문제 — 고정 IP 를 신청한 이유

2026-08-04 에 크게 겪은 문제입니다.

```
로봇 라우터 WAN IP 가 하루에도 여러 번 바뀜
   10.230.x → 10.49.x → 10.25.x ...
```

주소가 바뀌면 서버가 로봇을 못 찾습니다.
심지어 **옛 주소가 다른 회사 장비에 재할당**되어, ping 은 되는데 로봇은 없는 상황까지 발생했습니다.
그동안의 매핑 미동작·대량 전송 실패·정보 조회 실패가 **전부 IP 불일치가 원인**이었습니다.

→ 고정 IP 신청 (2026-08-13 기준 U+ 상품군 문제로 지연 중)

## 3-6. 고정 IP USIM — 라우터에서 뭘 설정하나

### ⚠️ IP 가 두 종류라는 걸 먼저 구분

| | 누가 정하나 | 현재 | 고정 방법 |
|---|---|---|---|
| **WAN IP** | **통신사** | `10.230.x` (변동) | **USIM 상품으로 고정** |
| LAN·로봇 IP | 우리 | `192.168.39.100` | 라우터/로봇 설정 |

**"고정 IP 를 받는다"는 WAN IP 이야기입니다.**
라우터 설정에서 손으로 박는 게 아니라, **통신사가 "이 USIM 에는 항상 이 주소를 준다"고 정해주는 것**입니다.

### 라우터에서 할 일

```
1) 받은 USIM 을 로봇용 라우터(TC700_5170086)에 삽입
2) 그 라우터 WiFi 에 붙어서 http://192.168.39.1:8090/  (admin / uned123456)
3) APN 설정 → 통신사가 알려준 APN 이름 입력
4) 재접속 / 재부팅
5) 상태 화면에서 WAN IP 확인 → 받기로 한 고정 IP 가 뜨는지
6) ★ 라우터를 2~3회 재부팅해도 같은 주소가 나오는지 확인 (고정 여부 실검증)
```

> **USIM 은 로봇용 라우터에만 필요합니다.** 서버 PC 쪽은 나가기만 하므로 고정 IP 가 필요 없습니다.

**대부분 APN 만 맞으면 끝납니다.** WAN IP 를 손으로 입력하는 게 아닙니다.

### 통신사에서 받아야 할 정보

```
□ APN 이름          (고정IP 상품용 APN 이 따로 있을 수 있음)
                     현재: m2m-router.lguplus.co.kr
□ 부여된 고정 IP 주소
□ 인증 정보         (사용자명/비밀번호 — 없는 경우가 많음)
□ 인증 방식         (PAP / CHAP / 없음)
□ ★ 공인 IP 인가, 사설 고정 IP 인가
```

### ★ 마지막 항목이 중요합니다

| 종류 | 주소 예 | 외부 인터넷에서 접속 | 같은 APN 장비끼리 |
|---|---|---|---|
| **공인 고정 IP** | `211.x.x.x` | ⭕ | ⭕ |
| **사설 고정 IP** | `10.x.x.x` 고정 | ❌ | ⭕ |

**우리 용도에는 사설 고정으로도 충분합니다** (서버와 로봇이 같은 APN 망 안).
다만 "사무실에서 현장 로봇을 원격으로 보고 싶다"가 되면 공인 IP 가 필요합니다.
**나중에 바꾸려면 상품을 다시 바꿔야 하므로 미리 확인하세요.**

> TC700 관리 페이지의 정확한 메뉴명은 미확인입니다.
> `APN` / `프로파일` / `모바일 네트워크` / `WAN 설정` 중 하나에 있습니다.

## 3-7. 사무실 vs 현장 한눈에

| | 사무실 | 현장 |
|---|---|---|
| "공유기" 역할 | s300 공유기 | **통신사 APN 망** |
| 붙는 방법 | WiFi 비밀번호 | **USIM** |
| 서버 주소 | `192.168.30.2` | `10.240.x` (라우터 WAN) |
| 로봇 주소 | `192.168.30.100` | `10.230.x` (라우터 WAN) |
| 로봇 위치 | 공유기에 **직접** | 라우터 **안쪽** |
| 포트포워딩 | ❌ 불필요 | ⭕ **필요** (로봇 라우터에) |
| DB 로봇 IP | `192.168.30.100` | `10.230.x` ← **라우터 주소** |
| 주소 안정성 | 고정 설정함 | 유동 → **고정 IP 신청 중** |

# 4. 2026-08-13 WiFi 장애 기록

## 증상

로봇 재부팅 후 사무실 망에 안 붙고 LTE 라우터 망으로 자동 연결.
로봇의 `wifi_setup` 목록에 **`s300` 이 아예 보이지 않음.**

## 경위

| 시각 | 상황 |
|---|---|
| 오전~오후 | 로봇이 `192.168.30.100` 에서 정상 동작 |
| 재부팅 후 | `192.168.30.100` 응답 없음 |
| 진단 | `192.168.30.1~254` **ICMP 스윕 + 8090 스캔** → 로봇 없음 확정 |
| | ARP 에도 없음 (`.1` 공유기 / `.2` PC / `.11` / `.17` 만) |
| 태블릿 확인 | 로봇이 **`192.168.39.54`** (LTE 망)에 있었음 |
| 도달 시험 | PC(`192.168.30.2`) → `192.168.39.54` **100% 손실**. 두 망 분리 |
| 원인 규명 | `netsh wlan show interfaces` → **`s300` = 5GHz, 채널 149** |
| 확인 | 폰을 `iptime` 에 연결 → **`192.168.30.x` 수령** → 같은 공유기의 2.4GHz 확정 |

## 원인

사무실 공유기가 **대역별로 다른 SSID** 를 쓰고 있었고 **`s300` 은 5GHz 전용**.
**로봇은 2.4GHz 만 지원**하므로 5GHz SSID 는 스캔 목록에 원리적으로 나오지 않음.
2.4GHz SSID 이름이 `iptime` 이었는데, 로봇 설정 시 `s300` 을 찾다가 막힘.

## 해결

```
공유기 설정에서
  2.4GHz SSID 를 iptime → s300 으로 변경
  + 채널 변경
  + 비밀번호 설정
→ 정상 연결
```

**양쪽 대역이 같은 이름(`s300`)** 이 되어, 어느 대역에 붙든 헷갈릴 일이 없어졌습니다.
이게 이번 조치의 핵심 이점입니다.

## 교훈 — 기록의 함정

2026-08-11 일지에 **"로봇을 `s300` 으로 이전"** 이라고만 적혀 있었습니다.
이건 대화를 요약한 문장이지 **실제로 목록에서 무엇을 골랐는지의 기록이 아니었습니다.**
당시에도 2.4GHz(`iptime`)를 골랐을 가능성이 큽니다.

> **망 이름을 기록할 때는 "어느 대역의 어떤 SSID 를 골랐는지" 까지 남길 것.**

# 8. 포트 구성 — 백엔드와 프론트

## 8-1. "백엔드는 화면이 없는데 8002 는 뭔가?"

**화면이 없다 ≠ 접속할 곳이 없다** 입니다.
백엔드는 데이터를 주고받는 프로그램이고, 그 요청을 받는 창구가 **8002** 입니다.

```
http://192.168.30.2:8002/ping
   → {"message":"pong"}                    ← 글자만 (사람용 화면이 아님)

http://192.168.30.2:8002/api/dispatch/console/status
   → {"pois":[...], "robots":[...]}         ← 데이터 덩어리
```

**사람이 보라고 만든 게 아니라 프로그램이 읽으라고 만든 것**이라 예쁜 화면이 아닙니다.

### 그런데 — 백엔드가 이미 화면도 서빙합니다

```
http://192.168.30.2:8002/api/dispatch/console          → 배차 콘솔 화면
http://192.168.30.2:8002/api/dispatch/robot-tablet/12  → 로봇 태블릿 화면
```

`app/templates/` 의 HTML 을 백엔드가 읽어서 그대로 내려주는 방식입니다.
**"백엔드는 화면이 없다"는 이 프로젝트에서는 절반만 맞습니다.**

## 8-2. "8002 하나로 합친다"는 무슨 뜻인가

### 지금 — 배달부가 2명

```
브라우저 → http://192.168.30.2:3000
   ① Node 서버(3000)  →  관제화면 HTML/JS 를 보내줌
   ② 화면이 브라우저에서 돌며 "로봇 목록 줘" → 8002 에 요청
   ③ 백엔드(8002)     →  데이터 보내줌
```

### 합치면 — 배달부가 1명

관제화면은 사실 **HTML·JS 파일 뭉치**일 뿐입니다. 확인 결과 서버가 할 일이 하나도 없었습니다.
```
API route 0개 / 서버 컴포넌트 0개 / 동적 라우트 0개 / middleware 0개
```

그러면 **그 파일들을 백엔드가 같이 나눠주면** 됩니다. 콘솔·로봇태블릿을 이미 그렇게 주고 있습니다.

```
브라우저 → http://192.168.30.2:8002
   백엔드(8002) → 관제화면 파일도 보내주고, 데이터도 보내줌
```

**Node 프로그램이 아예 사라집니다.**

### 얻는 것

| | 지금 | 합치면 |
|---|---|---|
| 돌아가는 프로그램 | 2개 | **1개** |
| 서버 PC 에 설치할 것 | Python + **Node.js** | **Python 만** |
| 열어야 할 포트 | 8002, 3000 | **8002 만** |
| 접속 주소 | 관제 3000 / 태블릿 8002 | **전부 8002** |
| **서버 IP 바뀌면** | **화면 재빌드 필요** | **그냥 됨** |

### 마지막 줄이 제일 큽니다

지금은 화면을 만들 때 서버 주소가 **글자 그대로 박힙니다.**
```
빌드 후:  fetch("http://192.168.30.2:8002/api/robots")   ← 박제됨
```
**IP 가 바뀌면 화면을 통째로 다시 만들어야 합니다.** 서버 PC 에 Node 를 안 깔았으면 못 합니다.

합치면 주소를 비울 수 있습니다.
```
빌드 후:  fetch("/api/robots")   ← "나한테 화면 준 서버한테 물어봐"
```
화면을 준 서버가 곧 데이터를 줄 서버이므로 **IP 가 뭐든 알아서 맞습니다.**

> 코드 수정은 완료됐고 실빌드 검증만 남았습니다. 적용 후 이 문서의 포트 표기를 갱신할 것.

# 9. 다른 PC 에서 관제화면 접속하기

## 9-1. 같은 공유기면 그냥 됩니다

```
http://192.168.30.2:3000      (통합 후 :8002)
```

조건 2가지:
1. 서버 PC **방화벽에 3000·8002 허용** — 등록 명령은 [03_서버PC구축.md](03_서버PC구축.md) STEP 6
2. 프론트 API 주소가 `localhost` 가 아니라 **서버 PC IP** 여야 함

> 2026-08-13 에 화면 3개(원격제어·통계 등)가 `localhost` 폴백이라
> **다른 PC 에서 열면 그 화면만 안 나오는** 문제가 있어 수정했습니다.

## 9-2. 다른 공유기면 그냥은 안 됩니다

```
PC-A : 192.168.30.x  (s300)        ← 서버
PC-B : 192.168.0.x   (다른 공유기)  ← 접속 시도

동네가 달라서 못 감  (로봇 39.x 문제와 동일)
```

## 9-3. 방법 3가지

**① 포트포워딩 (+ DDNS)**
```
외부 → 공유기 공인IP:8002 → 192.168.30.2:8002
```
필요: 공유기 관리자 권한, **공인 IP**(CGNAT 면 불가), IP 변동 시 DDNS
> ⚠️ **인터넷에 그대로 노출됩니다.** 로봇을 움직일 수 있는 시스템이라 권하지 않습니다.

**② VPN (권장)**
다른 동네에 있어도 **같은 동네인 것처럼** 만들어줍니다. 포트를 하나도 안 열어도 됩니다.
> TC700 에는 VPN 메뉴가 없습니다(2026-08-03 확인). 사무실 공유기나 별도 장비 필요.

**③ 같은 공유기로 옮기기** — 대부분 이게 정답입니다.

| 상황 | 방법 |
|---|---|
| 같은 공유기 | `http://서버IP:3000` (통합 후 `:8002`) |
| 다른 공유기, 사내 | **VPN** 또는 같은 공유기로 이동 |
| 외부 인터넷 | 포트포워딩 + DDNS (**보안 위험**) |
| LTE 환경 | CGNAT 라 외부 접속 불가. 같은 APN 망 안에서만 |

> **포트 통합하면 열 포트가 1개로 줄고, API 주소가 상대경로라 외부 접속도 자동으로 맞습니다.**

# 10. LG 현장 연결 방안

## 10-1. 두 가지 길

### (A) LGIT 사내망에 유선으로 물리기

```
LGIT 사내 네트워크
      │ (랜선)

      │

      │
    로봇

**장점:** 빠르고 안정적, LTE 요금 불필요, **유동 IP 문제 없음**
**단점:** LGIT 보안 정책 통과 필요. 외부 장비 반입을 막는 회사도 많음

### (B) LTE 그대로 (현재 준비 중)

**장점:** 남의 네트워크에 손 안 댐, 협의 최소
**단점:** 고정 IP 신청 필요, 요금, 속도

## 10-2. (A) 로 갈 때 LGIT 에 요청할 것

```
기기 대수만큼
  1. 고정 IP 주소
  2. 서브넷 마스크
  3. 기본 게이트웨이
  4. DNS 서버
  5. 사용 가능한 포트 (8002, 8090 등이 막히지 않는지)
  6. 기기 등록 필요 여부 (MAC 등록제를 쓰는 회사가 많음)

# 11. LGIT 자체 관제시스템과 연동 (개념)

LG 에 이미 자기네 관제시스템이 있을 경우의 연동 방식입니다.

## 방식 ① REST API 연동 (가장 일반적)

```
LGIT 관제  ──"로봇 상태 알려줘"──>  우리 백엔드(8002)
           <──{배터리 80%, 위치 J1}──

LGIT 관제  ──"J3 으로 보내줘"──>  우리 백엔드
           <──{접수됨, 세션 67}──
```

**우리 시스템은 이미 REST API 를 갖고 있어** 이 방식이 가장 자연스럽습니다.

협의할 것:
```
- 어느 쪽이 요청하는가 (LGIT → 우리 / 우리 → LGIT)
- 인증 방식 (API 키, 토큰)
- 주고받을 정보 (로봇 상태? 작업 지시? 완료 통보?)
- 응답 형식 (JSON 필드 규칙)
```

## 방식 ② 이벤트 밀어주기 (Webhook)

```
로봇이 J1 도착 → 우리 백엔드가 LGIT 주소로 "도착했음" 전송
```
실시간성이 필요할 때. LGIT 쪽에서 받을 창구를 만들어줘야 합니다.

## 방식 ③ DB 직접 공유

**권하지 않습니다.** 한쪽이 스키마를 바꾸면 반대쪽이 깨지고 보안·권한 관리가 어렵습니다.

## 실무 순서

```
1. "무엇을 연동할 것인가" 정의        ← 여기서 제일 오래 걸림
     우리가 로봇을 다 제어하고 상태만 보고?
     LGIT 가 작업 지시를 내리고 우리는 실행만?
2. 인터페이스 규격서 작성 (API 목록·필드·인증)
3. 테스트 환경 연동
4. 실운영 적용
```
기술이 아니라 **역할 분담**의 문제라 1번이 핵심입니다.

# 12. 재발 방지 / 현장 반영 사항

| # | 항목 | 이유 |
|---|---|---|
| 1 | **로봇의 저장된 WiFi 목록에서 LTE 망 삭제** | 재부팅 시 그쪽으로 자동 연결. **2026-08-13 사고의 직접 원인** |
| 2 | **양쪽 대역 SSID 를 같은 이름으로** | 이번에 `s300` 으로 통일. 대역 혼동 없음 |
| 3 | **로봇은 2.4GHz 만 지원한다고 가정** | 5GHz 전용 SSID 는 로봇 목록에 안 뜸 |
| 4 | **로봇 IP 는 고정** | DHCP 면 재부팅마다 바뀌어 DB 를 계속 고쳐야 함 |
| 5 | **IP 변경 시 DB 도 갱신** | 관제 → 로봇 관리 → IP 수정 |
| 6 | 현장 공유기 설정 시 **2.4GHz 활성화 확인** | 5GHz 전용이면 로봇이 못 붙음 |
| 7 | **고정 IP USIM 은 공인/사설 여부 확인** | 나중에 바꾸려면 상품 변경 필요 |

# 14. 확인 명령 모음

```cmd
netsh wlan show interfaces              현재 연결 AP·BSSID·밴드·채널
netsh wlan show networks mode=bssid     주변 AP 전체
ping <IP>                               도달 확인
arp -a                                  같은 세그먼트에서 본 장비
ipconfig /all                           내 IP·게이트웨이·MAC
```

```powershell
Get-NetIPAddress -AddressFamily IPv4        IP 목록
Get-NetRoute -AddressFamily IPv4            라우팅
Find-NetRoute -RemoteIPAddress <IP>         특정 IP 경로

# 로봇 상태 종합 (위치추정·잭·랙검출)
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --ip <로봇IP>
```
