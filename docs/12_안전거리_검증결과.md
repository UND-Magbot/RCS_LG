## 5. 발견된 결함 — 판정이 실시간을 따라가지 못함

### 5-1. 증상
안전존 워커가 WS 로 받은 점군을 **받은 순서대로 전부 처리**한다. 한 스캔 처리에 드는
시간(밴드 계산·맵 벽 대조·설정 파일 읽기·REST 호출)이 스캔 주기(0.53초)를 넘으면
큐가 쌓이고, **과거 상황으로 현재를 판단**하게 된다.

측정된 지연 (백엔드 로그 값 ↔ 그 값의 실제 발생 시각 대조):
```
14:11:22  앞 2.76 m  →  실제 시각 14:11:20.2   지연 1.8초
14:11:28  앞 1.82 m  →  실제 시각 14:11:22.3   지연 5.7초
14:11:35  앞 0.95 m  →  실제 시각 14:11:25.5   지연 9.5초
14:11:38  앞 0.74 m  →  실제 시각 14:11:26.5   지연 11.5초
```
**지연이 누적되어 계속 커진다.**

### 5-2. 실제 사고 — 7회차 오정지
```
14:39:59  [safety] RED 후보 1/3 — 앞 0.96 m, 지령 0.10 m/s (추정 +0.57)
14:40:00  7회차 출발 — 로봇은 장애물에서 3.2 m 떨어진 시작점에 있다
14:40:01  [safety] ★ RED — 앞 0.91 m 정지 | 로봇(6.85,9.04) 포즈나이0.30s
                    점=맵(7.82,9.92) 중심거리1.29m        ← 직전 회차 상황에 대한 판정
14:40:02  로봇 0.27 m 전진 후 정지 (측정 도구 기록: edge 3.07 m 로 장애물은 멀리 있음)
```
로봇이 이미 복귀해 3.2 m 떨어져 있는데, 밀린 판정이 뒤늦게 확정되어 속도 0 이 걸렸다.
**현장에서 보고된 "아무것도 없는데 멈칫거린다" 의 메커니즘이 이것이다.**

### 5-3. 방증
- 같은 WS 를 구독하되 계산이 가벼운 측정 도구(`safety_probe.py`)는 **밀리지 않았다**
  (스캔 지연 변동폭 195 ms) → 전송 문제가 아니라 **처리 부하** 문제
- `포즈가 낡아 판정 보류 (1.24~2.35초 > 1.2)` 로그가 반복 발생
- RED 판정 시 `포즈나이 0.21~0.35초`

### 5-4. 조치 (`safety_zone.py`)
```python
SCAN_MAX_LAG_SEC = 0.5      # 이보다 밀린 스캔은 판정에 쓰지 않는다

# 점군 처리 진입부 — 무거운 계산 전에 버린다
stamp = msg.get("stamp")
if stamp:
    d = time.time() - float(stamp)
    if scan_offset is None or 주기경과:  scan_offset = d
    elif d < scan_offset:                scan_offset = d
    if d - scan_offset > SCAN_MAX_LAG_SEC:
        continue            # 버리는 비용이 0 이라 큐가 빠르게 소진된다
```
- 로봇 시계가 서버보다 **1.1초 빠르다**(실측). 그래서 `stamp` 를 그대로 빼지 않고
  **관측 차이의 최솟값**을 오프셋으로 잡아 상대 지연만 본다.
- 계속 밀리는 상황이면 오프셋도 같이 내려가 상대 지연이 0 이 되므로,
  **전부 버려서 판정이 멈추는 일은 생기지 않는다**(자기 보정).
- **판정 임계값(`yellow_m` / `red_m` / `band_half_w` / `RED_CONFIRM_TICKS`)은 변경하지 않았다.**

## 6-2. 안전영역 — 랙 적재 상태 (LG2 대차, 11회)

수정 후 공차 10회와 **완전히 같은 조건**에서, LG2 대차를 실을 때만 달리했다.
(2026-09-15 16:15~16:30, 로봇 192.168.30.130, 속도 지령 0.5 m/s)

### 6-2-1. 랙을 실었을 때 로봇이 스스로 커진다

로봇은 잭업하면 **자기 풋프린트를 랙 크기까지 넓혀서 보고**하고(`supportsDynamicFootprints`),
백엔드 안전존은 DB 플래그가 아니라 이 보고값(`/robot_model`)을 그대로 읽는다.
잭을 내렸다 올려 두 상태를 연속으로 찍은 로그가 근거다.

```
09-15 16:13:01  [safety] 192.168.30.130 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.230 m (폭 0.46)   ← 잭다운(공차)
09-15 16:13:24  [safety] 192.168.30.130 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.400 m (폭 0.8)    ← 잭업(LG2 적재)
```

| | 공차 | LG2 적재 |
|---|---|---|
| 풋프린트 | 0.748 × 0.460 m | 0.748 × **0.800** m |
| 앞끝 | 0.379 m | **0.379 m (그대로)** |
| 반폭 | 0.230 m | **0.400 m** |
| 감지 밴드 반폭 `max(0.2, 반폭)` | ±0.230 m | **±0.400 m** |

**앞끝이 안 변하는 이유**: LG2 랙의 풋프린트 길이는 0.705 m(다리 간격 0.545 + 여유 0.08×2)로
로봇 전장 0.748 m보다 **짧다**. 그래서 앞으로 튀어나오는 것은 여전히 로봇 코다.
→ **전방 정지 거동은 공차와 같고, 좌우로 감시하는 폭만 0.23 → 0.40 m 로 넓어진다.**

※ 참고 — S300 랙(0.765×0.765)은 풋프린트가 0.95×0.95 라 앞끝이 0.475 m 로 커진다.
  즉 앞끝 변화 여부는 **랙 길이가 로봇보다 긴가**로 갈린다.

### 6-2-2. 랙이 실제로 LG2인지 확인한 근거

주행 전 점군을 로봇 좌표계로 변환해 다리 4개의 위치를 쟀다.

```
전좌 (+0.27, +0.31)   전우 (+0.28, -0.32)
후좌 (-0.29, +0.31)   후우 (-0.29, -0.33)
  → 다리 중심 간격  좌우 0.63 m × 전후 0.57 m
  → LG2 도면값 0.64 × 0.545 와 일치 (S300 0.765×0.765 아님)
```

로봇의 `rack.specs` 도 시험 동안만 LG2 로 바꿨고(시험 후 S300 원복 완료),
잭업 무게는 `weight 22`(공차 0) 로 적재를 확인했다.

## 8. 한계 — LG 회신에 반드시 포함할 것

1. **인증 안전기능이 아니다.** 탑재 라이다는 항법용(PACECAT LDS-50C-E)이며
   IEC 61496-3 인증 안전 라이다가 아니다(제조사의 안전 라이다는 별도 LSS 시리즈).
   로봇 펌웨어에도 거리 기반 안전영역 설정 항목이 존재하지 않는다(설정 49개 전수 확인).
   서행·정지는 **관제 서버가 점군을 받아 판정하는 소프트웨어 보조 정지**다.
2. **사람과 물체를 구분하지 못한다.** `supportsVisionBasedDetector: false`,
   뎁스 카메라 없음. "작업자 감지" 가 아니라 **"장애물 감지"** 다.
3. **판정 영역은 전방 직사각형 밴드**다(부채꼴 아님). 좌우 ±0.23 m(공차) /
   ±0.475 m(적재) 밖은 판정하지 않으며, **로봇 내장 회피가 담당**한다.
4. **경유지를 쓰지 않는 구간은 로봇이 먼저 회피**한다(§2 참조).
   "3 m 서행 / 1 m 정지" 가 보장되는 것은 `detour_tolerance: 0` 인 경유지 주행 구간이다.
5. **정지 판정 후에도 확인 구간(연속 3회) 동안 0.10 m/s 로 전진**한다.
   그래서 실제 정지는 판정 임계(1.0 m)보다 평균 0.29 m 안쪽이다.

### 랙 적재 상태로 시험할 때 (§6-2 재현)

로봇의 `rack.specs` 가 S300 이면 **LG2 랙을 실어도 로봇이 S300 크기로 풋프린트를 보고**한다.
그래서 시험 동안만 로봇 설정을 바꾼다. **서버 코드·설정 파일은 건드리지 않는다.**

```bash
# 1) 현재 설정 백업
curl -s http://<IP>:8090/system/settings/user -o _logs/rack_backup/user_settings_before.json

# 2) rack.specs 를 LG2 로 (BackEnd/app/constants/rack_specs.py 의 RACK_SPECS['LG2'] 값)
curl -X PATCH http://<IP>:8090/system/settings/user -H "Content-Type: application/json"      -d '{"rack.specs":[{"width":0.64,"depth":0.545,"margin":[0.08,0.08,0.08,0.08], ...}]}'

# 3) 잭다운 → 잭업 (풋프린트 재계산 유도)
curl -X POST http://<IP>:8090/services/jack_down -d '{}'
curl -X POST http://<IP>:8090/services/jack_up   -d '{}'

# 4) backend.log 에 두 줄이 연속으로 찍히는지 확인 — 이게 적재 반영 증거다
#    ... 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.230 m (폭 0.46)   ← 잭다운
#    ... 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.400 m (폭 0.8)    ← 잭업

# 5) 시험 실행 → 6) rack.specs 를 백업본으로 원복
```

**주의**
- 시험 중 **맵 동기화 금지** — `rack.specs` 가 DB 의 POI `rack_size` 기준으로 재생성돼 원복된다.
- 잭업 직후 `/robot_model` 은 **과도값**을 한 번 내보낸다(이번 시험 16:10:16 에 반폭 0.330).
  0.08 Hz 라 안정값까지 최대 ~12초 기다리고, 백엔드 로그로 확인할 것.
- 앞 장애물이 **맵에 있는 벽이면 백엔드가 건너뛴다.** 시험 전에 확인:
  `map_image.is_wall_at(meta, x, y, 0.25)` 가 `False` 여야 한다.
