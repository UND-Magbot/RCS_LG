## 5. 발견된 결함 — 판정이 실시간을 따라가지 못함

### 5-1. 증상
안전존 워커가 WS 로 받은 점군을 **받은 순서대로 전부 처리**한다. 한 스캔 처리에 드는
시간(밴드 계산·맵 벽 대조·설정 파일 읽기·REST 호출)이 스캔 주기(0.53초)를 넘으면
큐가 쌓이고, **과거 상황으로 현재를 판단**하게 된다.

측정된 지연 (백엔드 로그 값 ↔ 그 값의 실제 발생 시각 대조):
```
14:11:22  앞 2.76 m  →  실제 시각 14:11:20.2   지연 1.8초
14:11:28  앞 1.82 m  →  실제 시각 14:11:22.3   지연 5.7초
14:11:35  앞 0.95 m  →  실제 시각 14:11:25.5   지연 9.5초
14:11:38  앞 0.74 m  →  실제 시각 14:11:26.5   지연 11.5초
```
**지연이 누적되어 계속 커진다.**

### 5-2. 실제 사고 — 7회차 오정지
```
14:39:59  [safety] RED 후보 1/3 — 앞 0.96 m, 지령 0.10 m/s (추정 +0.57)
14:40:00  7회차 출발 — 로봇은 장애물에서 3.2 m 떨어진 시작점에 있다
14:40:01  [safety] ★ RED — 앞 0.91 m 정지 | 로봇(6.85,9.04) 포즈나이0.30s
                    점=맵(7.82,9.92) 중심거리1.29m        ← 직전 회차 상황에 대한 판정
14:40:02  로봇 0.27 m 전진 후 정지 (측정 도구 기록: edge 3.07 m 로 장애물은 멀리 있음)
```
로봇이 이미 복귀해 3.2 m 떨어져 있는데, 밀린 판정이 뒤늦게 확정되어 속도 0 이 걸렸다.
**현장에서 보고된 "아무것도 없는데 멈칫거린다" 의 메커니즘이 이것이다.**

### 5-3. 방증
- 같은 WS 를 구독하되 계산이 가벼운 측정 도구(`safety_probe.py`)는 **밀리지 않았다**
  (스캔 지연 변동폭 195 ms) → 전송 문제가 아니라 **처리 부하** 문제
- `포즈가 낡아 판정 보류 (1.24~2.35초 > 1.2)` 로그가 반복 발생
- RED 판정 시 `포즈나이 0.21~0.35초`

### 5-4. 조치 (`safety_zone.py`)
```python
SCAN_MAX_LAG_SEC = 0.5      # 이보다 밀린 스캔은 판정에 쓰지 않는다

# 점군 처리 진입부 — 무거운 계산 전에 버린다
stamp = msg.get("stamp")
if stamp:
    d = time.time() - float(stamp)
    if scan_offset is None or 주기경과:  scan_offset = d
    elif d < scan_offset:                scan_offset = d
    if d - scan_offset > SCAN_MAX_LAG_SEC:
        continue            # 버리는 비용이 0 이라 큐가 빠르게 소진된다
```
- 로봇 시계가 서버보다 **1.1초 빠르다**(실측). 그래서 `stamp` 를 그대로 빼지 않고
  **관측 차이의 최솟값**을 오프셋으로 잡아 상대 지연만 본다.
- 계속 밀리는 상황이면 오프셋도 같이 내려가 상대 지연이 0 이 되므로,
  **전부 버려서 판정이 멈추는 일은 생기지 않는다**(자기 보정).
- **판정 임계값(`yellow_m` / `red_m` / `band_half_w` / `RED_CONFIRM_TICKS`)은 변경하지 않았다.**

## 6-2. 안전영역 — 랙 적재 상태 (LG2 대차, 11회)

수정 후 공차 10회와 **완전히 같은 조건**에서, LG2 대차를 실을 때만 달리했다.
(2026-09-15 16:15~16:30, 로봇 192.168.30.130, 속도 지령 0.5 m/s)

### 6-2-1. 랙을 실었을 때 로봇이 스스로 커진다

로봇은 잭업하면 **자기 풋프린트를 랙 크기까지 넓혀서 보고**하고(`supportsDynamicFootprints`),
백엔드 안전존은 DB 플래그가 아니라 이 보고값(`/robot_model`)을 그대로 읽는다.
잭을 내렸다 올려 두 상태를 연속으로 찍은 로그가 근거다.

```
09-15 16:13:01  [safety] 192.168.30.130 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.230 m (폭 0.46)   ← 잭다운(공차)
09-15 16:13:24  [safety] 192.168.30.130 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.400 m (폭 0.8)    ← 잭업(LG2 적재)
```

| | 공차 | LG2 적재 |
|---|---|---|
| 풋프린트 | 0.748 × 0.460 m | 0.748 × **0.800** m |
| 앞끝 | 0.379 m | **0.379 m (그대로)** |
| 반폭 | 0.230 m | **0.400 m** |
| 감지 밴드 반폭 `max(0.2, 반폭)` | ±0.230 m | **±0.400 m** |

**앞끝이 안 변하는 이유**: LG2 랙의 풋프린트 길이는 0.705 m(다리 간격 0.545 + 여유 0.08×2)로
로봇 전장 0.748 m보다 **짧다**. 그래서 앞으로 튀어나오는 것은 여전히 로봇 코다.
→ **전방 정지 거동은 공차와 같고, 좌우로 감시하는 폭만 0.23 → 0.40 m 로 넓어진다.**

※ 참고 — S300 랙(0.765×0.765)은 풋프린트가 0.95×0.95 라 앞끝이 0.475 m 로 커진다.
  즉 앞끝 변화 여부는 **랙 길이가 로봇보다 긴가**로 갈린다.

#### 랙 종류별 — LGIT 제출은 **LG 랙** 기준이다

현장에 실제로 들어가는 건 LG 랙이다. 등록된 `rack.specs`(`BackEnd/app/constants/rack_specs.py`)
로 계산하면 이렇다. 계산식은 `풋프린트 = width + 2×margin`, `감지 폭 = max(0.4, 풋프린트 폭)`.

| 랙 | `rack.specs` | 랙 풋프린트 | 앞끝 | 감지 폭 |
|---|---|---|---|---|
| **LG** (현장) | 0.700 × 0.500, margin 0.090 | 0.880 × 0.680 | **0.379** (로봇 코) | **0.880 m** |
| LG2 (이번 시험) | 0.640 × 0.545, margin 0.080 | 0.800 × 0.705 | **0.379** (로봇 코) | 0.800 m |
| S300 | 0.765 × 0.765, margin 0.0925 | 0.950 × 0.950 | 0.475 (랙) | 0.950 m |
| S600 | 0.830 × 0.870, margin 0.100 | 1.030 × 1.070 | 0.535 (랙) | 1.030 m |

**계산식이 실측으로 확인됐다** — LG2 는 `0.640 + 2×0.080 = 0.800` 인데, 로봇이 실제로
보고한 값도 `반폭 0.400 (폭 0.8)` 이었다(위 16:13:24 로그). 같은 식을 LG 에 적용한 값이
0.880 이다. LG 수치 자체는 **계산값이고 실측은 아니다.**

**그래도 전방 수치는 LG 에 그대로 쓸 수 있다.** LG 랙 길이 0.680 m 역시 로봇 전장
0.748 m 보다 짧아 **앞끝이 0.379 로 동일**하기 때문이다. 랙이 바뀌어 달라지는 것은
좌우 감지 폭뿐이다(0.800 → 0.880). 그래서 §6-2-3 의 서행·정지·실제 정지 수치는
LG 랙 기준 도면에 그대로 싣는다.

## 6-3. 가감속 부드러움 — 정면 접근 vs 측면 돌발 (2026-09-15, 3라운드 22회)

> **왜 쟀나**
> 대차에 싣는 제품이 충격에 민감하다. 주행 중 '멈칫' 은 제품 손상으로 이어지므로
> 반드시 없애야 한다(속도가 느려졌다 빨라지는 것 자체는 무관). 육안으로는
> "좀 덜컹인다" 로 끝나 설정을 바꿨을 때 좋아졌는지 비교가 안 되므로,
> 로봇이 직접 보고하는 `/motion_metrics`(10 Hz, `linear_velocity`/`linear_acc`)
> 를 기록해 **가속도 크기로 판정**했다.

### 6-3-1. 시험 구성

로봇 192.168.30.130 (longjack, 랙 미적재). **서버 코드도 로봇 설정도 바꾸지 않았다.**
주행 속도만 인자로 줬고, 끝나면 안전존이 자동 복구한다.

| | 1라운드 | 2라운드 | 3라운드 |
|---|---|---|---|
| 목적 | 정면 접근 기준선 | 측면 돌발 | 속도 0.7 검증 |
| 속도 | 0.8 m/s | 0.8 m/s | 0.7 m/s |
| 회차 | 10/10 성공 | 7회 후 중단 | 5/5 성공 |
| 사람 개입 | 없음 | 4회 | 2회 (4·5회차) |

판정 기준: **덜컹 = |감속| > 1.0 m/s² 인 연속 구간 수** (샘플 수가 아니라 구간 수),
**멈칫 = 주행 구간 안에서 v < 0.05 m/s 로 떨어진 구간 수** (출발 전·최종 정지는 제외).

### 6-3-2. 정면 접근 — 문제 없음

| 지표 (1라운드 10회) | 최소 | 최대 | 평균 | 편차 |
|---|---|---|---|---|
| YELLOW 진입 | 2.639 | 2.967 | 2.856 | 0.098 |
| RED 진입 | 0.913 | 0.983 | **0.957** | 0.018 |
| 최종 정지 | 0.552 | 0.800 | **0.719** | 0.064 |
| 임계후 전진 | 0.157 | 0.395 | 0.237 | 0.063 |

```
감속 피크 최대   0.92 m/s²   ← 로봇 제동 한계 2.0 의 46%
감속 p95 평균    0.59
가속 피크        0.52
덜컹 (>1.0)      0 회 / 10회
주행 중 멈칫      0 회 / 10회
```

속도 흐름이 계단식으로 내려간다(`0.77 → 0.71 → 0.51`). 한 번에 떨어지지 않는다.
3라운드 기준선 3회도 같다 — 감속 0.55~0.98, 덜컹 0, 멈칫 0.

**즉 정면에서 장애물에 접근하는 정상 주행은 부드럽다. 로봇이 급감속을 쓰지 않는다.**

### 6-3-3. 측면 돌발 — 여기서 급정지가 난다

| | 정면 접근 | 측면 돌발 |
|---|---|---|
| 감속 피크 최대 | **0.92 m/s²** | **2.16 m/s²** |
| 덜컹 (>1.0) | 0회 | **4회** |
| RED 감지 거리 | 0.913~0.983 | **0.707~0.931** |
| 임계후 전진 | 0.157~0.395 | **0.455~0.646** |
| 최종 정지 | 0.552~0.800 | **0.252~0.285** |

2라운드에서도 사람이 안 들어온 회차(3·4·7)는 감속 0.63~0.72 로 부드러웠다.
**같은 설정·같은 로봇인데 접근 방향만으로 3배 갈린다.**

원인은 RED 감지 거리에 그대로 드러난다 — 측면 돌발은 **처음 잡힌 순간 이미
RED(1.0 m) 안쪽**이라 `0.50 → 0.30 → 0.10` 단계를 밟을 거리 자체가 없다.
정면은 2.6~2.9 m 에서 YELLOW 로 먼저 잡혀 단계를 다 밟고 내려온다.

> **이것은 결함이 아니다.** 예고 없이 나타난 장애물 앞에서 최대 제동을 쓰는 것은
> 정상 동작이다. 문제는 그 제동이 제품에 주는 충격이며, 대책은 §6-3-5 에 정리했다.

### 6-3-4. 주행 속도를 낮춰도 효과가 없다 (실측)

**개입 없는 기준선끼리 비교 — 이것이 유효한 대조군이다.**

| | 0.8 m/s (10회) | 0.7 m/s (3회) | 차이 |
|---|---|---|---|
| RED 진입 | 0.947 | 0.917 | — |
| 최종 정지 | **0.719** | **0.699** | **0.020 m** |
| 임계후 전진 | 0.237 | 0.218 | 0.019 m |
| 감속 피크 | 0.50~0.92 | 0.55~0.98 | 없음 |
| 덜컹 / 멈칫 | 0 / 0 | 0 / 0 | 없음 |

속도를 12.5% 낮췄는데 **정지거리는 2 cm(2.8%) 만 줄었다.**

이유는 **RED 를 통과하는 순간의 실제 속도**에 있다.

```
RED 통과 시점 속도 (실측)
  1라운드 정면 0.8      0.090 ~ 0.280   평균 0.116 m/s
  2라운드 측면 0.8      0.100 ~ 0.370   평균 0.224 m/s
  3라운드 정면 0.7      0.100 ~ 0.500   평균 0.346 m/s
```

**주행 속도가 아니라 서행 단계가 RED 시점 속도를 정한다.** 그래서 기본 속도를
바꿔도 정지거리가 안 바뀐다. 0.8 → 0.7 변경은 **안전·충격 어느 쪽에도 효과가 없다.**

### 6-3-5. 임계후 전진의 정체 — 제동거리가 아니다

임계후 전진 0.455~0.646 m 를 제동거리로 보면 안 된다.
0.36 m/s 로 0.486 m 를 가려면 **1.35초**가 걸리고, 그중 제동거리는 0.03 m 뿐이다.
**나머지 0.45 m 는 정지를 확정하기까지 기다리는 동안 굴러간 거리다.**

`confirm_allowed()` 가 원인이다.
```
v = 0.36 → stop = (0.68 + 2×0.53)×0.36 + 0.36²/4 = 0.658
           0.658 ≤ red_m 1.0 × 0.7  → True  → 3틱(1.06초) 확인 후 정지
```
속도가 0.381 m/s 아래면 "여유 있다" 고 보고 3틱을 더 확인한다.
정면 접근은 RED 가 0.95 m 에서 잡히니 여유가 맞다.
**측면 돌발은 0.707 m 에서 잡혀 여유가 없는데도 똑같이 1.06초를 기다린다.**

검증: 1라운드 0.116 × (0.68 + 1.06) = 0.202 m, 실측 평균 0.237 m — 일치.

### 6-3-6. 대책 후보와 판단

| 후보 | 판단 | 근거 |
|---|---|---|
| 기본 속도 0.8 → 0.7 | **효과 없음. 기각** | §6-3-4 실측, 정지거리 차이 2 cm |
| `acc_smoother.smooth_level` → `higher` | **기각** | 비상 제동까지 뭉갠다. 감속이 0.6 까지 깎이면 0.77 m/s 기준 정지거리 1.018 m 로 **red_m 1.0 m 초과**. 게다가 실측 감속 피크가 0.92 로 이미 한계의 46% 라 완화할 여지가 없다 |
| `max_forward_decel` −2.0 → −1.2 | **유력. 미검증** | 정면 13회 감속 피크가 전부 0.98 이하라 **평상시에는 제한선에 안 닿는다.** 급정지의 2.16 만 1.2 로 잘린다(−44%). 제동거리 증가는 0.031 → 0.054 m 로 **+0.023 m** |
| 측면 예비 감속 (신규) | **검토 필요** | 밴드 바깥 좌우 0.23~0.6 m 에 물체가 있으면 미리 0.5 로 낮춘다. 사람이 좁은 통로에서 하는 행동. 현장 영상의 73~76초·84~90초(옆에 세워둔 대차·팔레트) 구간과 같은 뿌리 |
| 밴드를 먼 쪽만 좁히는 사다리꼴 | **철회** | 좌우 0.40~0.43 m 물체를 1.09~1.38 m 에서야 감지 → 0.8 m/s 정지거리 1.05~1.40 m 와 겹쳐 충돌. 랙 반폭이 0.440 이라 그 위치 물체는 실제 간섭 대상이다 |

### 6-3-7. 이 시험의 한계 — 그대로 남긴다

1. **수정 전 기준선이 없다.** `/motion_metrics` 계측을 설정 변경 이후에 넣었다.
   "좋아졌다" 가 아니라 **"지금 절대값이 기준 안에 있다"** 까지만 말할 수 있다.
2. **개입 표본이 6회뿐이라 감속 피크를 못 가른다.** 2R-6(0.8, RED 0.707)이 0.69 인데
   2R-1·2(0.8, RED 0.76·0.78)는 2.09~2.16 이다. 개입 거리가 0.39~0.93 m 로
   들쭉날쭉해 데이터가 섞였다. **다음에는 개입 거리를 2.0~2.5 m 로 통제**해야 한다.
3. **10 Hz 라 0.1초보다 짧은 사건은 못 본다.** 2.0 m/s² 로 0.8→0.5 는 0.15초라
   1~2 샘플에 걸린다. 피크가 실제보다 낮게 나올 수 있으므로 **절대 기준이 아니라
   설정 변경 전후 비교에만 쓸 것.**
4. 3라운드 5회차는 사람이 **0.387 m** 에서 들어와 비상취소가 걸렸다(정지 0.300 m).

## 8. 한계 — LG 회신에 반드시 포함할 것

1. **인증 안전기능이 아니다.** 탑재 라이다는 항법용(PACECAT LDS-50C-E)이며
   IEC 61496-3 인증 안전 라이다가 아니다(제조사의 안전 라이다는 별도 LSS 시리즈).
   로봇 펌웨어에도 거리 기반 안전영역 설정 항목이 존재하지 않는다(설정 49개 전수 확인).
   서행·정지는 **관제 서버가 점군을 받아 판정하는 소프트웨어 보조 정지**다.
2. **사람과 물체를 구분하지 못한다.** `supportsVisionBasedDetector: false`,
   뎁스 카메라 없음. "작업자 감지" 가 아니라 **"장애물 감지"** 다.
3. **판정 영역은 전방 직사각형 밴드**다(부채꼴 아님). 좌우 ±0.23 m(공차) /
   ±0.475 m(적재) 밖은 판정하지 않으며, **로봇 내장 회피가 담당**한다.
4. **경유지를 쓰지 않는 구간은 로봇이 먼저 회피**한다(§2 참조).
   "3 m 서행 / 1 m 정지" 가 보장되는 것은 `detour_tolerance: 0` 인 경유지 주행 구간이다.
5. **정지 판정 후에도 확인 구간(연속 3회) 동안 0.10 m/s 로 전진**한다.
   그래서 실제 정지는 판정 임계(1.0 m)보다 평균 0.29 m 안쪽이다.

### 랙 적재 상태로 시험할 때 (§6-2 재현)

로봇의 `rack.specs` 가 S300 이면 **LG2 랙을 실어도 로봇이 S300 크기로 풋프린트를 보고**한다.
그래서 시험 동안만 로봇 설정을 바꾼다. **서버 코드·설정 파일은 건드리지 않는다.**

```bash
# 1) 현재 설정 백업
curl -s http://<IP>:8090/system/settings/user -o _logs/rack_backup/user_settings_before.json

# 2) rack.specs 를 LG2 로 (BackEnd/app/constants/rack_specs.py 의 RACK_SPECS['LG2'] 값)
curl -X PATCH http://<IP>:8090/system/settings/user -H "Content-Type: application/json"      -d '{"rack.specs":[{"width":0.64,"depth":0.545,"margin":[0.08,0.08,0.08,0.08], ...}]}'

# 3) 잭다운 → 잭업 (풋프린트 재계산 유도)
curl -X POST http://<IP>:8090/services/jack_down -d '{}'
curl -X POST http://<IP>:8090/services/jack_up   -d '{}'

# 4) backend.log 에 두 줄이 연속으로 찍히는지 확인 — 이게 적재 반영 증거다
#    ... 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.230 m (폭 0.46)   ← 잭다운
#    ... 자기 크기 갱신 — 앞끝 0.379 m / 반폭 0.400 m (폭 0.8)    ← 잭업

# 5) 시험 실행 → 6) rack.specs 를 백업본으로 원복
```

**주의**
- 시험 중 **맵 동기화 금지** — `rack.specs` 가 DB 의 POI `rack_size` 기준으로 재생성돼 원복된다.
- 잭업 직후 `/robot_model` 은 **과도값**을 한 번 내보낸다(이번 시험 16:10:16 에 반폭 0.330).
  0.08 Hz 라 안정값까지 최대 ~12초 기다리고, 백엔드 로그로 확인할 것.
- 앞 장애물이 **맵에 있는 벽이면 백엔드가 건너뛴다.** 시험 전에 확인:
  `map_image.is_wall_at(meta, x, y, 0.25)` 가 `False` 여야 한다.
