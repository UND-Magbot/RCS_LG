### Claude에게 시킬 경우

```

```

**Claude에게 주는 지시 (이 문단은 Claude가 읽을 것):**
- `[확인]` 명령은 **실제로 실행**해서 결과를 보고할 것. 실행 없이 "완료"라고 하지 말 것
- **STEP 1(물리 조치)은 사람이 해야 한다.** 완료됐는지 먼저 물어볼 것
- 맵핑·POI 등록은 **관제 화면(브라우저)에서 사람이 하는 작업**이다. Claude는 결과 검증을 맡는다
- 로봇을 움직이는 명령은 **사람이 로봇을 볼 수 있는 상태인지 확인**하고 실행할 것
- 실패하면 다음으로 넘어가지 말고 PART 3 문제 해결을 먼저 볼 것

### 왜 맵을 다시 따는가 (배경)

2026-08-13에 아래 문제가 확인됐습니다.

```
lidar_matched: False           라이다는 정상 회전(스캔 데이터 수신 중)
lidar_matching_score: 0.21     그런데 지도와 맞는 지점이 하나도 없음
good_constraint_count: 0
alerts: []                     하드웨어 경고 없음
```

**센서 고장이 아니라 "로봇이 자기 위치를 잘못 알고 있는 상태"** 입니다.
원인으로 지목된 것: **충전소(C1)가 앵커로 고정돼 있지 않아 물리적으로 밀림.**
충전소는 위치재조정의 **기준점**이라, 여기가 움직이면 이후 모든 좌표가 그만큼 어긋납니다.

그 결과 오늘 이런 일이 있었습니다.
- 랙이 R1 제자리에 있는데 로봇이 R1 정중앙까지 가서도 **랙 검출 0**
- 랙을 든 채 이동해 **랙이 두 번 끌려감**
- 세트가 연속 실패로 중단

| 이름 | 타입 | 비고 |
|---|---|---|
| `C1` | charging | 충전소 |

## STEP 5 — 로봇에 동기화

```
맵 관리 → 동기화 → 대상 로봇 선택 → 실행
```

동기화가 하는 일:
1. 맵 데이터 전송 + 로봇의 현재 맵으로 설정 (**LTE 지연 대비 최대 3회 재시도**)
2. overlay 전송 (충전소·가상벽 + **Shelves Point**)
3. **`rack.specs` 전송** — 맵의 POI 들이 가진 `rack_size` 종류만큼만
4. 유휴(충전소 도킹) 로봇은 **충전소 기준으로 자동 위치재조정**, 작업 중 로봇은 포즈 저장·복원

> **Shelves Point(`type=34`, `subtype=rack`)** 가 overlay 에 있어야 `align_with_rack` 이 동작합니다.
> 동기화가 자동으로 넣어줍니다.
> 반영 확인은 `create_time` 이 아니라 **`last_modified_time`** 으로 보세요(덮어쓰기라 create_time 은 안 바뀜).

### [확인]
```powershell
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py
```

**반드시 확인할 것**
- `위치추정 [정상] lidar_matched=True` ← ★ **이게 False면 다음 단계로 가지 마세요**
- `랙 위치 R1 ... rack_size=LG2`

그리고 로봇에 들어간 규격 확인:
```powershell
.\BackEnd\venv\Scripts\python.exe -c "import sys; sys.argv=['x']; sys.path.insert(0,'scripts'); import rack_bench as m; [print(' ', {k:s.get(k) for k in ('width','depth','leg_size','foot_radius','margin')}) for s in m.Robot('192.168.30.100').get_rack_specs()]"
```
**LG2 (0.64 × 0.545) 하나만** 나와야 합니다. 2개 이상이면 STEP 3으로 돌아가세요.

## 7-1. `robot_check.py` — 로봇 상태 진단

REST 로는 못 읽는 값들을 WebSocket 으로 모아 한 화면에 보여줍니다.
**테스트 시작 전에 반드시 한 번 돌리세요.**

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py           # 한 번
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --watch   # 3초마다
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --rack    # 랙 검출까지
.\BackEnd\venv\Scripts\python.exe scripts\robot_check.py --ip <로봇IP>
```

```
==================================================================
  로봇 192.168.30.100   14:39:35
==================================================================
  위치추정  [문제]  lidar_matched=False  score=0.306
            reliable=True quality=10 wheel_slipping=False
            ↳ 로봇이 자기 위치를 잘못 알고 있을 수 있습니다.
  섀시      [정상]  비상정지=False 제어모드=auto 바퀴과부하=False
  잭        [정상]  내려감   state=hold progress=0.0 weight=0
  현재위치  (+0.765, -28.552)  ori=+245.8도
            R1 까지 165cm, 방향차 +151.3도
  랙 위치   R1  (-0.015, -30.008) ori=+94.5도  rack_size=LG2
==================================================================
```

| 항목 | 정상 | 문제일 때 |
|---|---|---|
| **`lidar_matched`** | `True` | ★ `False` 면 **로봇이 자기 위치를 잘못 앎.** 이 상태로는 어떤 테스트도 무의미 |
| `lidar_matching_score` | 높을수록 좋음 | 2026-08-13 문제 상황은 0.21~0.37 |
| 섀시 | auto / 비상정지 False | 비상정지·원격모드면 이동 불가 |
| 잭 `progress` | 0.0 = 내려감 | **1.0 = 올라감.** 이 상태로 이동하면 랙이 끌려감 |
| 잭 `weight` | 0 = 빈 상태 | 65~69 = 랙 적재 중 |
| 랙검출 (`--rack`) | 검출 > 0 | **로봇이 랙 아래에 있어야만 잡힘** |

> `현재위치` 가 안 나오는 것은 정상입니다. `/tracked_pose` 는 로봇이 정지 중이면 발행되지 않습니다.

## 7-2. `rack_bench.py` — 랙 인식 전용 벤치

### 왜 따로 만들었나

배차(세션·워커·경유지)를 거치지 않고 **랙 인식만** 반복합니다.
백엔드가 필요 없고, `zone_guard`·워커 상태 같은 부수효과가 섞이지 않습니다.

**★ 핵심 설계: `align_with_retry` 를 쓰지 않습니다.**
백엔드의 그 함수는 실패 시 재로컬화 → 후진 0.5m → 측면 우회로 4번까지 시도합니다.
그걸 쓰면 1차에 실패해도 3차에 우연히 성공해 **"잘 됩니다"로 보입니다.**
여기서 재려는 건 **1차 성공률**이라, `align_with_rack` 을 딱 1회만 보냅니다.
(`--retry` 옵션을 주면 4단계를 켜되, **몇 차에 성공했는지 따로 기록**합니다)

### 실행

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\rack_bench.py --cond B --trials 20 --retry
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--trials` | 20 | 한 세트당 반복 횟수 |
| `--retry` | 꺼짐 | 4단계 회복 재시도 켜기 (실운영과 동일) |
| `--fail-limit` | 3 | 연속 **최종 실패** 이 횟수면 중지 (1차 실패는 안 셈) |
| `--backoff` | 2 | 반납 후 후진 거리(m) |
| `--cond` | B | 조건 라벨 (A=체인 현상태 / B=기둥 밀착 / C=제거) |
| `--dry-run` | — | 연결·POI 확인만 |

| 키 | 동작 |
|---|---|
| `Enter` | **자동 반복 시작** — N회 돌고 멈춤 → 랙 자세 입력 → 다음 세트 |
| `Space` | 수동: 랙 진입 ↔ 반납 토글 |
| `d` | 랙 치수 측정 (15초) |
| `s` / `2` | 로봇의 현재 규격 조회 / LG2 주입 |
| `w` / `e` | `leg_size` ∓5mm 조정 후 주입 |
| `x` | 이동 취소 (비상) |
| `q` | 종료 + 결과 집계 |

### 세트 = 랙 한 자세

세트가 시작될 때마다 **랙 자세를 직접 타이핑**합니다.

```
  다음 세트의 랙 자세를 적어주세요.
  예)  정위치  /  오른쪽으로 조금 돌림  /  왼쪽으로 많이 돌림

  랙 자세 > _
```

> 자세를 안 적으면 나중에 **어느 자세가 문제였는지 알 수 없습니다.**
> 2026-08-12에 4시간·120회를 돌리고도 50%가 나온 세트의 자세를 몰라 재현을 못 했습니다.
>
> 로봇 자세로 각도를 자동 기록하려 했으나 `/tracked_pose` 가 **정지 상태에서 발행되지 않아**
> 120건 전부 실패했습니다. 라벨이 유일하게 확실한 방법입니다.

**허용 각도를 재려면** — 랙 다리 간격 0.64m 기준, **한쪽 다리만** 옮깁니다.

| 옮기는 거리 | 각도 |
|---|---|
| 2.2 cm | 약 2° |
| 5.6 cm | 약 5° |
| 11 cm | 약 10° |
| 17 cm | 약 15° |

세트를 `0도` → `왼쪽 5도` → `오른쪽 5도` → `왼쪽 10도` → `오른쪽 10도` 순으로.
**작은 각도부터** 하세요. 큰 각도부터 하면 전부 실패해서 아무 기준도 안 남습니다.
각 세트 10회면 충분합니다 (`--trials 10`).

### 결과 읽는 법

```
  세트  랙 자세          1차  2차  3차  4차  최종실패  1차성공률    최종성공률   평균시간
  1    정면              19   1   0   0      0     95%(19/20)  100%(20/20)    30s
  2    왼쪽 5도           17   2   1   0      0     85%(17/20)  100%(20/20)    32s
  3    왼쪽 10도           9   4   3   0      4     45%(9/20)    80%(16/20)    58s

  최종 실패 4건 — 실패 순간 로봇이 랙을 봤는가:
    세트3 [왼쪽 10도] 4차까지 시도 — 검출 0/77회
    세트3 [왼쪽 10도] 4차까지 시도 — 검출 11/84, 중앙 0.710 x 0.580
```

- **1차 성공률** = 랙 인식이 얼마나 깨끗한가 (자세의 좋고 나쁨)
- **최종 성공률** = 실운영에서 실제로 성공하는 비율 ← 현장에서 중요한 숫자
- **뒤 단계(3·4차)에 몰리면** 지금은 되지만 여유가 없다는 뜻
- **"랙을 봤는가"** 가 원인을 가릅니다
  - `검출 0` → 랙을 **아예 못 봄** (위치·자세 문제)
  - `검출 있음 + 치수 큼` → **봤는데 뭔가를 다리로 오인** (체인 등 간섭물)

### 실패 분류

| 분류 | 의미 | 성공률 집계 |
|---|---|---|
| `ok` | 성공 | 포함 |
| `rack` | 진짜 랙 인식 실패 (`fail_reason=501`) | 포함 |
| `timeout` | 시간 초과 | 포함 |
| `jack` | 잭 상태 문제 (`fail_reason=506`) | **제외** |
| `comm` | 통신 두절 | **제외** |

**506(`jack is in up state`)은 랙 인식 실패가 아닙니다.** 잭이 올라가 있어 이동이 거부된 것입니다.
이걸 랙 실패로 세면 성공률이 왜곡됩니다.

## 7-3. `auto_cycle.py` — 고정 경로 배차 사이클

콘솔에서 사람이 하던 것과 **똑같은 API** 를 호출합니다. 백엔드 코드는 안 건드립니다.

```
호출(J1) → 랙 픽업(align + jack_up) → J1 도착
  → 경유지 J2,J3,J4 등록 + 출발
  → 각 도착마다 dwell 초 후 자동 [확인]
  → 마지막 확인 → 복귀(랙 반납 + 충전소) → 다음 사이클
```

### ★ 진짜 목적은 "랙 반납 정확도"

매 사이클마다 랙을 내려놓고 다시 집습니다. 반납 위치가 조금씩 밀리면
**사이클이 갈수록 픽업이 어려워집니다.**

```
  사이클  픽업+이동   →J2   →J3   →J4   복귀   합계
  1           28      45    38    41    112    264
  2           31      44    39    40    115    269
  3           71      46    38    42    118    315
  ------------------------------------------------
  픽업 소요 추세: 28초 → 71초  (증가 ↑)
  ⚠️ 랙 반납 위치가 밀리고 있을 가능성
```

**픽업 시간이 우상향하면** 몇 사이클마다 사람이 랙을 맞춰줘야 하는지가 정해집니다.

> 근본 원인 후보: 복귀 시 랙 반납이 `standard` 이동입니다
> (`dispatch_service._return_to_standby_and_park`). `standard` 는 **로봇**을 POI에 세우는 것이라
> **랙**은 그만큼 어긋난 자리에 놓입니다. → [05_랙인식.md](05_랙인식.md) §6-2 (**미적용**)

### 실행

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --dry-run     # 흐름만 (로봇 안 움직임)
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --rounds 1    # 1사이클, 지켜보며
.\BackEnd\venv\Scripts\python.exe scripts\auto_cycle.py --rounds 10   # 5~10 사이클: 누적 오차
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--rounds` | 1 | 반복 횟수 |
| `--call` | J1 | 호출할 POI **이름** |
| `--route` | J2,J3,J4 | 경유지 POI **이름** 순서 |
| `--dwell` | 5 | 도착 후 자동 확인까지 대기(초) |
| `--rest` | 10 | 사이클 사이 휴식(초) |
| `--pickup-timeout` | 300 | 단계별 한도 — **전부 추정치라 실측 후 조정 필요** |
| `--move-timeout` | 300 | |
| `--return-timeout` | 420 | |

> **★ POI 를 id 가 아니라 이름으로 지정합니다.**
> 2026-08-12 하루에만 POI id 가 두 번 바뀌었습니다(985 → 988 → 1009).
> 이름은 안 바뀌므로 맵을 다시 따도 스크립트를 고칠 필요가 없습니다.

> 로봇 이동 이력(`/chassis/moves`)은 **`page_size` 가 무시되어 전체가 반환**됩니다(실측).
> 그래서 스크립트는 시작 시점의 최신 이동 id 를 기준선으로 잡고 그 이후만 판정합니다.
> (이 처리가 없으면 과거 실패 기록을 현재 상황으로 오인해 즉시 오탐 정지 — 실제로 겪음)

⚠️ **[확인] 버튼은 원래 "이 지점 작업이 끝났고 출발해도 안전하다"는 사람의 승인**입니다.
이 스크립트는 그걸 시간(`--dwell`)으로 대체하므로 **테스트 전용**입니다. 현장 운영에 쓰지 마세요.
**첫 회차는 반드시 옆에서 지켜보고, `Ctrl+C` 로 비상정지가 실제로 되는지 확인하세요.**

## 7-4. `random_cycle.py` — 랜덤 배차 사이클

### 왜 필요한가

정해진 순서만 돌면 **안 밟히는 경로**가 있습니다. 특히 **예약 이어받기**
(`_take_next_reservation_if_continuable`)는 실기에서 거의 안 돌려본 코드라
여기서 버그가 나올 가능성이 높고, **그걸 찾는 것이 이 테스트의 목적**입니다.

```
1. 호출 POI 랜덤 (J1~J4)
2. 랙 픽업 → 도착 → awaiting_next
3. ★ 랜덤 분기 ①  — 콘솔에 [경유지 등록] [종료] 두 버튼이 있는 지점
     (a) 경유지 1~3개 랜덤 등록 → 진행
     (b) 바로 [종료] → 복귀              ← "한 번은 그냥 복귀"
4. 각 경유지 도착 → 랜덤 대기 → [확인]   (낮은 확률로 도중에 [종료])
5. ★ 랜덤 분기 ②  — 마지막 확인 **전에** 확률 p 로 다른 POI 예약
     예약 있음 → 백엔드가 자동 이어받기(충전소·랙반납 생략) → 3번으로 (루프)
     예약 없음 → 복귀 → 사이클 종료
```

> ⚠️ **마지막 [확인] 뒤에 "복귀할지 더 할지" 고르는 화면은 없습니다** (코드·화면 확인함).
> 더 진행하려면 **예약이 미리 걸려 있어야** 합니다. 그래서 분기 ②가 예약을 겁니다.
> 콘솔의 선택 화면은 **`awaiting_next` 시점**(호출 지점 도착 직후)에 있습니다.

```powershell
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --dry-run
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --seed 42 --cycles 3
.\BackEnd\venv\Scripts\python.exe scripts\random_cycle.py --seed 42 --cycles 20
```

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--seed` | 42 | **★ 반드시 고정.** 재현 불가하면 원인 분석이 불가능 |
| `--cycles` | 3 | 사이클 수 |
| `--route-prob` | 0.8 | 분기①에서 [경유지 등록]을 고를 확률 |
| `--reserve-prob` | 0.5 | 마지막 확인 전 예약을 걸 확률 (= 이어받기 유발) |
| `--abort-prob` | 0.1 | 경유지 도중 [종료]를 누를 확률 |
| `--max-waypoints` | 3 | 한 구간의 최대 경유지 수 |
| `--max-legs` | 4 | 한 사이클의 최대 구간 수 (무한루프 방지) |

### 불변식 검사 — 백엔드 결함 후보 찾기

매 시도마다 아래를 확인하고, 위반하면 결과에 표시합니다.

- **보낸 경유지 순서 == 실제 방문 순서**
  (2026-08-11에 동시 [출발] 시 이게 어긋나는 결함을 실제로 잡았습니다 — [06](06_테스트현황과_이슈.md) 결함 A)
- **`is_last` 표시가 실제와 일치**

```
  #   호출   구간                이어받기   총시간   종료 사유
  1   J2    J4→J1                    1      412    예약 없음 → 자동 복귀
  2   J1    (없음)                   0       98    랜덤: 경유지 없이 종료
  3   J3    J1→J2→J4 / J3            2      680    최대 구간 4 도달

  종료 사유 분포:
     3회  랜덤: 경유지 없이 종료
     2회  예약 없음 → 자동 복귀
     1회  예약 있었으나 이어받기 안 됨    ← 원인 확인 필요

  ⚠️ 불변식 위반 2건 — 백엔드 결함 후보:
    - [사이클3] 경유지 순서 불일치 — 보낸 것=J3, 실제 도착=J4
```

**"예약 있었으나 이어받기 안 됨"** 이 나오면 원인을 봐야 합니다:
- 배터리가 `min_battery` 미만 (백엔드가 충전 우선으로 판단)
- 그 POI 가 점유됨
- 이어받기 로직 결함 ← 이걸 찾는 게 목적

> 종료 시 **이 스크립트가 건 예약을 자동으로 정리**합니다. 안 하면 다음 실행에 영향을 줍니다.

## 7-6. 세 스크립트 공통 — 안전 장치

| 상황 | 동작 |
|---|---|
| **비상정지(E-STOP)** | **실패로 세지 않고 대기.** 해제하면 자동으로 이어짐 (최대 5분) |
| **통신 두절** | 대기 후 재개. 성공률 집계에서 제외 |
| **이동 명령 전** | ★ **잭 상태를 로봇에 직접 확인** → 올라가 있으면 먼저 내림 |
| `x` 키 | 현재 이동 취소 |
| `q` 키 | 자동 반복 중단 |
| `Ctrl+C` | 이동 취소(그 자리 정지, 잭 유지) → 세션 정리 → 스냅샷 저장 → 종료 |

**감시 항목**: 경로 계산 실패 연속 발생 / 비상정지 / 원격 모드 전환 / 바퀴 과부하 /
잭 상태로 인한 이동 거부 / 세션 실패 / 단계별 시간 초과

### E-STOP 을 "대기"로 처리하는 이유

백엔드도 사실상 같게 동작합니다. `safe_move` 가 이동 실패 시 **5초 간격으로 최대 200회(≈17분) 재시도**하므로
세션이 죽지 않습니다. 다만 백엔드는 E-STOP 인지 **모르고** 재시도할 뿐이라 화면에 사유가 안 뜹니다.
스크립트는 사유를 정확히 알려주고, 백엔드의 17분보다 먼저 끊도록 **5분**으로 제한합니다.

### ★ 잭 판정 기준은 `progress` 입니다 (`weight` 아님)

```
랙 적재:   progress 1.0, weight 65
내려놓음:  progress 0.0, weight  0
잭만 올림: progress 1.0, weight  0~26   ← weight 로는 구분 불가
```

2026-08-13에 `weight` 로 판정했다가 **"잭은 올라갔는데 랙을 못 받친"** 경우를 '내려감'으로 오판했고,
그 상태로 후진해 **랙을 끌고 간 사고가 두 번** 있었습니다.

또 하나: **HTTP 타임아웃 = 명령 실패가 아닙니다.**
`jack_up` 의 응답을 못 받아도 명령은 실행됐을 수 있습니다. 예외가 나면 단정하지 말고
**로봇에 실제 상태를 물어봐야** 합니다.

# PART 3 — 문제 해결

### 9-1. `lidar_matched=False` 가 안 없어진다
```
1) 로봇을 충전소에 도킹했는지 확인 (도킹 안 하고 재조정하면 더 나빠짐)
2) 위치재조정 재실행
3) 그래도 False면 → 로봇 재부팅 (원격제어 → 시스템 재시작, 약 90초)
     부팅 후 boot_recovery 가 충전소 기준으로 자동 재조정
4) 재부팅해도 False면 → 하드웨어 점검
```
하드웨어 점검용 서비스(로봇에 존재 확인됨):
```
/services/imu/recalibrate            IMU 재보정 (평평한 곳에 정지 상태로)
/services/imu/calibrate_gyro_scale   자이로 스케일
/services/baseboard/power_on_lidar   라이다 전원 재인가
/services/reset_usb_devices          USB 리셋
/services/monitor_recheck_errors     에러 재점검
```
경고 확인: `/alerts` 토픽이 비어 있으면(`[]`) 하드웨어 경고는 없는 것입니다.

### 9-2. 랙 검출이 0
- **로봇이 랙 아래에 있어야 검출됩니다.** 앞에서 1.6m 떨어져 바라보면 안 잡힙니다(실측 확인)
- 랙이 실제로 R1 자리에 있는지 눈으로 확인
- `lidar_matched` 가 False면 로봇이 엉뚱한 데 있는 것 → 9-1

### 9-3. 정렬이 `fail_reason=506` 으로 실패
`jack is in up state` — 잭이 올라가 있어 이동이 거부된 것입니다. **랙 인식 실패가 아닙니다.**
스크립트가 자동으로 잭을 내리고 이어가지만, 반복되면 수동으로 잭 다운 후 재시작하세요.

### 9-4. 정렬이 `fail_reason=501` 로 실패
`rack_detection_error` — **진짜 랙 인식 실패**입니다. 로그의 "랙 관측"을 보세요.
- `검출 0` → 랙을 아예 못 봄 (위치·자세 문제)
- `검출 있음 + 치수가 큼` → 체인 등 간섭물을 다리로 오인
→ 원인·대안은 [05_랙인식.md](05_랙인식.md)

### 9-5. 로봇에 규격이 2개 이상 들어감
맵에 `standby` POI 가 2개 이상이거나 `rack_size` 가 서로 다른 것입니다.
STEP 3 [확인]으로 POI 를 점검하고, 불필요한 standby 를 비활성화한 뒤 다시 동기화하세요.

# PART 4 — 부록: 로봇 수동 확인 (rb-admin)

> 원래 2026-08-11 작성 · **인터넷 없는 TC700(LTE) 망에서 혼자 보는 용도**로 만든 문서.
> ⚠️ **주소는 그때의 LTE 망 기준(`192.168.39.x`)** 입니다. 현재 사무실은 `192.168.30.100` 이니
> 자기 환경의 IP로 바꿔 읽으세요. 망 구성은 [02_네트워크.md](02_네트워크.md).

### A-1. 로봇이 살아있는지 (브라우저 주소창)

| 순서 | 주소 | 정상이면 |
|---|---|---|
| ① | `http://<로봇IP>:8090/` | Device/Maps/Chassis... 링크 목록 |
| ② | `.../device/info` | `longjack`, 펌웨어 `2.12.28` |
| ③ | `.../chassis/current-map` | 맵 id/이름. **404여도 로봇은 정상**(맵만 미설정) |
| ④ | `.../chassis/status` | 정상 JSON = 부팅 완료 |
| ⑤ | `.../battery-state` | 배터리 |

⚠️ 로봇 API는 **http 전용** (https 안 됨)

### A-2. rb-admin — 로봇 수동 운전

```
http://<로봇IP>:8090/rb-admin      로그인 guest@autoxing.com
그래픽 콘솔만: http://<로봇IP>:8090/live
```
할 수 있는 것: 수동 원격조작(조이스틱) · 지도에서 목표 지정 이동 ·
**위치 재조정(Relocate — 지도에서 로봇을 드래그해 실제 위치로)** · 충전소 등록

### A-3. 움직이기 전 안전 점검

- [ ] 로봇 주변에 사람·장애물 없음
- [ ] 비상정지 버튼 위치 파악
- [ ] **잭이 올라가 있는지 눈으로 확인** (랙을 든 상태인지)

잭이 올라간 채로 부팅되면(`jack_in_up_state`) **align/charge 명령이 전부 506으로 거부**됩니다.
rb-admin 에서 잭 다운, 안 되면 `POST /services/jack_down`.

> 잭 상태 판단: `/jack_state` 의 `state:"hold"` 는 **위/아래와 무관**(모터 정지 유지일 뿐).
> 실제 높이는 **`progress`** — `0.0` 완전 내려감 / `1.0` 완전 올라감. (7-6 참조)

명령을 받는데 제자리면 → **위치추정 소실**. rb-admin 에서 수동 Relocate.

### A-4. ⚠️ 하지 말 것 — rb-admin 수동 조작과 관제(배차)를 섞지 말 것

관제 배차는 DB 세션 + 메모리 워커로 로봇 상태를 추적하는데, rb-admin 으로 수동 조작하면
**세션이 안 닫혀서 꼬입니다.** (VESA에서 "가용 로봇 0대" 사고의 원인)

- **움직이는지만 보는 것** → **rb-admin 만** 사용, 관제 배차는 건드리지 않기
- 배차 테스트를 할 거면 → 관제/콘솔만 사용, rb-admin 수동조작 금지
- 이미 꼬였으면 → 관제 원격제어의 **[작업 강제 종료]** 로 세션만 정리

**"로봇 호출(렉 포함)"은 픽업(align + jack_up)을 자동으로 합니다.** 미리 잭업 해두면 오히려 506으로 충돌합니다.

### A-5. 자주 겪는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| rb-admin에 맵이 검게/안 뜸 | 로봇 **부팅 중** | `/maps/{id}.png` 가 503→200 되는지, `/chassis/status` 정상인지 확인 후 Ctrl+F5 |
| 명령은 받는데 제자리 | 위치추정 소실 | rb-admin **Relocate**(수동 드래그) |
| align/charge가 506 거부 | 잭이 올라간 상태 | `jack_down` 먼저 |
| 관제 지도에서 마커 안 움직임 | 지도에서 **"로봇 연결"** 을 안 함 | "위치재조정"과 "로봇 연결"은 별개 — 연결해야 실시간 이동 |
| 백엔드 로그 `속도 설정 실패` | 로봇에 못 닿음 | 망 확인. 닿으면 사라짐 |
| 태블릿에서 접속 안 됨 | 태블릿이 다른 망 | 태블릿도 같은 망으로 |

### A-6. 태블릿 주소

```
콘솔 (중앙 단말)      http://<서버PC IP>:8002/api/dispatch/console
로봇 부착 태블릿      http://<서버PC IP>:8002/api/dispatch/robot-tablet/{robot_id}
TabletApp(안드로이드) 앱 설정 → 서버 주소 http://<서버PC IP>:8002
```
> 서버 PC 를 다른 Wi-Fi 로 옮기면 이 주소도 바뀝니다:
> ```powershell

> ```
